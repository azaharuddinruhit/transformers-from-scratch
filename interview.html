Transformer fundamentals

Architecture

Q1Walk me through what happens when a prompt goes into a decoder-only LLM.

Sample answer The text is split into tokens, each token becomes a vector with position information added, and a stack of identical blocks, each attention plus an MLP with residuals and LayerNorm, refines those vectors. The last position’s vector is projected to a probability for every vocabulary token; we pick one, append it and repeat, reusing a KV cache.

  • Tokenize: text becomes T integer IDs.
  • Embed: each ID selects a row of E; add position information. Shape [T, d_model].
  • L blocks, each: masked multi-head attention, then an MLP, each wrapped in LayerNorm and a residual add. Shape never changes.
  • Output: final LayerNorm, then W_U gives logits [T, n_vocab]; softmax at the last position gives the next-token distribution.
  • Decode: choose a token (greedy or sampling), append it, repeat. The KV cache avoids recomputing earlier positions.

Likely follow-up: “Where are most of the parameters?” In the MLPs: with d_{\text{ff}}=4d_{\text{model}} an MLP has about 8d_{\text{model}}^2 weights, attention about 4d_{\text{model}}^2. Review:

Q2Explain self-attention. Why divide by \sqrt{d_k}?

Sample answer Each token builds a query, compares it with every token’s key by dot product, turns the scores into weights with a softmax and takes the weighted sum of the values. We divide by the square root of the key size because dot products grow with dimension, and unscaled scores would saturate the softmax and kill its gradients.

  • Each token is projected to a query, a key and a value.
  • Score of token j for token i is q_i\cdot k_j; softmax over j gives weights that sum to 1; the output is the weighted sum of values.
  • Matrix form: \mathrm{softmax}(QK^{\top}/\sqrt{d_k})\,V.
  • A dot product of d_k terms has a spread of about \sqrt{d_k}. Unscaled, large scores saturate softmax into near one-hot outputs with vanishing gradients. Dividing keeps the spread near 1.

Q3Why multi-head attention? What are MQA and GQA?

Sample answer Several heads let each token follow several relationships at once, at the same cost as one wide head because each works in a slice of the width. MQA and GQA let query heads share key and value heads, which shrinks the KV cache and speeds up decoding with little loss in quality.

  • One head gives each token one softmax, so one pattern of focus. Several heads capture several relationships at once (syntax, coreference, nearby tokens).
  • Each head works in d_k=d_{\text{model}}/h dimensions, so the cost and parameter count match one wide head.
  • Head outputs are concatenated and mixed by W_O.
  • MQA (multi-query): all heads share one key and value head. GQA (grouped-query): groups of query heads share a key and value head.
  • Why: the KV cache shrinks by the sharing factor, which cuts inference memory and speeds up decoding, with little quality loss.

import numpy as np


def softmax(S, axis=-1):
    e = np.exp(S - S.max(axis=axis, keepdims=True))
    return e / e.sum(axis=axis, keepdims=True)


rng = np.random.default_rng(0)
B, T, d_k = 1, 6, 16
n_q_heads, n_kv_heads = 8, 2            # GQA: 4 query heads share each KV head
group = n_q_heads // n_kv_heads

Q = rng.normal(size=(B, n_q_heads, T, d_k))
K = rng.normal(size=(B, n_kv_heads, T, d_k))   # only these are cached
V = rng.normal(size=(B, n_kv_heads, T, d_k))

# Repeat each KV head so it lines up with its group of query heads
K_full = np.repeat(K, group, axis=1)            # [B, 8, T, d_k]
V_full = np.repeat(V, group, axis=1)
S = Q @ K_full.transpose(0, 1, 3, 2) / np.sqrt(d_k)
S = np.where(np.triu(np.ones((T, T), dtype=bool), k=1), -np.inf, S)
out = softmax(S) @ V_full
print("Q", Q.shape, " cached K", K.shape, " output", out.shape)


def kv_cache_bytes(L, T, kv_heads, d_k, bytes_per_number=2):
    return 2 * L * T * kv_heads * d_k * bytes_per_number


L, T_ctx, heads, d_k = 32, 8192, 32, 128
for name, kv in [("MHA", heads), ("GQA (8 KV heads)", 8), ("MQA", 1)]:

Q4What does the causal mask do, and why does training still run in parallel?

Sample answer The causal mask sets attention scores to future positions to minus infinity, so each position sees only itself and the past. Training still runs in parallel because we feed the true text and predict every next token in one pass; the mask keeps each prediction honest.

  • It sets the scores for later positions to −∞ before softmax, so position t only sees positions ≤ t.
  • Training feeds the true text (teacher forcing) and predicts every next token in one pass; the mask makes every position’s prediction honest.
  • It matches generation, where the future does not exist yet.
  • It is also why the KV cache is exact: earlier positions never change when tokens are appended.

Q5Why do Transformers need positional encodings? What options exist?

Sample answer Attention on its own ignores order, so position has to be added. The options are fixed sinusoids, a learned position table, RoPE, which rotates queries and keys so scores depend on relative distance and is the usual choice today, and ALiBi, which penalises distant tokens.

  • Attention without a mask treats its input as a set: shuffle the tokens and the outputs shuffle with them. Order must be supplied.
  • Sinusoidal (2017 paper): fixed waves of different frequencies added to the embeddings.
  • Learned absolute (GPT-2): a trainable table, one row per position, with a hard maximum length.
  • RoPE (rotary): rotates queries and keys by a position-dependent angle so q\cdot k depends on the relative offset. Common in recent open models; context can be extended by rescaling its frequencies.
  • ALiBi: adds a distance-proportional penalty to attention scores.

In Python: rotary position embedding (RoPE)
Runs on its own · Python 3 + NumPy
import numpy as np


def rope(x, t, base=10000):
    """Rotate each pair of dimensions (2i, 2i+1) by the angle t * theta_i."""
    d = x.shape[-1]
    theta = base ** (-2 * np.arange(d // 2) / d)   # one speed per pair
    cos, sin = np.cos(t * theta), np.sin(t * theta)
    x1, x2 = x[0::2], x[1::2]
    out = np.empty_like(x)
    out[0::2] = x1 * cos - x2 * sin
    out[1::2] = x1 * sin + x2 * cos
    return out


rng = np.random.default_rng(0)
q, k = rng.normal(size=8), rng.normal(size=8)

# The score depends only on the offset between the two positions
print("q at 5,  k at 3 :", round(rope(q, 5) @ rope(k, 3), 6))
print("q at 12, k at 10:", round(rope(q, 12) @ rope(k, 10), 6))
print("q at 12, k at 3 :", round(rope(q, 12) @ rope(k, 3), 6))

# A rotation never changes a vector's length
print("length kept:", np.isclose(np.linalg.norm(rope(q, 7)), np.linalg.norm(q)))

# Output:
# q at 5,  k at 3 : -1.763129
# q at 12, k at 10: -1.763129
# q at 12, k at 3 : -1.417411
# length kept: True

Q6Why residual connections and LayerNorm? Pre-norm or post-norm?

Sample answer Residual connections let each layer learn a correction and give gradients a direct path back through a deep stack; LayerNorm keeps each token’s activations at a steady scale. Most modern models use pre-norm, often RMSNorm, because it trains more stably at depth than the original post-norm.

  • Residual (x+f(x)): layers learn corrections; the gradient has a path to early layers that bypasses all weights, so deep stacks train.
  • LayerNorm: resets each token vector to mean 0 and spread 1, plus a learned scale and shift, so activations do not drift.
  • Post-norm (2017): normalise after the add. Pre-norm (GPT-style): normalise a copy before each sublayer; easier to train at depth.
  • RMSNorm, used in many recent models, drops the mean subtraction and the bias: cheaper and about as good.

Runs on its own · Python 3 + NumPy
import numpy as np


def layer_norm(x, gamma=1.0, beta=0.0, eps=1e-5):
    mu = x.mean(axis=-1, keepdims=True)
    return gamma * (x - mu) / np.sqrt(x.var(axis=-1, keepdims=True) + eps) + beta


def rms_norm(x, gamma=1.0, eps=1e-5):
    # No mean subtraction and no beta: divide by the root mean square
    rms = np.sqrt((x ** 2).mean(axis=-1, keepdims=True) + eps)
    return gamma * x / rms


x = np.array([2.0, 4.0, 6.0, 8.0])
print("LayerNorm:", layer_norm(x).round(4))
print("RMSNorm:  ", rms_norm(x).round(4))

# On a vector that already has mean 0 the two agree
x0 = x - x.mean()
print("same when the mean is 0:", np.allclose(layer_norm(x0), rms_norm(x0)))

# Output:
# LayerNorm: [-1.3416 -0.4472  0.4472  1.3416]
# RMSNorm:   [0.3651 0.7303 1.0954 1.4606]
# same when the mean is 0: True

Q7What is the cost of attention, and how do models handle long context?

Sample answer Attention compute grows with the square of the sequence length, and at inference the KV cache grows linearly with it. FlashAttention computes exact attention in tiles to save memory traffic, and GQA, paged KV memory, quantization and sliding windows keep long contexts affordable, though models still use the middle of a long context less reliably.

  • Compute grows as T^2 d_{\text{model}}; a naive implementation stores a T\times T score matrix per head.
  • FlashAttention: exact attention computed in tiles held in fast on-chip memory, never storing the full matrix. Same result, much less memory traffic, faster.
  • Approximate or restricted attention: sliding windows, sparse patterns.
  • At inference, the KV cache grows linearly with T: GQA, paged KV memory and KV quantization address that.
  • Quality also matters: models often use information in the middle of a long context less reliably than at the start or end.

Q8Encoder-only, decoder-only, encoder–decoder: when would you use each?

Sample answer I would use an encoder-only model such as BERT for classification and embeddings, a decoder-only model for generation and general assistants, and an encoder–decoder model such as T5 for input-to-output tasks like translation. In practice a decoder-only model can also do those tasks by putting input and output in one sequence.

  • Encoder-only (BERT family): bidirectional; classification, tagging, and embedding models for search.
  • Decoder-only (GPT family): causal; generation and general-purpose assistants. The dominant LLM design.
  • Encoder–decoder (T5, the 2017 model): a separate input and output, linked by cross-attention; translation and summarisation.
  • A decoder-only model can do seq2seq tasks by putting input and output in one sequence.

Q9What is a mixture of experts (MoE)?

Sample answer A mixture of experts replaces each MLP with many expert MLPs and a router that sends each token to its top one or two. You get far more parameters for roughly the compute of a smaller dense model, but every expert must sit in memory and load balancing makes training and serving harder.

  • The MLP in each block is replaced by many expert MLPs plus a small router.
  • The router sends each token to its top-k experts (often 1 or 2).
  • Result: many more total parameters with roughly the compute per token of a much smaller dense model.
  • Costs: all experts must sit in memory, an auxiliary loss is needed to balance load across experts, training can be less stable, and serving is more complex.
In Python: a mixture-of-experts layer with a top-2 router
Runs on its own · Python 3 + NumPy
import numpy as np


def softmax(z, axis=-1):
    e = np.exp(z - z.max(axis=axis, keepdims=True))
    return e / e.sum(axis=axis, keepdims=True)


rng = np.random.default_rng(0)
T, d_model, d_ff, n_experts, top_k = 6, 8, 16, 4, 2

W_router = rng.normal(size=(d_model, n_experts))
experts = [(rng.normal(0, 0.3, size=(d_model, d_ff)),
            rng.normal(0, 0.3, size=(d_ff, d_model))) for _ in range(n_experts)]


def expert_mlp(x, e):
    W1, W2 = experts[e]
    return np.maximum(0, x @ W1) @ W2


def moe_layer(X):
    logits = X @ W_router                              # [T, n_experts]
    chosen = np.argsort(-logits, axis=1)[:, :top_k]    # top-k experts per token
    out = np.zeros_like(X)
    for t in range(len(X)):
        gates = softmax(logits[t, chosen[t]])          # weights over the chosen
        for g, e in zip(gates, chosen[t]):
            out[t] += g * expert_mlp(X[t], e)          # only k experts run
    return out, chosen


X = rng.normal(size=(T, d_model))
out, chosen = moe_layer(X)
print("output shape:", out.shape)
print("experts chosen per token:", chosen.tolist())
print("tokens per expert (load):", np.bincount(chosen.ravel(), minlength=n_experts))
print(f"each token runs {top_k} of {n_experts} expert MLPs")

# Output:
# output shape: (6, 8)
# experts chosen per token: [[0, 2], [0, 2], [0, 2], [1, 0], [1, 3], [1, 3]]
# tokens per expert (load): [4 3 3 2]
# each token runs 2 of 4 expert MLPs

Training

Q10What is the pretraining objective? What is perplexity?

Sample answer Pretraining minimises the cross-entropy of predicting each next token, so raw text provides its own labels. Perplexity is e to the power of that loss, the effective number of tokens the model is choosing between, and it is only comparable between models that share a tokenizer.

  • Next-token prediction with cross-entropy: the average of -\log p(correct next token) over all positions.
  • Self-supervised: the targets are the text itself shifted by one, so any raw text is training data.
  • Perplexity = e^{\mathcal{L}}: the effective number of tokens the model is choosing between. Lower is better.
  • Sanity check: an untrained model has loss near \ln n_{\text{vocab}}, perplexity near n_{\text{vocab}}.

Trap: comparing perplexity across models with different tokenizers. The numbers are per token, and tokens differ. Review:

Q11How does a base model become a chat assistant?

Sample answer Pretraining gives the model knowledge and language, supervised fine-tuning on prompt–response pairs teaches it to follow instructions in a chat format, and preference tuning with RLHF or DPO shapes helpfulness, tone and safety. Evaluation and red-teaming run throughout.

  • Pretraining on a very large text corpus: knowledge and language.
  • Supervised fine-tuning (SFT) on prompt–response examples: follows instructions, uses a chat format.
  • Preference tuning (RLHF or DPO) on pairs of better and worse answers: helpfulness, tone, safety.
  • Throughout: evaluation, red-teaming, safety data. Some models add training for reasoning or tool use.

Q12Why AdamW, warm-up and gradient clipping?

Sample answer AdamW gives each parameter its own step size from running gradient statistics and applies weight decay separately from that step. Warm-up keeps early updates small while those statistics are unreliable, and gradient clipping stops one bad batch from causing a loss spike.

  • Adam keeps running averages of each parameter’s gradient and squared gradient, giving every parameter its own step size.
  • AdamW applies weight decay directly to the weights, separate from the adaptive step.
  • Warm-up: early gradients are noisy and Adam’s estimates are poor, so the learning rate starts small, then decays.
  • Gradient clipping caps the gradient norm, preventing one bad batch from causing a loss spike.

Q13The loss curve misbehaves. How do you diagnose it?

Sample answer I first check the shape of the curve: spikes or NaN point to the learning rate, warm-up, precision or a bad batch, and a flat loss from the start points to a bug, which I confirm by overfitting one small batch. If training loss falls while validation loss rises it is overfitting, and if both plateau high the model is too small or the learning rate too low.

  • Loss spikes or NaN: learning rate too high, missing warm-up, bad data batch, precision overflow. Lower the LR, clip gradients, use bf16, inspect the batch.
  • Flat from the start: bug. Overfit one small batch first; check that labels are shifted and that the mask is right.
  • Train falls, validation rises: overfitting. More data, dropout or weight decay, early stopping.
  • Both plateau high: model too small or LR too low.

Q14What do scaling laws say? What is “Chinchilla-optimal”?

Sample answer Loss falls as a smooth power law in parameters, data and compute, and training costs about six times parameters times tokens in FLOPs. Chinchilla showed that for a fixed budget you should grow both together, about 20 tokens per parameter, though today models are often trained far longer because smaller models are cheaper to serve.

  • Loss falls as a smooth power law in parameters N, data D and compute, until one of them becomes the bottleneck.
  • Training compute is about 6ND FLOPs.
  • Hoffmann et al. (2022): for a fixed compute budget, grow N and D together, roughly 20 tokens per parameter.
  • In practice many models are trained on far more tokens than that: a smaller model is cheaper to serve, and serving cost dominates over the model’s lifetime.

Inference

Q15What is the KV cache, and how much memory does it use?

Sample answer The KV cache stores the keys and values of earlier tokens so each decoding step computes only the new token, which is exact because of the causal mask. It takes about two times layers times tokens times the key–value width times bytes per number, per request, and it often limits how many users one GPU can serve.

  • During generation, the keys and values of earlier tokens are stored and reused; each step computes only the new token.
  • Valid because of the causal mask: earlier positions never change.
  • Memory ≈ 2 × layers × tokens × (KV heads × d_k) × bytes per number × batch. Without GQA the bracket is d_{\text{model}}.
  • It grows with context length and concurrent requests, and often limits how many users one GPU can serve.

Q16Prefill versus decode: why are they different?

Sample answer Prefill processes the whole prompt in one parallel pass, so it is limited by compute and sets the time to the first token. Decode produces one token per step and rereads all the weights each time, so it is limited by memory bandwidth and sets tokens per second; batching helps because requests share each read.

  • Prefill: the whole prompt in one parallel pass. Compute-bound. Sets time to first token.
  • Decode: one token per step, reading all weights each step. Memory-bandwidth-bound. Sets tokens per second.
  • Batching many requests raises decode throughput because they share each read of the weights.

Q17How would you make inference cheaper or faster?

Sample answer I would quantize the weights, serve with continuous batching and paged KV memory as vLLM does, cache shared prompt prefixes, and use speculative decoding. Beyond that, route easy requests to a smaller or distilled model and keep prompts and outputs short, checking quality on our eval after each change.

  • Quantization: 8- or 4-bit weights (e.g. GPTQ, AWQ) cut memory and bandwidth; check quality on your own eval.
  • Continuous batching and paged KV memory (as in vLLM): keep the GPU full and memory unfragmented.
  • Speculative decoding: a small draft model proposes several tokens, the large model checks them in one pass; with correct acceptance sampling the output distribution is unchanged.
  • Prefix (prompt) caching for shared system prompts and documents.
  • Smaller or distilled model, routing easy requests to it; shorter prompts; capped output length.

Q18Explain temperature, top-k and top-p. Is temperature 0 deterministic?

Sample answer Temperature scales the logits, sharper below 1 and flatter above, while top-k and top-p cut off the unlikely tail before sampling. Temperature 0 means greedy decoding, but results can still vary between runs because batching and floating-point order are not fully deterministic.

  • Temperature divides logits: below 1 sharpens, above 1 flattens; the ranking never changes.
  • Top-k keeps the k most likely tokens; top-p keeps the smallest set whose probabilities reach p. Both cut the unreliable tail.
  • Low temperature for extraction, classification and code; higher for brainstorming.
  • Temperature 0 means greedy, but outputs can still vary run to run in practice, because batching and floating-point arithmetic order are not fully deterministic.

Concepts

Q1What is RAG, and when would you choose it over fine-tuning?

Sample answer RAG retrieves relevant passages for each question and puts them in the prompt, so I choose it when the gap is knowledge, especially private or changing documents, because updating means re-indexing and it gives citations and access control. I would fine-tune for behaviour such as format or style, and the two combine well.

  • Retrieve relevant passages for each query and include them in the prompt.
  • Use RAG for knowledge: private, changing or very large document sets. Updating means re-indexing, not retraining.
  • Gives citations and lets you enforce access control per user.
  • Use fine-tuning for behaviour: format, style, tone, domain phrasing. The two combine well.

Trap: “fine-tune the model on our docs so it knows them.” Fine-tuning is unreliable for adding facts and cannot cite or be updated cheaply.

Q2What is an embedding model, and how is similarity measured?

Sample answer An embedding model maps a whole text to one vector, trained so related texts land close together, and we compare vectors with cosine similarity. Because queries and documents are embedded separately, document vectors are computed once and search stays fast.

  • A model, often encoder-only, that maps a text to one vector; trained contrastively so related texts land close together.
  • Similarity is usually cosine similarity (a dot product of normalised vectors).
  • Bi-encoder: query and documents are embedded separately, so document vectors are computed once and search is fast.
  • Different from the token embeddings inside an LLM: one vector per text, not per token.

In Python: cosine similarity search
Runs on its own · Python 3 + NumPy
import re
import numpy as np

docs = [
    "Reset your password from the account settings page.",
    "Expense claims must be filed within 30 days of purchase.",
    "The VPN client needs to be updated before connecting.",
    "Annual leave requests go to your line manager for approval.",
    "Forgotten password? Use the self-service reset link.",
]
words = lambda text: re.findall(r"[a-z0-9]+", text.lower())
vocab = sorted({w for d in docs for w in words(d)})


def embed(text):
    # Word counts stand in for a real embedding model here; the search code
    # below is the same whichever model produces the vectors.
    v = np.array([words(text).count(w) for w in vocab], dtype=float)
    return v / (np.linalg.norm(v) or 1.0)          # normalise to length 1


doc_vectors = np.stack([embed(d) for d in docs])   # computed once, offline


def search(query, k=2):
    scores = doc_vectors @ embed(query)            # cosine = dot of unit vectors
    best = np.argsort(-scores)[:k]
    return [(round(float(scores[i]), 3), docs[i]) for i in best]


for score, doc in search("how do I reset my password"):
    print(score, doc)

# Output:
# 0.5 Reset your password from the account settings page.
# 0.5 Forgotten password? Use the self-service reset link.

Q3How do you chunk documents?

Sample answer I split on the document’s structure, such as headings, paragraphs and table rows, into chunks of a few hundred tokens with some overlap, then tune the size on the eval. Each chunk carries metadata such as title, section path, date and permissions, and a parent–child scheme can retrieve small chunks but pass their larger section to the model.

  • Chunk size trades precision against context: small chunks match precisely but lose surrounding meaning; large chunks dilute the embedding and waste prompt space.
  • A common start: a few hundred tokens with some overlap, then tune on your eval.
  • Split on structure (headings, paragraphs, code blocks, table rows), not at a fixed character count.
  • Attach metadata: title, section path, date, source URL, permissions.
  • Parent–child: retrieve small chunks, pass their larger parent section to the model.

Q4How does vector search scale to millions of chunks?

Sample answer Comparing the query with every vector is too slow at scale, so we use an approximate nearest-neighbour index such as HNSW, IVF or product quantization, which trades a little recall for a large speed-up. Metadata filters run during the search, and the tool, from pgvector to a dedicated vector database, depends on scale and operations effort.

  • Exact search compares the query to every vector: too slow at scale.
  • Approximate nearest neighbour (ANN) indexes trade a little recall for large speed-ups: HNSW (navigable graph), IVF (search only nearby clusters), PQ (compressed vectors).
  • Filter on metadata (permissions, date, product) during search.
  • Tooling ranges from pgvector or FAISS to dedicated vector databases; choose by scale, filtering needs and operations effort.

Q5Why hybrid search and reranking?

Sample answer Embeddings capture meaning but miss exact strings such as error codes or product IDs, so I run keyword search alongside and merge the lists, for example with reciprocal rank fusion. A cross-encoder reranker then rescores the top few dozen results, which is accurate but too slow for the whole corpus, and only the best few go to the model.

  • Embeddings capture meaning but miss exact strings: error codes, product IDs, names. Keyword search (BM25) catches those.
  • Run both and merge the lists, for example with reciprocal rank fusion.
  • A cross-encoder reranker reads query and passage together: much more accurate than a bi-encoder, but too slow for the whole corpus, so apply it to the top 20 to 100.
  • Then send only the best few passages to the LLM.

Runs on its own · Python 3, standard library only
from collections import defaultdict


def reciprocal_rank_fusion(rankings, k=60):
    """Merge ranked lists: each list adds 1 / (k + rank) to a document."""
    scores = defaultdict(float)
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] += 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

keyword_hits = ["doc4", "doc7", "doc1"]          # BM25 order (exact terms)

def recall_at_k(retrieved, relevant, k):
    """Share of the relevant chunks that appear in the top k."""
    return len(set(retrieved[:k]) & relevant) / len(relevant)


def reciprocal_rank(retrieved, relevant):
    """1 / position of the first relevant chunk (0 if none was found)."""
    for rank, doc_id in enumerate(retrieved, start=1):
        if doc_id in relevant:
            return 1 / rank
    return 0.0

Q3Full fine-tuning versus LoRA. How does LoRA work?

Sample answer Full fine-tuning updates every weight and needs about 16 bytes per parameter for weights, gradients and Adam state. LoRA freezes each weight matrix and learns a low-rank update B times A, often under 1% of the parameters, starting from zero and mergeable into the weights afterwards, so there is no extra latency.

  • Full fine-tuning updates every weight. Memory holds weights, gradients and optimizer state: roughly 16 bytes per parameter with Adam in mixed precision.
  • LoRA freezes each chosen weight matrix W and learns a low-rank update: W'=W+\tfrac{\alpha}{r}BA, with rank r much smaller than the matrix sides.
  • Trainable parameters per matrix: r\,(d_{\text{in}}+d_{\text{out}}), often well under 1% of the model.
  • B starts at zero, so training starts from the original model.
  • After training, BA can be merged into W (no extra latency), or kept as a swappable per-task adapter.

Likely follow-up: “Which matrices get adapters?” Originally the attention projections; applying it to all linear layers often works better. Review:

In Python: a LoRA layer
Runs on its own · Python 3 + PyTorch
import torch
import torch.nn as nn

torch.manual_seed(0)


class LoRALinear(nn.Module):
    """W' = W + (alpha / r) * B A, with W frozen and only A, B trained."""

    def __init__(self, base: nn.Linear, r=4, alpha=8):
        super().__init__()
        self.base = base
        self.base.requires_grad_(False)                      # freeze W and b
        self.A = nn.Parameter(torch.randn(r, base.in_features) * 0.01)
        self.B = nn.Parameter(torch.zeros(base.out_features, r))  # starts at 0
        self.scale = alpha / r

    def forward(self, x):
        return self.base(x) + (x @ self.A.T @ self.B.T) * self.scale

    def merged(self) -> nn.Linear:
        """Fold B A into W: no extra cost at inference time."""
        out = nn.Linear(self.base.in_features, self.base.out_features)
        with torch.no_grad():
            out.weight.copy_(self.base.weight + self.scale * self.B @ self.A)
            out.bias.copy_(self.base.bias)
        return out


base = nn.Linear(512, 512)              # PyTorch stores W as [out, in]
layer = LoRALinear(base, r=4)
x = torch.randn(3, 512)
print("same output as base at start:", torch.allclose(layer(x), base(x)))

trainable = sum(p.numel() for p in layer.parameters() if p.requires_grad)
print(f"trainable {trainable:,} of {trainable + base.weight.numel():,} weights",
      f"= r * (d_in + d_out) = {4 * (512 + 512):,}")

# A few training steps on a made-up target; only A and B change
opt = torch.optim.AdamW([layer.A, layer.B], lr=1e-2)
target = torch.randn(3, 512)
for _ in range(20):
    loss = ((layer(x) - target) ** 2).mean()
    opt.zero_grad()
    loss.backward()
    opt.step()
print("base weights unchanged:", torch.equal(layer.base.weight, base.weight))
print("merged layer matches adapter:",
      torch.allclose(layer.merged()(x), layer(x), atol=1e-5))

# trainable 4,096 of 266,240 weights = r * (d_in + d_out) = 4,096

Q7Explain RLHF.

Sample answer RLHF collects human judgements of which of two responses is better, trains a reward model to predict them, and then optimises the LLM with reinforcement learning, classically PPO, to maximise that reward. A KL penalty keeps it close to the SFT model, and the whole process is effective but complex and unstable.

  • Collect human comparisons: for one prompt, which of two responses is better.
  • Train a reward model to predict those preferences.
  • Optimise the policy (the LLM) with reinforcement learning, classically PPO, to maximise reward.
  • Add a KL penalty that keeps the policy close to the SFT model.
  • Effective but complex: several models in memory, sensitive hyperparameters, unstable training.

Q8What is DPO, and why is it popular?

Sample answer DPO trains directly on chosen and rejected response pairs, raising the probability of the chosen one relative to a frozen reference model. It needs no separate reward model or RL loop, so it is simpler and more stable and gives similar results in many settings.

  • Direct Preference Optimization trains directly on preference pairs (chosen, rejected).
  • Its loss raises the probability of the chosen response relative to the rejected one, measured against a frozen reference model.
  • No separate reward model and no RL loop: simpler and more stable, similar results in many settings.
  • Many variants exist; the core idea is preference learning as a classification-style loss.
In Python: the DPO loss
Runs on its own · Python 3 + PyTorch
import torch
import torch.nn.functional as F


def sequence_logprob(logits, labels):
    """Sum of log p(token) over a response. logits [T, V], labels [T]."""
    logp = F.log_softmax(logits, dim=-1)
    return logp[torch.arange(len(labels)), labels].sum()


def dpo_loss(pi_chosen, pi_rejected, ref_chosen, ref_rejected, beta=0.1):
    """Inputs are summed log-probabilities of whole responses, shape [batch]."""
    margin = (pi_chosen - ref_chosen) - (pi_rejected - ref_rejected)
    return -F.logsigmoid(beta * margin).mean()


torch.manual_seed(0)
logits, labels = torch.randn(5, 10), torch.randint(0, 10, (5,))
print(f"log p(response) = {sequence_logprob(logits, labels).item():.3f}")

ref_c, ref_r = torch.tensor([-12.0]), torch.tensor([-11.0])  # frozen reference

# Policy equal to the reference: loss = ln 2
print(f"policy = reference: {dpo_loss(ref_c, ref_r, ref_c, ref_r).item():.4f}")

# Policy now prefers the chosen answer more than the reference does
pi_c, pi_r = torch.tensor([-9.0]), torch.tensor([-14.0])
print(f"policy prefers chosen: {dpo_loss(pi_c, pi_r, ref_c, ref_r).item():.4f}")

# The gradient raises the chosen log-prob and lowers the rejected one
pi_c = torch.tensor([-12.0], requires_grad=True)
pi_r = torch.tensor([-11.0], requires_grad=True)
dpo_loss(pi_c, pi_r, ref_c, ref_r).backward()
print(f"step direction: chosen {-pi_c.grad.item():+.3f}, "
      f"rejected {-pi_r.grad.item():+.3f}")

Building agents

Q1What is an agent, and when should you not build one?

Sample answer An agent is an LLM that decides its own sequence of tool calls from what it observes until the goal is met, whereas a workflow fixes the steps in code. I would not build one when a single call or a fixed workflow will do, because agents are slower, costlier and harder to test, and their errors compound.

  • An LLM that chooses its own sequence of actions (tool calls) based on what it observes, until a goal is met.
  • A workflow is different: code fixes the steps and calls the LLM at chosen points.
  • Prefer the simplest thing that works: one call, then a fixed chain or workflow, then an agent only when the steps cannot be known in advance.
  • Agents cost more, are slower and harder to test, and errors compound over steps.

Q2How does tool (function) calling work?

Sample answer You describe each tool with a name, a description and a JSON schema; the model replies with a structured call naming a tool and its arguments. Your code validates and runs it and sends the result back, and the model either calls another tool or answers. The model never executes anything itself.

  • You describe each tool to the model: a name, a description and a JSON schema for its parameters.
  • The model replies with a structured call: tool name plus arguments.
  • Your code validates the arguments, executes the tool and sends back the result; the model never executes anything itself.
  • The model then continues: another call, or a final answer.
In Python: a tool-calling loop
Runs on its own · Python 3, standard library only
import json

# 1. Describe each tool: name, description and a JSON schema for its arguments
TOOLS = {
    "get_order_status": {
        "description": "Look up the delivery status of an order by its ID.",
        "parameters": {"type": "object",
                       "properties": {"order_id": {"type": "string"}},
                       "required": ["order_id"]},
        "run": lambda order_id: {"order_id": order_id, "status": "shipped",
                                 "eta": "2 days"},
    },
}


def fake_model(messages, tools):
    """Stands in for an LLM API call. Real providers return the same shape:
    either a tool call (name + JSON arguments) or a final text answer."""
    if messages[-1]["role"] == "user":
        return {"tool_call": {"name": "get_order_status",
                              "arguments": json.dumps({"order_id": "A-1042"})}}
    result = json.loads(messages[-1]["content"])
    return {"text": f"Order {result['order_id']} has {result['status']}; "
                    f"it should arrive in {result['eta']}."}


def validate(args, schema):
    missing = [k for k in schema["required"] if k not in args]
    if missing:
        raise ValueError(f"missing arguments: {missing}")


def run_agent(user_message, max_steps=5):
    messages = [{"role": "user", "content": user_message}]
    specs = {n: {k: v for k, v in t.items() if k != "run"} for n, t in TOOLS.items()}
    for step in range(max_steps):                    # always cap the loop
        reply = fake_model(messages, specs)
        if "text" in reply:                          # 4. final answer: stop
            return reply["text"]
        call = reply["tool_call"]                    # 2. model asks for a tool
        tool = TOOLS[call["name"]]
        args = json.loads(call["arguments"])
        validate(args, tool["parameters"])           # 3. your code checks ...
        result = tool["run"](**args)                 #    ... and runs it
        print(f"step {step}: {call['name']}({args}) -> {result}")
        messages.append({"role": "tool", "content": json.dumps(result)})
    return "Stopped: step limit reached."


print(run_agent("Where is my order A-1042?"))

Frameworks

Q7What do frameworks such as LangChain and LangGraph give you, and when would you skip them?

Sample answer LangChain gives integrations behind one interface and agent building blocks such as create_agent, and LangGraph is a lower-level runtime for stateful agents with persistence, streaming and human approval. I use them when I need durable state, approvals or many integrations, and write plain code for a single call or a fixed chain, because frameworks add a layer to debug and change quickly.

  • LangChain: integrations behind one interface (many model providers, tools, vector stores) and agent building blocks; create_agent builds a tool-calling agent from a model, tools and a system prompt.
  • LangGraph: a lower-level runtime for long-running, stateful agents. You define the flow as a graph; it adds persistence, streaming and pauses for human input. It does not need LangChain, and LangChain’s agents are built on it.
  • Gains: less boilerplate, switching providers by configuration, durable state and approval steps without writing them yourself.
  • Costs: another layer to debug, APIs that change quickly, and a dependency to keep up to date. The core agent loop is short enough to write yourself.
  • Rule of thumb: plain code for a single call or a fixed chain; a framework when you need durable state, human approval or many integrations.

Trap: knowing only a framework’s API. Interviewers want the loop underneath: the model call, the tool execution, the state and the stop condition.

Q8Why model an agent as a graph instead of a plain loop?

Sample answer A graph makes the control flow explicit: nodes are steps, edges say what runs next, conditional edges branch on a shared state, and loops are visible and bounded. Each node can be tested on its own, and adding a retry or a review step is just another node and edge.

  • Nodes are steps (call the model, run a tool, check the output); edges say what runs next; conditional edges choose the next step from the state.
  • State is one shared record that every node reads and updates. In LangGraph, a reducer decides how an update merges, for example appending messages instead of replacing them.
  • Loops still exist (model → tool → model), but they are explicit and bounded, and fixed steps and model-driven steps sit in the same graph.
  • Each node can be tested alone, and adding a retry, a review step or a branch is one more node and edge.
  • In LangGraph: StateGraph, add_node, add_edge, add_conditional_edges, START and END, then compile().

def call_model(state):
    if "order" not in state:
        return {"action": "lookup_order"}
    if state["order"]["status"] == "damaged" and "refund" not in state:
        return {"action": "refund", "amount": 40}
    return {"action": "finish", "answer": state.get("refund", "No refund needed.")}


class Interrupt(Exception):
    """Raised by a node to pause the run until a person answers."""


def model_node(state, resume):
    state["next"] = call_model(state)


def lookup_node(state, resume):
    state["order"] = {"id": "A-1042", "status": "damaged"}   # stands in for a tool


def refund_node(state, resume):
    # On resume the node runs again from its start, so nothing before the pause
    # may have side effects (LangGraph's interrupt() behaves the same way)
    if resume is None:
        raise Interrupt(f"approve a refund of {state['next']['amount']}?")
    state["refund"] = "Refund issued." if resume == "yes" else "Refund declined."


NODES = {"model": model_node, "lookup_order": lookup_node, "refund": refund_node}
EDGES = {"lookup_order": "model", "refund": "model"}       # tools return to the model


def route(state):                                          # conditional edge
    action = state["next"]["action"]
    return "END" if action == "finish" else action


CHECKPOINTS = {}                                           # thread_id -> (state, node)


def run(thread_id, state=None, resume=None, max_steps=10):
    if state is None:                                      # resume from the checkpoint
        state, node = copy.deepcopy(CHECKPOINTS[thread_id])
    else:
        node = "model"
    for _ in range(max_steps):
        print("  step:", node)
        try:
            NODES[node](state, resume)

            return f"paused, {pause}"

        CHECKPOINTS[thread_id] = (copy.deepcopy(state), node)
        if node == "END":
            return state["next"]["answer"]
    return "stopped at the step limit"

Q9How do checkpoints and human approval work in a stateful agent?

Sample answer A checkpointer saves the graph’s state under a thread ID as it runs, so a run can resume after a crash or a pause. For approval a node calls interrupt() to pause and hand an action to a person, and the run resumes on the same thread with their answer, rerunning that node from its start, so anything before the pause must be safe to repeat.

  • A checkpointer saves the graph’s state as it runs, under a thread ID. A run can then resume after a crash or a pause, and a conversation can continue later.
  • For approval, a node pauses the run (LangGraph’s interrupt()) and hands back a payload, such as the action it wants to take. Your application shows it to a person.
  • The run resumes on the same thread with the person’s answer (Command(resume=...)), which becomes the return value of interrupt().
  • Use a durable checkpointer in production, such as one backed by Postgres; in-memory ones lose everything on restart.

Trap: on resume, the paused node runs again from its start, so anything it does before the pause must be safe to repeat. Likely follow-up: “How is this different from long-term memory?” Checkpoints belong to one thread, one conversation; a separate store holds what should persist across threads.

Reliability and safety

Q10How do agents fail, and how do you mitigate it?

Sample answer Agents loop, choose the wrong tool or invent arguments, compound errors over long tasks, overflow their context and claim success too early. I add step and cost limits, validate arguments, keep tasks short with verification steps, summarise history, and check the end state with code.

  • Loops and repeated actions: step, time and cost limits; detect repeats.
  • Wrong tool or invented arguments: clearer tool descriptions, validation, fewer tools.
  • Errors compound over long tasks: shorter tasks, checkpoints, verification steps.
  • Context overflow: summarise history, keep tool outputs short.
  • Stopping too early or claiming success: check the end state with code where possible.

Q11What are the security risks of agents?

Sample answer The biggest risk is prompt injection from web pages, emails or files, so I treat every tool output as untrusted data. I give agents only the permissions they need, require human confirmation for irreversible or outward-facing actions, sandbox code and keep audit logs, assuming an injected instruction will eventually get through.

  • Prompt injection: web pages, emails or files contain instructions the model may follow. Treat all tool output as untrusted data.
  • Least privilege: only the tools and permissions the task needs.
  • Human confirmation for irreversible or outward-facing actions: payments, deletions, sending messages.
  • Sandbox code execution; keep audit logs of every action.
  • Assume an injected instruction will eventually get through, and limit what damage it could do.

Evaluation

Q1How do you evaluate an LLM feature?

Sample answer I agree on what success means with stakeholders, then build an eval set of real inputs, edge cases and adversarial cases, each with a reference answer or rubric. Scoring depends on the output: exact checks for structured output, a calibrated LLM judge for open text, human review for a sample; it runs on every change, followed by online metrics after launch.

  • Agree on what success means with stakeholders, and turn it into measurable criteria.
  • Build an eval set: real user inputs, edge cases, adversarial cases; a reference answer or rubric for each.
  • Choose the scorer by output type: exact match or parsing checks for structured output; task metrics; an LLM judge with a rubric for open-ended text; human review for a sample.
  • Run it offline on every prompt or model change, like a regression test; measure online after launch (A/B tests, feedback, task completion).

Q2What are the pitfalls of LLM-as-judge?

Sample answer LLM judges favour the first answer, longer answers and their own model family’s style, and they tend to be lenient. I give them a specific rubric with examples, run pairwise comparisons in both orders, score narrow criteria, and check agreement with human labels before trusting the scores.

  • Biases: position (prefers the first answer), verbosity (prefers longer), self-preference (prefers its own model family’s style), leniency.
  • Mitigate: a specific rubric with examples, pairwise comparison run in both orders, scores on narrow criteria rather than “overall quality”.
  • Calibrate: measure agreement with human labels on a sample before trusting it.

Q3What causes hallucinations, and how do you reduce them?

Sample answer Models are trained to produce probable text, not verified facts, so gaps get filled with plausible guesses. I ground answers in retrieved sources with citations, let the model say “I don’t know”, use low temperature and verification steps for high-stakes claims, and measure the rate on our eval, knowing it never reaches zero.

  • The model is trained to produce probable text, not verified facts; gaps and outdated knowledge get filled with plausible guesses.
  • Ground answers in retrieved sources and require citations.
  • Let the model say “I don’t know”, and reward that in your eval.
  • Low temperature for factual tasks; a verification step for high-stakes claims; human review where errors are costly.
  • Measure the hallucination rate on your eval; it does not reach zero.

def monthly_cost(requests_per_day, input_tokens, output_tokens,
                 price_in_per_m, price_out_per_m, cached_share=0.0,

    return per_request, per_request * requests_per_day * 30

In Python: retries with backoff, then a fallback
Runs on its own · Python 3, standard library only
import random
import time


class TransientError(Exception):
    """Rate limit, timeout or 5xx: worth retrying."""


def call_with_retries(fn, max_attempts=5, base_delay=0.05, max_delay=2.0):
    for attempt in range(1, max_attempts + 1):
        try:
            return fn()
        except TransientError as err:
            if attempt == max_attempts:
                raise                                  # give up: let a fallback run
            # Exponential backoff with full jitter spreads retries out
            delay = random.uniform(0, min(max_delay, base_delay * 2 ** attempt))
            print(f"attempt {attempt} failed ({err}); retrying in {delay:.3f} s")
            time.sleep(delay)


random.seed(0)
failures = iter([TransientError("429 rate limited"), TransientError("timeout")])


def flaky_llm_call():                                 # stands in for an API call
    err = next(failures, None)
    if err:
        raise err
    return "answer"


def with_fallback(primary, fallback):
    try:
        return call_with_retries(primary)
    except TransientError:
        return fallback()


print(with_fallback(flaky_llm_call, lambda: "answer from the backup model"))

# attempt 1 failed (429 rate limited); retrying in 0.084 s
# attempt 2 failed (timeout); retrying in 0.152 s

Memory, bandwidth and the CUDA stack: the questions that come up when a team runs its own models.

Q1How much GPU memory do you need to serve a model?

Sample answer Memory is the weights, parameters times bytes per parameter, so 140 GB for a 70B model in bf16, plus the KV cache for every concurrent request, plus a 10 to 20% margin. If that does not fit, I quantize, choose a smaller model, shorten the context or cap concurrency, or split the model across GPUs.

  • Weights: parameters × bytes per parameter (2 for bf16, 0.5 for int4). A 70B model in bf16 is 140 GB.
  • KV cache: 2 × layers × context length × key–value width × 2 bytes, for every request served at once. Grouped-query attention shrinks the width.
  • A margin of 10–20% for the CUDA context, activations and fragmentation.
  • If it does not fit: quantize, choose a smaller model, shorten the context or cap concurrency, or split the model across GPUs with tensor parallelism.

Q2Why is decoding limited by memory bandwidth, and what follows from that?

Sample answer Each decode step reads every weight to produce one token per request, about one operation per byte, while a GPU such as the H100 can do about 295 operations per byte of bandwidth, so the tensor cores wait for memory. That is why quantization speeds decoding up, batching raises throughput almost for free, and for chat-style serving I compare GPUs by memory bandwidth before TFLOPS.

  • Each decode step reads every weight once to produce one token per request: about one operation per byte read.
  • GPUs can do hundreds of operations per byte of bandwidth (an H100 about 295), so at small batch sizes the tensor cores wait for memory.
  • So quantization speeds up decoding as well as saving memory; batching raises throughput almost for free; for interactive use, compare GPUs by memory and bandwidth before TFLOPS.
  • Prefill is the opposite: all prompt tokens share each weight read, so it is limited by compute.

Trap: quoting the headline TFLOPS. Data-centre figures are usually given with sparsity, twice the dense rate. Review: ,

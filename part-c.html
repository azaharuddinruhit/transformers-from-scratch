    The loss: cross-entropy, derived

    What we want: a model that gives real text a high probability. From , the probability of a text is a product of next-token probabilities, \prod_t p_\theta(w_t\mid w_{\lt t}).

    Make it workable. A product of thousands of numbers below 1 is astronomically small and awkward to differentiate. Taking the logarithm turns the product into a sum without changing which parameters are best.

    Turn it into something to minimise. Optimizers minimise, so flip the sign. Then divide by the number of tokens so the value does not depend on how long the text is:

    \mathcal{L}(\theta)=-\frac{1}{T}\sum_{t=1}^{T}\log p_{\theta}\!\left(w_t \mid w_{\lt t}\right)

    \theta stands for all the parameters; p_\theta(w_t\mid w_{\lt t}) is the probability the model gave to the token that really came next; \log is the natural logarithm. In words: \mathcal{L}=-\sum_t\log p(\text{target}_t\mid\text{tokens}_{\lt t}), averaged over positions.

    Why -\log?
    It is 0 when the model gave the correct token probability 1, and it grows without limit as that probability approaches 0. So a confident mistake is punished far more than a hesitant one. It also has a plain reading: the loss is the model’s average surprise at the real text. A useful reference point: guessing uniformly gives every token probability 1/n_{\text{vocab}}, hence a loss of \ln n_{\text{vocab}}. An untrained model starts near that value.

    Teacher forcing

    The targets are just the inputs shifted one place left, so a single sequence of T tokens provides T training examples. At every position the model is given the true previous tokens rather than its own guesses; this is called teacher forcing. Combined with the causal mask (), it lets all positions be trained in one parallel pass.

    inputthe␣ca
    targethe␣cat

    From loss to learning

    • Batching: B sequences are processed together so the update reflects an average over examples and the hardware is used efficiently.
    • Backpropagation: the chain rule, applied mechanically from the loss back through every layer, yields the gradient \nabla_\theta\mathcal{L}: for each parameter, how much the loss would rise if that parameter increased slightly.
    • Gradient descent: move every parameter a small step in the direction that lowers the loss.
    \theta\leftarrow\theta-\eta\,\nabla_{\theta}\mathcal{L}

    \eta is the learning rate, the step size.

    Why the minus sign?
    The gradient points in the direction in which the loss increases fastest, so we step the opposite way. \eta controls how far: too small and training crawls, too large and each step overshoots. It usually warms up from zero, then decays. In practice the optimizer (Adam or AdamW) replaces the raw gradient with a running average that gives each parameter a step size suited to it. One elegant fact: for softmax with this loss, the gradient with respect to each logit is simply “predicted probability minus 1 for the correct token, predicted probability for every other”. The model is pushed in proportion to how wrong it was.

    Worked example

    Suppose the model gave the three correct next tokens probabilities 0.5,\ 0.25,\ 0.9.

    Per-token losses: -\ln0.5=0.6931,\ \ -\ln0.25=1.3863,\ \ -\ln0.9=0.1054. Mean loss \mathcal{L}=2.1848/3=0.7283.

    One gradient-descent step on a single weight: \theta=2.0, gradient 0.5, learning rate \eta=0.1 gives \theta\leftarrow2.0-0.1\times0.5=1.95.

    The uniform baseline for the 21-character model below is \ln 21=3.0445.

    Loss measures surprise. A confident correct guess costs almost nothing, an unsure guess costs a little, and a confident wrong guess costs a lot. Training rolls downhill on that number in small steps.

    import math
import torch
import torch.nn as nn
import torch.nn.functional as F

torch.manual_seed(0)

# Training text: sentences like the toy model's, read character by character
subjects = ["the cat", "the dog", "a bird", "the fox"]
verbs = ["sat on", "saw", "ran to", "likes"]
objects = ["the mat", "a box", "the tree", "the sofa"]
text = " ".join(f"{s} {v} {o}." for s in subjects for v in verbs for o in objects)
chars = sorted(set(text))
stoi = {c: i for i, c in enumerate(chars)}
data = torch.tensor([stoi[c] for c in text])
n_vocab, T, B = len(chars), 16, 32


class TinyGPT(nn.Module):
    def __init__(self, d_model=48, n_head=2, n_layer=2):
        super().__init__()
        self.tok = nn.Embedding(n_vocab, d_model)
        self.pos = nn.Embedding(T, d_model)
        layer = nn.TransformerEncoderLayer(
            d_model, n_head, 4 * d_model, dropout=0.0, activation="gelu",
            batch_first=True, norm_first=True)          # pre-norm block
        self.blocks = nn.TransformerEncoder(layer, n_layer,
                                            enable_nested_tensor=False)
        self.ln = nn.LayerNorm(d_model)
        self.head = nn.Linear(d_model, n_vocab)        # W_U

    def forward(self, idx):                            # idx: [B, T]
        t = idx.shape[1]
        x = self.tok(idx) + self.pos(torch.arange(t))
        mask = nn.Transformer.generate_square_subsequent_mask(t)
        x = self.blocks(x, mask=mask, is_causal=True)
        return self.head(self.ln(x))                   # logits: [B, T, n_vocab]


def get_batch():
    starts = torch.randint(len(data) - T - 1, (B,))
    x = torch.stack([data[s:s + T] for s in starts])
    y = torch.stack([data[s + 1:s + T + 1] for s in starts])  # shifted by one
    return x, y


model = TinyGPT()
opt = torch.optim.AdamW(model.parameters(), lr=3e-3, weight_decay=0.01)
print(f"{sum(p.numel() for p in model.parameters()):,} parameters,",
      f"uniform baseline ln {n_vocab} = {math.log(n_vocab):.3f}")

for step in range(601):
    x, y = get_batch()
    logits = model(x)                                         # 1. forward
    loss = F.cross_entropy(logits.reshape(-1, n_vocab), y.reshape(-1))  # 2. loss
    opt.zero_grad()
    loss.backward()                                           # 3. backward
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)   # cap the gradient
    opt.step()                                                # 4. update
    if step % 150 == 0:
        print(f"step {step:3}  loss {loss.item():.3f}")

# Greedy generation from the trained model
idx = torch.tensor([[stoi[c] for c in "the "]])
with torch.no_grad():
    for _ in range(40):
        next_id = model(idx[:, -T:])[0, -1].argmax()
        idx = torch.cat([idx, next_id.view(1, 1)], dim=1)
print("sample:", "".join(chars[i] for i in idx[0]))

    Where the text comes from

    Pretraining text is mostly filtered web pages, plus code, books, papers and reference works: trillions of tokens (Meta reports over 15 trillion for Llama 3). Most of the effort goes into cleaning it: keeping the wanted languages, filtering out low-quality and harmful pages, removing personal data, and removing near-duplicates, which otherwise get memorised. The mixture decides what the model is good at, and any benchmark questions that leak into it make evaluation look better than it is.

    Reading loss curves

    • Validation loss is measured on text held out from training. It estimates how well the model handles text it has not seen, which is what you actually care about.
    • Underfitting: both losses stay high. The model is too small, has trained too briefly, or the learning rate is wrong.
    • Overfitting: training loss keeps dropping while validation loss stalls or rises. The model is memorising its training text instead of learning patterns that carry over.
    • Why curves matter: they are the main instrument panel of training. A flat line, a sudden spike or a widening gap between the two curves each points to a different problem, long before you read any generated text.

    Common misconceptions

    • “Loss should reach zero.” Language is uncertain; many continuations are valid. A loss of zero would mean memorisation.
    • “The model is trained on its own outputs.” During pretraining it always sees real text (teacher forcing). It first consumes its own outputs at inference time.
    • “A larger learning rate just trains faster.” Beyond a point it destabilises training or settles on a worse result.
    • Pitfall: evaluating on data that overlaps the training set makes a model look better than it is.

    Key takeaways

    • Loss = average of -\log(probability given to the correct next token).
    • An untrained model starts near \ln n_{\text{vocab}}, the loss of uniform guessing.
    • Targets are the inputs shifted by one; all positions are trained in one parallel pass.
    • One step: \theta\leftarrow\theta-\eta\,\nabla_\theta\mathcal{L}, in practice with Adam and a warm-up schedule.
    • Training loss falling while validation loss rises is overfitting.

    The model offers “mat” 0.44, “sofa” 0.24 and a long tail. Greedy decoding always writes “mat”. Sampling writes “sofa” about one time in four. The chosen token is appended and the model runs again.

    A trained model gives a probability distribution. Turning that into text needs a rule for choosing one token, then a loop: append the chosen token to the input and ask again. This is autoregressive generation, and the choosing rule is the decoding strategy. The same model can sound cautious or wild depending on that rule alone.

    • Context window: the maximum number of tokens the model can take in. Older tokens beyond it are simply not seen.
    • Greedy decoding: always take the most probable token. Deterministic, but prone to dull, repetitive text.
    • Temperature \tau: divide the logits by \tau before softmax. Below 1 sharpens the distribution, above 1 flattens it.
    • Top-k: keep only the k most probable tokens, then renormalise.
    • Top-p (nucleus): keep the smallest set of top tokens whose probabilities add up to at least p, then renormalise. The set shrinks when the model is confident and widens when it is unsure.
    • Repetition penalty: lower the logits of tokens already present in the context, to discourage loops.
    • KV cache: when one token is appended, the keys and values of all earlier tokens are unchanged, because the causal mask stops them seeing the new token. Storing them means each step only computes the new token’s row instead of redoing the whole sequence. The output is identical; generation is simply much faster, at the cost of memory. shows this pass by pass.

    The equations, and the reasoning behind them

    Temperature. We want one dial that makes the model’s distribution sharper or flatter without retraining. Recall from that softmax depends only on the gaps between logits. So divide every logit by a number \tau before softmax:

    p_v=\frac{e^{z_v/\tau}}{\sum_{v'} e^{z_{v'}/\tau}}

    z_v is the logit of vocabulary entry v; \tau is the temperature; \tau=1 leaves the model’s distribution unchanged.

    Why does dividing work?
    Dividing by \tau multiplies every gap by 1/\tau. A small \tau stretches the gaps, so the largest logit dominates; as \tau\to0 this becomes greedy decoding. A large \tau shrinks the gaps, pushing the distribution towards uniform. The ranking of tokens never changes, only how much the ranking matters. That is the whole “determinism versus creativity” dial: low temperature repeats the model’s single best guess; high temperature gives lower-ranked guesses a real chance, which reads as more varied and, pushed too far, as incoherent.

    Top-k and top-p. Even a sensible distribution has a long tail of very unlikely tokens, and over hundreds of steps an unlucky draw from that tail becomes likely. Both filters choose a set S of tokens to keep, discard the rest, and rescale what is left so it sums to 1 again:

    p'_v=\begin{cases}\dfrac{p_v}{\sum_{u\in S}p_u}& v\in S\\[2ex]0& v\notin S\end{cases}

    For top-k, S is the k most probable tokens. For top-p, S is the smallest set of most-probable tokens whose probabilities total at least p.

    Worked example

    Logits z=[2.0,\ 1.0,\ 0.1] again.

    \tau=1: [0.6590,\ 0.2424,\ 0.0986].   \tau=0.5: [0.8638,\ 0.1169,\ 0.0193].   \tau=2: [0.5017,\ 0.3043,\ 0.1940].

    For \tau=0.5 the logits become [4,\ 2,\ 0.2]: every gap has doubled.

    Top-k and top-p on probabilities [0.5,\ 0.3,\ 0.15,\ 0.05]: top-k with k=2 keeps the first two and rescales to [0.625,\ 0.375]. Top-p with p=0.9 keeps tokens until the running total reaches 0.9: 0.5,\ 0.8,\ 0.95, so three tokens survive and rescale to [0.5263,\ 0.3158,\ 0.1579].

    With scores 2.0, 1.0 and 0.1, the top token wins 66% of the time at temperature 1, 86% at temperature 0.5 and only 50% at temperature 2. Top-k and top-p then cut off the unlikely tail so that a rare unlucky draw cannot derail the text.

    In Python: temperature, top-k, top-p and the generation loop
    Runs on its own · Python 3 + NumPy
    from collections import Counter
import numpy as np


def softmax(z):
    e = np.exp(z - z.max())
    return e / e.sum()


def next_token_probs(logits, tau=1.0, top_k=None, top_p=None):
    p = softmax(np.asarray(logits, dtype=float) / tau)    # temperature
    order = np.argsort(-p)                                # most probable first
    keep = np.ones(p.size, dtype=bool)
    if top_k is not None:
        keep[order[top_k:]] = False                       # top-k
    if top_p is not None:
        cum = np.cumsum(p[order])
        n = np.searchsorted(cum, top_p) + 1               # smallest set >= p
        keep[order[n:]] = False                           # top-p
    p = np.where(keep, p, 0.0)
    return p / p.sum()                                    # renormalise


z = [2.0, 1.0, 0.1]
for tau in (1, 0.5, 2):
    print(f"tau={tau:<3}", next_token_probs(z, tau).round(4))

probs = np.array([0.5, 0.3, 0.15, 0.05])
logits = np.log(probs)              # logits whose softmax is exactly `probs`
print("top-k=2  ", next_token_probs(logits, top_k=2).round(4))
print("top-p=0.9", next_token_probs(logits, top_p=0.9).round(4))

# The generation loop. The "model" here is a table of character counts that
# looks at the last two characters. It stands in for a trained Transformer.
text = "the cat sat on the mat. the dog sat on the sofa. a cat saw the dog. "
chars = sorted(set(text))
counts = Counter((text[i:i + 2], text[i + 2]) for i in range(len(text) - 2))
model = lambda context: np.log(                     # logits for the next char
    np.array([counts[(context[-2:], c)] for c in chars]) + 0.01)


def generate(prompt, n, rng, greedy=False, **settings):
    out = prompt
    for _ in range(n):
        p = next_token_probs(model(out), **settings)
        i = p.argmax() if greedy else rng.choice(len(p), p=p)
        out += chars[i]                                   # append, repeat
    return out


rng = np.random.default_rng(0)
print("greedy:   ", repr(generate("the ", 30, rng, greedy=True)))
print("tau=0.7:  ", repr(generate("the ", 30, rng, tau=0.7, top_p=0.9)))
print("tau=2.0:  ", repr(generate("the ", 30, rng, tau=2.0)))

    Common misconceptions

    • “Temperature 0 means the model is certain or correct.” It means the top token is always chosen, even when it had 30% probability.
    • “Higher temperature makes the model more intelligent or creative.” The model’s knowledge is unchanged. Only the dice are loaded differently.
    • “The KV cache changes the result.” It is purely a speed optimisation; outputs are identical.
    • Pitfall: text outside the context window is forgotten completely. Nothing about it remains inside the model.
    Why models make things up

    The model does not look facts up; it samples a plausible next token. When its training text held no clear answer, a fluent wrong answer can be just as probable as a right one, and it is written with the same confidence. This is called hallucination. Giving the model the facts in its context (retrieval, see ), asking it to say when it does not know, and checking its claims all reduce it; lowering the temperature does not, because the wrong answer may be the most probable one.

    Key takeaways

    • Temperature \tau divides the logits: below 1 sharpens the distribution, above 1 flattens it.
    • Greedy = always the top token: deterministic and often repetitive.
    • Top-k keeps the k most probable tokens; top-p keeps the smallest set whose probabilities total at least p.
    • These are settings applied at generation time. They do not change the model.

    Builds on Matrix multiplications from and ; parameter counts from ; the training loop from .

    A team wants to run a model with 7 billion parameters on one 24 GB graphics card. In 16-bit numbers the weights alone take 14 GB. Is there room for a 4,096-token conversation, and how many tokens per second will the card produce?

    Almost all the work in a Transformer is matrix multiplication: billions of multiply-adds that do not depend on each other. A CPU has a few dozen powerful cores built for varied, step-by-step code. A GPU has thousands of simpler cores that apply one instruction to many numbers at once, plus tensor cores that multiply a small block of a matrix in one step at reduced precision.

    A GPU has its own memory, often called VRAM. The weights, the KV cache () and the intermediate values must all fit in it. Two figures matter: capacity decides whether a model fits at all; bandwidth, the bytes per second the GPU can read from that memory, decides how fast it generates.

    What “CUDA” means

    CUDA is NVIDIA’s platform for running general-purpose programs on its GPUs. Several separately versioned pieces share the name, and most installation problems come from mixing them up:

    • Driver: part of the operating system. nvidia-smi prints its version and the newest CUDA version it supports, which is not necessarily one you have installed.
    • Toolkit and runtime: the compiler (nvcc) and libraries for building and running GPU programs. PyTorch’s pip packages bring the runtime they need, so for PyTorch you usually need only a recent enough driver.
    • Kernels and libraries: a kernel is a function that runs on the GPU across many threads at once. PyTorch calls ready-made ones from cuBLAS (matrix multiplication), cuDNN (neural-network operations) and NCCL (traffic between GPUs).
    • PyTorch’s build: each package is built for one CUDA version, shown by torch.version.cuda, or for the CPU only (None).

    Two errors catch almost everyone. torch.cuda.is_available() returning False usually means a CPU-only PyTorch or a missing driver. “CUDA driver version is insufficient for CUDA runtime version” means the driver is older than the CUDA version PyTorch was built for. Either way, install the PyTorch build that matches the driver, or update the driver. AMD’s ROCm is used through the same torch.cuda calls; Apple’s GPUs through the "mps" device.

    The equations, and the reasoning behind them

    Will the model fit? The weights take one number per parameter. The KV cache adds memory for every token of every request being served. The CUDA context, intermediate values and gaps between allocations come on top; a common rule of thumb allows another 20%:

    M_{\text{needed}}\approx1.2\times\left(N\times\text{bytes per parameter}+M_{\text{KV}}\right)\le n_{\text{GPU}}\times M_{\text{GPU}},\qquad M_{\text{KV}}=2\times L\times T\times d_{\text{model}}\times2\times B

    N is the number of parameters, with 4, 2, 1 or 0.5 bytes each; L is the number of layers, T the context length and B the number of requests served at once; the cache holds a key and a value (the first 2) at 2 bytes each (the second 2); n_{\text{GPU}} GPUs have M_{\text{GPU}} bytes each. The 1.2 is an allowance, not a measured constant.

    How fast can it generate? Each decode step reads every weight, and every cached key and value, from memory once. With few requests that reading takes longer than the arithmetic, so bandwidth sets the speed:

    \text{tokens per second per request}\lesssim\frac{n_{\text{GPU}}\times R}{N\times\text{bytes per parameter}+M_{\text{KV}}}

    R is one GPU’s memory bandwidth in bytes per second. This is an upper bound; real systems reach a fraction of it.

    Why bandwidth and not compute?
    For one request, each 16-bit weight read from memory (2 bytes) takes part in one multiply and one add (2 operations): one operation per byte. An H100 can do about 989\times10^{12} operations per second but read only 3.35\times10^{12} bytes, so it needs about 295 operations per byte to keep its tensor cores busy. Serving B requests together uses each byte B times, which is why batching raises throughput almost for free until B nears that ratio.

    And training? With the Adam optimizer in mixed precision, a common recipe keeps bf16 weights (2 bytes), bf16 gradients (2), fp32 master weights (4) and Adam’s two fp32 running averages (8), plus the activations saved for the backward pass:

    M_{\text{train}}\approx16\times N\ \text{bytes, before activations}

    Worked example

    Does it fit? The running example: N=7\times10^9 in bf16, with L=32,\ d_{\text{model}}=4096, serving one request at T=4096. Weights: 7\times10^9\times2 bytes = 14 GB. KV cache: 2\times32\times4096\times4096\times2=2{,}147{,}483{,}648 bytes, about 2.15 GB. Needed: 1.2\times(14+2.15)\approx19.4 GB, which fits in 24 GB.

    How fast? On an RTX 4090 (1,008 GB/s): 1008/16.15\approx62 tokens per second at most. On an L4 (300 GB/s), which has the same 24 GB: about 19.

    A 70B model (L=80,\ d_{\text{model}}=8192). In bf16: 1.2\times(140+10.7)\approx181 GB, so three 80 GB GPUs. In int4: 1.2\times(35+10.7)\approx55 GB, which fits on one H100 at up to 3350/45.7\approx73 tokens per second, or on one DGX Spark at up to 273/45.7\approx6.

    Training the 7B model needs 16\times7\times10^9 bytes = 112 GB before activations: more than any single GPU below.

    A 7-billion-parameter model in 16-bit numbers needs about 19 GB with a long conversation and a safety margin, so it fits on a 24 GB card. How fast it writes depends on how quickly the card reads its memory: about 62 tokens a second on a fast gaming card, about 19 on a low-power data-centre card with the same memory. Training the same model needs more than 100 GB.

    Unified memory: NVIDIA DGX Spark

    DGX Spark is a small desktop computer built around NVIDIA’s GB10 Grace Blackwell chip, whose CPU and GPU share one pool of 128 GB.     One GPU or several; local or cloud

    • Fit first. If the model fits on one GPU, use one. Otherwise it is split: tensor parallelism divides every weight matrix across GPUs that exchange results in every layer, over a fast link such as NVLink; pipeline parallelism puts consecutive layers on different GPUs. Data parallelism, a full copy per GPU, raises throughput but does not help a model that does not fit.
    • Local hardware: a one-off cost, and the data stays with you. Consumer cards top out at around 24 to 32 GB; unified-memory machines hold more, at lower bandwidth.
    • Cloud GPUs: rented by the hour, with data-centre memory and bandwidth; you pay while they sit idle.
    • Hosted APIs: no hardware at all. You pay per token and accept the provider’s models and data terms.

    You do not need a GPU to follow this guide: every interactive runs in the browser and every Python box runs on a CPU.

    Common misconceptions

    • “More TFLOPS means faster generation.” For a few users at a time, memory bandwidth sets the speed. The L4 and the RTX 4090 have the same memory, and the 4090 generates over three times faster.
    • “nvidia-smi shows the CUDA version I have installed.” It shows the newest CUDA version the driver supports.
    • “Two 24 GB cards are the same as one 48 GB card.” The model has to be split between them, and every layer then waits for data to cross between the cards.
    • Pitfall: choosing hardware by its compute figure alone. For serving, check memory first and bandwidth second.

    Key takeaways

    • Transformers are mostly matrix multiplication, which GPUs and their tensor cores run massively in parallel.
    • Memory capacity decides whether a model fits: weights (parameters × bytes) plus the KV cache plus a margin.
    • Memory bandwidth decides how fast a single request generates; compute matters only for large batches.
    • bf16 halves fp32’s memory with the same range; int8 and int4 shrink it further at some cost in quality.
    • For PyTorch, the driver must support the CUDA version your PyTorch build uses; the rest of CUDA comes with PyTorch.

Training happens once; inference happens on every request, so these numbers decide whether a model is practical to use.

    A request has two phases with very different behaviour:

    • Prefill: the whole prompt is processed in a single parallel pass, exactly as in training. Its keys and values are stored in the KV cache. The time this takes is, roughly, the time to first token (TTFT).
    • Decode: output tokens are produced one at a time. Each step processes only the newest token and reads the cache for everything earlier. This phase is sequential and cannot be parallelised across the tokens of one response.

    The vocabulary of serving

    • Latency: how long one request takes. Usually split into time to first token and the generation speed after it, in tokens per second.
    • Streaming: sending each token to the user as soon as it is produced. It does not make generation faster, but the wait people feel becomes the time to first token and not the full response time.
    • Throughput: tokens per second summed over all requests being served. This is what determines cost.
    • Batching: running several requests through the model in the same step. One pass over the weights serves all of them, so throughput rises; past a point each request slows down. Throughput and latency pull in opposite directions.
    • Memory: the weights, plus one KV cache per active request, plus working space. The cache grows with every token of context.
    • Prompt caching: keeping the KV cache of a prefix that many requests share, such as a long system prompt, so its prefill is paid once.
    • Beam search: keeping several candidate continuations alive and choosing the most probable overall. Common in translation; rare in chat models, where sampling gives more natural text.
    • FlashAttention: computes attention in tiles that fit in the GPU’s fast on-chip memory, so the full T\times T score matrix is never written out. The result is exact; it saves memory traffic, which is what makes long contexts affordable. Some long-context models also use sliding-window attention in some layers, where each token attends only to the most recent few thousand tokens.
    • A smaller cache: most current models share each key and value head between several query heads (grouped-query attention), which divides the cache by the same factor.
    • Speculative decoding: a small, fast model drafts a few tokens and the large model checks them in one parallel pass, keeping those it agrees with. Done correctly, the output distribution is unchanged and only the speed improves.

    The equations, and the reasoning behind them

    How much work does the cache save? Write P for the number of prompt tokens and n for the number of tokens to generate. To predict the first new token the model must process all P prompt positions; for the second, P+1 positions; and so on. Without a cache every pass starts from scratch, so the totals add up. With a cache, each pass after the first processes only the one position that is new:

    \text{without cache: }\sum_{j=0}^{n-1}(P+j)=nP+\frac{n(n-1)}{2}\qquad\qquad\text{with cache: }P+(n-1)

    j counts the passes from 0. The first total grows with n^2, the second with n.

    What does the cache cost? For every layer and every token it stores one key vector and one value vector. Summed over the heads, each has d_{\text{model}} numbers:

    M_{\text{KV}}=2\times L\times T\times d_{\text{model}}\times \text{bytes per number}\times B,\qquad M_{\text{weights}}=N\times\text{bytes per parameter}

    The 2 is for keys and values; L is the number of layers; T=P+n is the context length in use; B is the number of requests in the batch; N is the number of parameters.

    How long does a response take? The two phases simply add:

    t_{\text{response}}\approx t_{\text{first token}}+\frac{n}{\text{tokens per second}}
    Math detail: the rough speed model used by the estimator below

    Processing one token costs about 2N floating-point operations (one multiply and one add per parameter), so hardware delivering F operations per second can do at most F/2N tokens per second in total. There is a second limit: every decode step has to read all the weights from memory once, however many requests share that step. With a memory bandwidth of R bytes per second, that allows R/M_{\text{weights}} steps per second, or B\cdot R/M_{\text{weights}} tokens per second for a batch of B. Whichever limit is lower wins:

    \text{throughput}\approx\min\!\left(\frac{F}{2N},\ \frac{B\,R}{M_{\text{weights}}}\right),\qquad \text{speed per request}=\frac{\text{throughput}}{B},\qquad t_{\text{first token}}\approx\max\!\left(\frac{2N\,P\,B}{F},\ \frac{M_{\text{weights}}}{R}\right)

    These are order-of-magnitude bounds. They ignore attention’s extra cost at long contexts, software overhead and hardware details, all of which make real systems slower.

    Worked example

    Work saved. Prompt of P=3 tokens, generate n=5. Without a cache the passes process 3+4+5+6+7=25 token positions. With a cache: 3 in prefill, then 1 for each of the 4 later steps, 7 in all.

    Cache memory. A GPT-2-small-sized model, L=12,\ d_{\text{model}}=768, with T=1024 tokens of context at 2 bytes per number: 2\times12\times1024\times768\times2=37{,}748{,}736 bytes, about 37.7 MB, next to 248.9 MB of weights. A larger model with L=32,\ d_{\text{model}}=4096 and T=8192: 2\times32\times8192\times4096\times2=4{,}294{,}967{,}296 bytes, about 4.29 GB, for one request.

    Response time. Time to first token 0.4 s, then 50 tokens per second, for a 200-token answer: 0.4+200/50=4.4 seconds.

    Generating 5 tokens after a 3-token prompt takes 25 units of work if the model starts over each time, and 7 if it remembers its earlier work. The memory for that remembering is modest for a small model and several gigabytes per conversation for a large model with a long context.

    In Python: a KV cache gives identical outputs with less work
    Runs on its own · Python 3 + NumPy
    import numpy as np


def softmax(s):
    e = np.exp(s - s.max())
    return e / e.sum()


rng = np.random.default_rng(0)
d_model, P, n = 8, 3, 5               # prompt of 3 tokens, generate 5
W_Q, W_K, W_V = (rng.normal(size=(d_model, d_model)) for _ in range(3))
X = rng.normal(size=(P + n - 1, d_model))  # token vectors that will be processed


def attend(q, K, V):
    return softmax(K @ q / np.sqrt(d_model)) @ V


# Without a cache: every pass recomputes keys and values for all positions
no_cache, work_no_cache = [], 0
for t in range(P - 1, P + n - 1):     # one pass per generated token
    seen = X[:t + 1]
    K, V = seen @ W_K, seen @ W_V     # recomputed every time
    work_no_cache += len(seen)
    no_cache.append(attend(X[t] @ W_Q, K, V))

# With a cache: prefill the prompt once, then add one row per step
K_cache, V_cache = X[:P] @ W_K, X[:P] @ W_V
work_cache = P
with_cache = [attend(X[P - 1] @ W_Q, K_cache, V_cache)]
for t in range(P, P + n - 1):
    K_cache = np.vstack([K_cache, X[t] @ W_K])        # append the new key
    V_cache = np.vstack([V_cache, X[t] @ W_V])        # append the new value
    work_cache += 1
    with_cache.append(attend(X[t] @ W_Q, K_cache, V_cache))

print("identical outputs:", np.allclose(no_cache, with_cache))
print("positions computed without cache:", work_no_cache,
      "=", P * n + n * (n - 1) // 2)
print("positions computed with cache:   ", work_cache, "=", P + n - 1)

# Output:
# identical outputs: True

    def kv_cache_bytes(L, T, d_model, bytes_per_number=2, B=1):
    return 2 * L * T * d_model * bytes_per_number * B  # 2 = keys and values


def weight_bytes(N, bytes_per_param=2):
    return N * bytes_per_param


def response_seconds(t_first_token, n_tokens, tokens_per_second):
    return t_first_token + n_tokens / tokens_per_second


def rough_speed(N, P, B, F, R, bytes_per_param=2):
    """Order-of-magnitude bounds; real systems are slower."""
    m_weights = weight_bytes(N, bytes_per_param)
    throughput = min(F / (2 * N), B * R / m_weights)    # tokens/s, all requests
    t_first = max(2 * N * P * B / F, m_weights / R)     # seconds

    Beginner note

    This is why a model that “fits” on a device can still feel slow, and why a long conversation can run out of memory even though the model itself has not changed: the weights are fixed, but the cache grows with every token.

    Common misconceptions

    • “The KV cache saves memory.” It spends memory to save computation.
    • “Generation can be parallelised like training.” A prompt is processed in parallel, but each output token depends on the one before it, so decoding is sequential.
    • “Tokens per second is a property of the model.” It depends on hardware, precision, batch size and context length together.
    • “Streaming makes the model faster.” The total time is unchanged. Only the wait before the first visible word shrinks.
    • “Quantization only matters for fitting in memory.” Fewer bytes per weight also means fewer bytes to read on every step, which is often the real speed limit.
    • Pitfall: sizing hardware for the weights alone. Leave room for one KV cache per concurrent request at the longest context you intend to allow.

    Key takeaways

    • Because of the causal mask, earlier positions’ keys and values never change, so they can be cached.
    • Without a cache the work grows with n^2; with it, with n.
    • Cache memory = 2 × layers × tokens × d_{\text{model}} × bytes, per request.
    • Response time ≈ time to first token + output tokens ÷ tokens per second.
    • Batching raises total throughput but not the speed of a single request.

    Will it fit, and how fast will it be?

    The question: will a given model fit, and how many tokens per second can it produce? Memory follows the rule from : about 1.2 × (weights + KV cache). An Ollama download is the weights, already quantized (usually to about 4 bits), so its size is a good first estimate of the weights term.

    Speed follows the bound from : bandwidth divided by the bytes read per token. One twist matters here. In a mixture-of-experts model a router sends each token through only a few of each block’s expert MLPs. Every expert must be in memory, so memory follows the total parameter count; but each token reads only the active parameters, so in the speed bound N becomes the active count.

    Why is a mixture-of-experts model not simply a small model?

    Its 21 billion parameters store more knowledge and skills than a dense 3.6-billion-parameter model can, while each token pays the reading cost of only 3.6 billion. The price is memory: a dense model with the same speed would need about a sixth of the space.

    Does it fit? On the 24 GB card, apply the 1.2 margin to the Ollama download sizes:

    • gpt-oss:20b, 14 GB: 1.2\times14=16.8 GB. Fits, with room for a long cache.
    • qwen3.8:27b, 18 GB: 1.2\times18=21.6 GB. Fits, with a moderate context.
    • llama3.1:70b, 43 GB: 1.2\times43\approx52 GB. Does not fit; it needs more than two 24 GB cards, one 80 GB GPU, or a DGX Spark.

    Builds on Parameter counts from and the loss from .

    The toy model in this guide has under 10,000 parameters and has seen a few hundred sentences. Predicting “mat” well in general, for any prompt, is what billions of parameters and trillions of tokens buy.

    The toy model above and a frontier LLM share the same architecture. The difference is scale: parameters, data and compute, each larger by many orders of magnitude. A striking empirical finding is that performance improves smoothly and predictably as these grow together, following what are called scaling laws.

    • Model size (parameters, N): capacity to store patterns. More parameters help only if there is enough data to fill them.
    • Dataset size (tokens, D): how much text the model learns from.
    • Compute: training cost grows with both. A standard rule of thumb is about 6 floating-point operations per parameter per training token.
    • Inference cost: about 2 operations per parameter for every token generated, paid on every request for as long as the model is in service. This is why many released models are smaller than compute-optimal and trained on far more data: a smaller model is cheaper to serve.

    The equations, and the reasoning behind them

    Training compute. One forward pass costs about 2 floating-point operations per parameter per token: each weight is used in one multiplication and one addition. The backward pass costs about twice the forward pass. Together that is roughly 6 operations per parameter per token, so for N parameters and D training tokens:

    C_{\text{train}}\approx 6\,N\,D\ \ \text{FLOPs}

    Loss as a function of scale. Think of the loss as having three sources: a part no model can remove because language is uncertain, a part caused by having too few parameters, and a part caused by having seen too little data. Measured curves are close to straight lines on logarithmic axes, which is the signature of a power law, so each removable part is modelled as one:

    \mathcal{L}(N,D)\approx \mathcal{L}_{\infty}+\frac{a}{N^{r}}+\frac{b}{D^{s}}

    \mathcal{L}_\infty is the irreducible loss; a, b are constants; r, s are exponents between 0 and 1. This is the form fitted by Hoffmann et al. (2022).

    What the form tells you.
    The two fractions shrink independently. Make N enormous and the second term vanishes, but the third is untouched: you are left with \mathcal{L}_\infty+b/D^{s} however large the model. Whichever of parameters or data is scarce sets the floor, which is why the two must grow together.

    Worked example

    A model with N=10^{9} parameters trained on D=2\times10^{10} tokens needs about 6\times10^{9}\times2\times10^{10}=1.2\times10^{20} FLOPs. That is D/N=20 tokens per parameter, close to the compute-optimal ratio of about 20 found by Hoffmann et al. (2022). Llama 3 8B was trained on over 15\times10^{12} tokens: about 1,900 per parameter, far past that point, because it was built to be cheap to run.

    A 1-billion-parameter model reading 20 billion tokens costs on the order of a hundred billion billion arithmetic operations to train. That is 20 tokens per parameter, about the compute-optimal ratio. Models built to be cheap to run are trained on far more: Llama 3 8B saw about 1,900 tokens per parameter.

    Common misconceptions

    • “Bigger is always better.” Only when data and compute grow too. An oversized model on too little data wastes compute and overfits.

    The loss: cross-entropy, derived

    What we want: a model that gives real text a high probability. From , the probability of a text is a product of next-token probabilities, \prod_t p_\theta(w_t\mid w_{\lt t}).

    Make it workable. A product of thousands of numbers below 1 is astronomically small and awkward to differentiate. Taking the logarithm turns the product into a sum without changing which parameters are best.

    Turn it into something to minimize. Optimizers minimize, so flip the sign. Then divide by the number of tokens so the value does not depend on how long the text is:

    \mathcal{L}(\theta)=-\frac{1}{T}\sum_{t=1}^{T}\log p_{\theta}\!\left(w_t \mid w_{\lt t}\right)

    \theta stands for all the parameters. p_\theta(w_t\mid w_{\lt t}) is the probability the model gave to the token that really came next. \log is the natural logarithm. In words: \mathcal{L}=-\sum_t\log p(\text{target}_t\mid\text{tokens}_{\lt t}), averaged over positions.

    Why -\log?
    It is 0 when the model gave the correct token probability 1, and it grows without limit as that probability approaches 0. So a confident mistake is punished far more than a hesitant one. It also has a plain reading: the loss is the model’s average surprise at the real text. A useful reference point: guessing uniformly gives every token probability 1/n_{\text{vocab}}, hence a loss of \ln n_{\text{vocab}}. An untrained model starts near that value.

    Teacher forcing

    The targets are just the inputs shifted one place left, so a single sequence of T tokens provides T training examples. At every position the model is given the true previous tokens rather than its own guesses; this is called teacher forcing. Combined with the causal mask (), it lets all positions be trained in one parallel pass.

    targethe␣cat

    From loss to learning

    • Batching: B sequences are processed together so the update reflects an average over examples and the hardware is used efficiently.
    • Backpropagation: the chain rule, applied mechanically from the loss back through every layer, yields the gradient \nabla_\theta\mathcal{L}: for each parameter, how much the loss would rise if that parameter increased slightly.
    • Gradient descent: move every parameter a small step in the direction that lowers the loss.
    \theta\leftarrow\theta-\eta\,\nabla_{\theta}\mathcal{L}

    \eta is the learning rate, the step size.

    Why the minus sign?
    The gradient points in the direction in which the loss increases fastest, so we step the opposite way. \eta controls how far: too small and training crawls, too large and each step overshoots. It usually warms up from zero, then decays. In practice the optimizer (Adam or AdamW) replaces the raw gradient with a running average that gives each parameter a step size suited to it. One elegant fact: for softmax with this loss, the gradient with respect to each logit is simply “predicted probability minus 1 for the correct token, predicted probability for every other”. The model is pushed in proportion to how wrong it was.

    Worked example

    Loss measures surprise. A confident correct guess costs almost nothing, an unsure guess costs a little, and a confident wrong guess costs a lot. Training rolls downhill on that number in small steps.

    e = np.exp(z - z.max())
    return e / e.sum()

    In Python: a complete training loop
    Runs on its own · Python 3 + PyTorch
    import math
import torch
import torch.nn as nn
import torch.nn.functional as F

torch.manual_seed(0)

# Training text: sentences like the toy model's, read character by character
subjects = ["the cat", "the dog", "a bird", "the fox"]
verbs = ["sat on", "saw", "ran to", "likes"]
objects = ["the mat", "a box", "the tree", "the sofa"]
text = " ".join(f"{s} {v} {o}." for s in subjects for v in verbs for o in objects)
chars = sorted(set(text))
stoi = {c: i for i, c in enumerate(chars)}
data = torch.tensor([stoi[c] for c in text])
n_vocab, T, B = len(chars), 16, 32


class TinyGPT(nn.Module):
    def __init__(self, d_model=48, n_head=2, n_layer=2):
        super().__init__()
        self.tok = nn.Embedding(n_vocab, d_model)
        self.pos = nn.Embedding(T, d_model)
        layer = nn.TransformerEncoderLayer(
            d_model, n_head, 4 * d_model, dropout=0.0, activation="gelu",
            batch_first=True, norm_first=True)          # pre-norm block
        self.blocks = nn.TransformerEncoder(layer, n_layer,
                                            enable_nested_tensor=False)
        self.ln = nn.LayerNorm(d_model)
        self.head = nn.Linear(d_model, n_vocab)        # W_U

    def forward(self, idx):                            # idx: [B, T]
        t = idx.shape[1]
        x = self.tok(idx) + self.pos(torch.arange(t))
        mask = nn.Transformer.generate_square_subsequent_mask(t)
        x = self.blocks(x, mask=mask, is_causal=True)
        return self.head(self.ln(x))                   # logits: [B, T, n_vocab]


def get_batch():
    starts = torch.randint(len(data) - T - 1, (B,))
    x = torch.stack([data[s:s + T] for s in starts])
    y = torch.stack([data[s + 1:s + T + 1] for s in starts])  # shifted by one
    return x, y


model = TinyGPT()
opt = torch.optim.AdamW(model.parameters(), lr=3e-3, weight_decay=0.01)
print(f"{sum(p.numel() for p in model.parameters()):,} parameters,",
      f"uniform baseline ln {n_vocab} = {math.log(n_vocab):.3f}")

for step in range(601):
    x, y = get_batch()
    logits = model(x)                                         # 1. forward
    loss = F.cross_entropy(logits.reshape(-1, n_vocab), y.reshape(-1))  # 2. loss
    opt.zero_grad()
    loss.backward()                                           # 3. backward
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)   # cap the gradient
    opt.step()                                                # 4. update
    if step % 150 == 0:
        print(f"step {step:3}  loss {loss.item():.3f}")

# Greedy generation from the trained model
idx = torch.tensor([[stoi[c] for c in "the "]])
with torch.no_grad():
    for _ in range(40):
        next_id = model(idx[:, -T:])[0, -1].argmax()
        idx = torch.cat([idx, next_id.view(1, 1)], dim=1)
print("sample:", "".join(chars[i] for i in idx[0]))

    Where the text comes from

    Pretraining text is mostly filtered web pages, plus code, books, papers and reference works: trillions of tokens (Meta reports over 15 trillion for Llama 3). Most of the effort goes into cleaning it: keeping the wanted languages, filtering out low-quality and harmful pages, removing personal data, and removing near-duplicates, which otherwise get memorized. The mixture decides what the model is good at, and any benchmark questions that leak into it make evaluation look better than it is.

    Reading loss curves

    • Validation loss is measured on text held out from training. It estimates how well the model handles text it has not seen, which is what you actually care about.
    • Underfitting: both losses stay high. The model is too small, has trained too briefly, or the learning rate is wrong.
    • Overfitting: training loss keeps dropping while validation loss stalls or rises. The model is memorizing its training text instead of learning patterns that carry over.
    • Why curves matter: they are the main instrument panel of training. A flat line, a sudden spike or a widening gap between the two curves each points to a different problem, long before you read any generated text.

    How big, and how much data?

    The toy model on this page and a frontier LLM share the same architecture. The difference is scale: the number of parameters N, the number of training tokens D, and the compute that the two together require.

    Compute. A forward pass costs about 2 floating-point operations per parameter per token: each weight takes part in one multiplication and one addition. The backward pass costs about twice that. So training costs about 6 operations per parameter per token:

    C_{\text{train}}\approx 6\,N\,D\ \ \text{FLOPs}

    Parameters and data must grow together. A larger model can store more patterns, but only if there is enough text to fill it. Give a model ten times the parameters and the same data, and the loss soon stops falling, because the data has run out. Experiments by Hoffmann et al. (2022) found the lowest loss for a fixed training budget at about 20 training tokens per parameter.

    Serving changes the sum. Generating one token costs about 2N operations, paid on every request for as long as the model is in use. So many released models are smaller than that ratio suggests, and are trained on far more text: a smaller model is cheaper to run.

    Worked example: compute and tokens per parameter

    A 1-billion-parameter model reading 20 billion tokens costs on the order of a hundred billion billion arithmetic operations to train. That is 20 tokens per parameter, about the compute-optimal ratio. Models built to be cheap to run are trained on far more: Llama 3 8B saw about 1,900 tokens per parameter.

    Work through the exact numbers

    A model with N=10^{9} parameters trained on D=2\times10^{10} tokens needs about 6\times10^{9}\times2\times10^{10}=1.2\times10^{20} FLOPs. That is D/N=20 tokens per parameter, close to the compute-optimal ratio of about 20 found by Hoffmann et al. (2022). Llama 3 8B was trained on over 15\times10^{12} tokens: about 1,900 per parameter, far past that point, because it was built to be cheap to run.

    Common misconceptions

    • “Loss should reach zero.” Language is uncertain; many continuations are valid. A loss of zero would mean memorization.
    • “The model is trained on its own outputs.” During pretraining it always sees real text (teacher forcing). It first consumes its own outputs at inference time.
    • “A larger learning rate just trains faster.” Beyond a point it destabilizes training or settles on a worse result.
    • “Bigger is always better.” Only when data and compute grow too. An oversized model on too little data wastes compute and overfits.
    • Pitfall: evaluating on data that overlaps the training set makes a model look better than it is.

    Key takeaways

    • Loss = average of -\log(probability given to the correct next token).
    • An untrained model starts near \ln n_{\text{vocab}}, the loss of uniform guessing.
    • Targets are the inputs shifted by one; all positions are trained in one parallel pass.
    • One step: \theta\leftarrow\theta-\eta\,\nabla_\theta\mathcal{L}, in practice with Adam and a warm-up schedule.
    • Training loss falling while validation loss rises is overfitting.
    • Training compute ≈ 6ND operations; parameters and data must grow together, at about 20 tokens per parameter for the lowest training cost.

    Supervised fine-tuning and the chat template

    Supervised fine-tuning (SFT) continues training on example conversations, written or checked by people. It uses the same loss as pretraining, with two changes: the text is laid out in a fixed format, and only some of the tokens are trained.

    The format. A conversation has roles: system, user and assistant. The model, though, reads one sequence of tokens. A chat template writes the roles into that sequence with special tokens. Qwen and several other families use this style, called ChatML:

    <|im_start|>system
You are a helpful assistant.<|im_end|>
<|im_start|>user
What did the cat sit on?<|im_end|>
<|im_start|>assistant
The cat sat on the mat.<|im_end|>

    The system message sets instructions for the whole conversation. The user message is the question. The assistant message is the answer the model should learn to give.

    The question: which tokens should be trained? The model should learn to answer questions, not to write them. So the loss from is kept only at the positions inside assistant replies. The end marker counts too, so the model also learns when to stop:

    \mathcal{L}_{\text{SFT}}=-\frac{1}{|A|}\sum_{t\in A}\log p_{\theta}\!\left(w_t\mid w_{\lt t}\right)

    A is the set of positions inside assistant replies, and |A| is how many there are. Everything else is as in pretraining. The other tokens are still read as context; they just add nothing to the loss.

    Worked example

    Let words and punctuation stand in for tokens. Each message then adds five tokens around its text: a start marker, its role and a line break before it, and an end marker and a line break after it. The conversation above is 35 tokens long.

    Only 8 of them carry the loss: the 7 pieces of “The cat sat on the mat.” and the end marker after them, so |A|=8. The other 27 tokens, 77% of the sequence, are read but not trained.

    Pitfall: the wrong template

    A model behaves as trained only when it sees its own template. Raw text, or another family’s markers, quietly makes its answers worse. Ollama, vLLM and Hugging Face’s tokenizers apply the template stored with the model, so give them a list of messages and let them build the prompt.

    Base, instruct and reasoning versions

    Model cards often list several versions of one model: base (pretrained only, for further training), instruct or it (post-trained for chat), and sometimes a thinking version. For an application you almost always want the instruct or thinking version. A base model is a starting point for your own fine-tuning.

    In Python: a chat template and its loss mask
    Runs on its own · Python 3, standard library only
    import re

# A chat template turns a conversation into one token sequence (ChatML-style markers,
# as Qwen uses). Supervised fine-tuning puts the loss only on the assistant's reply.
conversation = [("system", "You are a helpful assistant."),
                ("user", "What did the cat sit on?"),
                ("assistant", "The cat sat on the mat.")]
tokens, trained = [], []
for role, text in conversation:
    words = re.findall(r"\w+|[^\w\s]", text)          # stand-in for a real tokenizer
    is_reply = role == "assistant"
    for piece, learn in ([("<|im_start|>", False), (role, False), ("\n", False)]
                         + [(w, is_reply) for w in words]
                         + [("<|im_end|>", is_reply), ("\n", False)]):
        tokens.append(piece)
        trained.append(learn)
print(f"{len(tokens)} tokens, loss on {sum(trained)}:",
      " ".join(t for t, k in zip(tokens, trained) if k))

# 35 tokens, loss on 8: The cat sat on the mat . <|im_end|>

    Builds on Supervised fine-tuning from .

    After fine-tuning, the model answers “What did the cat sit on?”. But it may say “The mat.”, or a long, flattering paragraph that ends with the mat, or now and then “The sofa.” It learned all three from its training text. Preference tuning moves its probability towards the answers people prefer.

    Fine-tuning shows the model one good answer. It is often easier to compare two answers and say which is better. Such judgements capture things that are hard to write down, like tone, helpfulness and honesty.

    Preference tuning learns from these judgements. Each example is a prompt, a preferred answer and a rejected one, judged by people or by a strong model.

    Two ways to do it: RLHF and DPO

    • RLHF (reinforcement learning from human feedback) works in two steps. It first trains a reward model that gives an answer a score. It then adjusts the language model with reinforcement learning, so that its answers earn higher scores.
    • DPO (direct preference optimization) skips the reward model and the reinforcement learning. It trains directly on the pairs, with a loss much like classification.

    The pull back to the starting model

    The question: why not just push the model towards whatever the judge scores highest? Because the judge is imperfect. Pushed hard enough, the model finds the judge’s blind spots: answers that score well without being better. A judge that likes long answers gets ever longer ones. This is reward hacking.

    So both methods add a penalty for moving too far from the starting model. The distance is measured by the KL divergence: a number that is 0 when two probability distributions are the same and grows as they differ. A strength \lambda sets the balance between earning reward and staying close.

    With that penalty, the best possible tuned model has a simple form. Take the starting probability of each answer, multiply it by a factor that grows with the answer’s reward, and rescale so the probabilities add up to 1:

    \pi^{*}(y\mid\text{prompt})=\frac{1}{Z}\,\pi_{\text{ref}}(y\mid\text{prompt})\,\exp\!\left(\frac{\text{reward}(y)}{\lambda}\right)

    y is one whole answer. \pi_{\text{ref}} is the model before preference tuning (after fine-tuning), and \pi^{*} is the tuned model. \lambda is the strength of the pull back. Z rescales the probabilities so they add up to 1. A large \lambda barely moves the model; a small one hands almost everything to the highest-scoring answer.

    Worked example

    Three answers: a short right one, a long flattering one and a wrong one, with probabilities 0.5, 0.3 and 0.2 before tuning. A careful reward model scores them 2, 1 and −2. After tuning with a moderate pull back to the original, the short right answer rises to about 0.81 and the wrong one falls to under 0.01.

    Work through the exact numbers

    Take the three answers from the story: A “The mat.”, B the long, flattering answer, and C “The sofa.”, which is wrong.

    1. Before tuning, the fine-tuned model gives them \pi_{\text{ref}}=[0.5,\ 0.3,\ 0.2].
    2. A careful reward model scores them [2,\ 1,\ -2].
    3. With \lambda=1, multiply each probability by e^{\text{reward}}: 0.5e^{2}=3.69, 0.3e^{1}=0.82 and 0.2e^{-2}=0.027.
    4. Divide by their sum, 4.54: \pi^{*}=[0.814,\ 0.180,\ 0.006]. The wrong answer almost disappears.
    5. The model has moved a KL distance of 0.284 nats from where it started. With \lambda=4 it moves less, to [0.619,\ 0.289,\ 0.091], a distance of 0.051.

    Reward model
    What is simplified: a real model chooses among countless possible answers; here three whole answers stand in for them, and the rewards are hand-picked. The tuned probabilities are the exact optimum of the objective above, which RLHF approaches by gradient steps and DPO through its loss.
    What just happened? Each answer’s probability is multiplied by e^{\text{reward}/\lambda}, and the three are rescaled to add up to 1. A large \lambda keeps the model close to where it started. A small one hands almost everything to the highest-scoring answer. With the careful judge, that is the short, right answer. With the flawed judge, a small \lambda makes the long, flattering answer win: reward hacking. The KL figure measures how far the model has moved.

    DPO’s loss. For a pair with preferred answer y_{+} and rejected answer y_{-}, DPO raises the preferred answer’s probability relative to the reference and lowers the rejected one’s:

    \mathcal{L}_{\text{DPO}}=-\log\operatorname{sigmoid}\!\left(\lambda\log\frac{\pi_{\theta}(y_{+}\mid\text{prompt})}{\pi_{\text{ref}}(y_{+}\mid\text{prompt})}-\lambda\log\frac{\pi_{\theta}(y_{-}\mid\text{prompt})}{\pi_{\text{ref}}(y_{-}\mid\text{prompt})}\right)

    \pi_{\theta} is the model being trained. Before training it equals the reference, both ratios are 1, and the loss is \log 2\approx0.693.

    Why does DPO not need a reward model?

    Rearranging the formula for \pi^{*} gives the reward in terms of the two models: \text{reward}(y)=\lambda\log\frac{\pi^{*}(y)}{\pi_{\text{ref}}(y)}+\lambda\log Z. The \log Z term cancels when two answers to the same prompt are compared. So a loss on pairs can train the model directly, with the reward model hidden inside it.

    Reasoning models and test-time compute

    A reasoning model gets one more stage of training: reinforcement learning on tasks whose answers can be checked automatically, such as maths problems or code with tests. The model makes many attempts at each task, and attempts that reach the right answer are rewarded. Over time it learns to write out intermediate steps before its final answer. These steps are often called thinking. Many problems it cannot answer directly, it solves after a few hundred or a few thousand tokens of working.

    The catch is the cost of using it. Each thinking token is one more decode step (see ), so a reasoning model answers more slowly and costs more per question. Many APIs, and open models such as gpt-oss, let you choose a low, medium or high reasoning effort.

    Spending more computation per question like this is called test-time compute. A simpler form needs no special training: sample several answers and keep the most common one. Suppose each attempt is right with probability 0.6, independently. Then a majority of 5 attempts is right with probability 0.68, and a majority of 9 with probability 0.73. Real attempts tend to make the same mistakes, so the gain is smaller in practice.

# 1. Preference tuning: the best policy for "reward minus lambda x KL from the reference"
#    reweights the reference by exp(reward / lambda).
answers = ["The mat.", "Great question! ... a soft woven mat ...", "The sofa."]
ref = [0.5, 0.3, 0.2]                                  # the SFT model's probabilities
reward = [2.0, 1.0, -2.0]                              # a careful reward model


def tune(ref, reward, lam):
    w = [p * math.exp(r / lam) for p, r in zip(ref, reward)]
    return [x / sum(w) for x in w]


for lam in (4, 1, 0.25):
    pi = tune(ref, reward, lam)
    kl = sum(p * math.log(p / q) for p, q in zip(pi, ref))
    print(f"lambda={lam:<4} probabilities {[round(p, 3) for p in pi]}  KL {kl:.3f} nats")

# 2. DPO trains on a pair (chosen, rejected). At the start the policy equals the
#    reference and the loss is log 2; at the optimum above the margin is the reward gap.
def dpo_loss(pi, ref, lam, chosen, rejected):
    margin = lam * (math.log(pi[chosen] / ref[chosen]) - math.log(pi[rejected] / ref[rejected]))
    return -math.log(1 / (1 + math.exp(-margin)))


lam = 1.0
print(f"DPO loss before tuning {dpo_loss(ref, ref, lam, 0, 2):.3f}, "
      f"at the optimum {dpo_loss(tune(ref, reward, lam), ref, lam, 0, 2):.3f}")

# 3. Test-time compute: sample several attempts and take the majority answer.

for n in (1, 5, 9):

    print(f"majority of {n} independent attempts is right with probability {p:.3f}")

    Common misconceptions

    • “RLHF makes a model truthful.” It optimizes what the judges prefer, which can include confident or flattering answers.
    • “A reasoning model’s thinking shows exactly how it reached the answer.” The written steps help it, but they are generated text, not a trace of the computation.
    • Pitfall: weakening the pull back to get the most out of a reward model. Any flaw in the judge is then exploited in full.

    Key takeaways

    • Preference tuning learns from pairs of answers: RLHF through a reward model and reinforcement learning, DPO directly from the pairs.
    • A KL penalty with strength \lambda keeps the model close to where it started.
    • With too weak a penalty, an imperfect judge is exploited: reward hacking.
    • Reasoning models write out their thinking before answering: better on hard problems, slower and costlier per answer.

    Builds on Supervised fine-tuning in , and the training step in .

    A support team wants every answer from Llama 3.1 8B as three short bullet points followed by a ticket category. A careful prompt gets the format right most of the time, not every time. The team has 2,000 good examples. Training all 8 billion weights on them would need about 128 GB of GPU memory before activations. A LoRA adapter trains 42 million numbers instead, half a percent of the model, and with the frozen weights stored in 4 bits the whole job fits on one 24 GB card.

    Fine-tuning continues training a pretrained model on your own examples, with the loss of supervised fine-tuning: the cross-entropy of the answer tokens. Full fine-tuning updates every weight, so memory must hold the weights, their gradients and the optimizer’s state. With Adam in mixed precision that is about 16 bytes per parameter, as works out, so 128 GB for an 8B model.

    LoRA (low-rank adaptation, 2021) freezes the pretrained weights and learns a small correction for some of the weight matrices. The correction is the product of two thin matrices, so it has few numbers to train. The bet behind it: adapting a model to one task needs a change in only a few directions, even though each matrix has thousands of them. On GPT-3 (175 billion parameters) the LoRA paper cut the trainable numbers by 10,000 times and the GPU memory by 3 times, with no extra time per token at inference.

    The equations, and the reasoning behind them

    What is learned? Take one weight matrix W of shape [d_in, d_out]. LoRA adds a correction made of two small matrices: A of shape [d_in, r] and B of shape [r, d_out]. Their product has the shape of W, but its rank is at most r, typically 8 to 64:

    W' = W + \frac{\alpha}{r}\,AB,\qquad xW' = xW + \frac{\alpha}{r}\,(xA)\,B

    x is the input row. W is frozen; only A and B are trained. r is the rank. \alpha is a fixed scale chosen with it, so that a change of rank does not change the size of the update. These are the names the LoRA paper and the libraries use; here B is a matrix, not the batch size. During training the product AB is never formed: the input is squeezed to r numbers by A and expanded back by B.

    Where does it start? A starts with small random numbers and B with zeros, so AB=0 and the adapted model starts exactly as the pretrained one. B gets a gradient at the first step because A is not zero, and A starts to move once B has.

    How many numbers are trained? A and B together hold

    r\,(d_{\text{in}}+d_{\text{out}})\quad\text{instead of}\quad d_{\text{in}}\times d_{\text{out}}

    For a 4,096 × 4,096 matrix at rank 16: 16 × 8,192 = 131,072 numbers instead of 16,777,216, under 1%.

    What does it cost at inference? Nothing, if you merge: W' has the shape of W, so it can be computed once and the model runs exactly as fast as before. Or keep the adapter as a separate file, a few megabytes to a few hundred, and switch adapters per task over one shared base model.

    And memory in training? The frozen weights need no gradients and no optimizer state, only storage. Each trained number needs about 16 bytes, as in full fine-tuning:

    M_{\text{LoRA}}\approx N\times\text{bytes per parameter}+16\,N_{\text{LoRA}}\ \text{bytes, before activations}

    N is the model’s parameter count and N_{\text{LoRA}} the adapter’s. With the frozen weights in bf16, that is 2 bytes per parameter. QLoRA (2023) stores them in NF4, a 4-bit format (see ), turns each block back to 16 bits only while it is used, and trains a LoRA adapter on top: about half a byte per frozen parameter. The QLoRA paper fine-tuned a 65-billion-parameter model on a single 48 GB GPU.

    When to fine-tune

    • Try a better prompt first. Instructions and a few examples in the prompt cost nothing to change.
    • Use retrieval for knowledge, especially knowledge that changes or must be cited: . Fine-tuning is an unreliable way to add facts.
    • Fine-tune for behaviour: a fixed format, a style, a narrow task done consistently, or a small model taught to match a large one on that task, which is cheaper to run.
    • Quality beats quantity. The LIMA paper fine-tuned a 65B model on only 1,000 carefully chosen examples. Hundreds to a few thousand good examples is a common start; check them by hand.

    Choosing the settings

    • Which matrices. The LoRA paper adapted the attention’s query and value matrices. The QLoRA paper found that adapters on all the linear layers of each block were needed to match full fine-tuning.
    • Rank and scale. Ranks of 8 to 64 are common; past a point a higher rank adds little. \alpha is often set to r or 2r.
    • Learning rate. Usually higher than for full fine-tuning, because only the small matrices move.
    • Preference tuning too. DPO from trains with LoRA in the same way; the frozen base model can even serve as the reference model.
    • Many adapters, one model. Servers such as vLLM can load many LoRA adapters over one copy of the base model and choose one per request.

    Common misconceptions

    • “Fine-tuning is how you teach a model your documents.” It mainly changes behaviour. For facts, put the documents in the prompt with retrieval.
    • “LoRA makes the model slower.” Merged into the weights, it costs nothing at inference.
    • “LoRA is as good as full fine-tuning.” Often close on narrow tasks. A 2024 study titled “LoRA Learns Less and Forgets Less” found it learns new domains less well than full fine-tuning, but keeps more of what the base model knew.
    • Pitfall: fine-tuning on a different chat template from the one used at inference ().

    Key takeaways

    • Full fine-tuning needs about 16 bytes per parameter for weights, gradients and Adam’s state, before activations.
    • LoRA freezes W and trains A and B, of rank r: r(d_{\text{in}}+d_{\text{out}}) numbers per matrix, often under 1% of the model.
    • B starts at zero, so training starts from the pretrained model; afterwards the update can be merged at no cost.
    • QLoRA keeps the frozen weights in 4 bits, so an 8B model fine-tunes on one 24 GB card.
    • Fine-tune for behaviour and format; use retrieval for knowledge.

    • Temperature \tau: divide the logits by \tau before softmax. Below 1 sharpens the distribution, above 1 flattens it.

    • Repetition penalty: lower the logits of tokens already present in the context, to discourage loops.
    • KV cache: when one token is appended, the keys and values of all earlier tokens are unchanged, because the causal mask stops them seeing the new token. Storing them means each step only computes the new token’s row instead of redoing the whole sequence. The output is identical; generation is simply much faster, at the cost of memory. shows this pass by pass.

    The equations, and the reasoning behind them

    Temperature. We want one dial that makes the model’s distribution sharper or flatter without retraining. Recall from that softmax depends only on the gaps between logits. So divide every logit by a number \tau before softmax:

    p_v=\frac{e^{z_v/\tau}}{\sum_{v'} e^{z_{v'}/\tau}}

    z_v is the logit of vocabulary entry v. \tau is the temperature. \tau=1 leaves the model’s distribution unchanged.

    Why does dividing work?
    Dividing by \tau multiplies every gap by 1/\tau. A small \tau stretches the gaps, so the largest logit dominates; as \tau\to0 this becomes greedy decoding. A large \tau shrinks the gaps, pushing the distribution towards uniform. The ranking of tokens never changes, only how much the ranking matters. That is the whole “determinism versus creativity” dial: low temperature repeats the model’s single best guess; high temperature gives lower-ranked guesses a real chance, which reads as more varied and, pushed too far, as incoherent.

    Top-k and top-p. Even a sensible distribution has a long tail of very unlikely tokens, and over hundreds of steps an unlucky draw from that tail becomes likely. Both filters choose a set S of tokens to keep, discard the rest, and rescale what is left so it sums to 1 again:

    p'_v=\begin{cases}\dfrac{p_v}{\sum_{u\in S}p_u}& v\in S\\[2ex]0& v\notin S\end{cases}

    For top-k, S is the k most probable tokens. For top-p, S is the smallest set of most-probable tokens whose probabilities total at least p.

    Worked example

    With scores 2.0, 1.0 and 0.1, the top token wins 66% of the time at temperature 1, 86% at temperature 0.5 and only 50% at temperature 2. Top-k and top-p then cut off the unlikely tail so that a rare unlucky draw cannot derail the text.

    In Python: temperature, top-k, top-p and the generation loop
    Runs on its own · Python 3 + NumPy
    from collections import Counter
import numpy as np


def softmax(z):
    e = np.exp(z - z.max())
    return e / e.sum()


def next_token_probs(logits, tau=1.0, top_k=None, top_p=None):
    p = softmax(np.asarray(logits, dtype=float) / tau)    # temperature
    order = np.argsort(-p)                                # most probable first
    keep = np.ones(p.size, dtype=bool)
    if top_k is not None:
        keep[order[top_k:]] = False                       # top-k
    if top_p is not None:
        cum = np.cumsum(p[order])
        n = np.searchsorted(cum, top_p) + 1               # smallest set >= p
        keep[order[n:]] = False                           # top-p
    p = np.where(keep, p, 0.0)
    return p / p.sum()                                    # renormalize


z = [2.0, 1.0, 0.1]
for tau in (1, 0.5, 2):
    print(f"tau={tau:<3}", next_token_probs(z, tau).round(4))

probs = np.array([0.5, 0.3, 0.15, 0.05])
logits = np.log(probs)              # logits whose softmax is exactly `probs`
print("top-k=2  ", next_token_probs(logits, top_k=2).round(4))
print("top-p=0.9", next_token_probs(logits, top_p=0.9).round(4))

# The generation loop. The "model" here is a table of character counts that
# looks at the last two characters. It stands in for a trained Transformer.
text = "the cat sat on the mat. the dog sat on the sofa. a cat saw the dog. "
chars = sorted(set(text))
counts = Counter((text[i:i + 2], text[i + 2]) for i in range(len(text) - 2))
model = lambda context: np.log(                     # logits for the next char
    np.array([counts[(context[-2:], c)] for c in chars]) + 0.01)


def generate(prompt, n, rng, greedy=False, **settings):
    out = prompt
    for _ in range(n):
        p = next_token_probs(model(out), **settings)
        i = p.argmax() if greedy else rng.choice(len(p), p=p)
        out += chars[i]                                   # append, repeat
    return out

    Common misconceptions

    • “Temperature 0 means the model is certain or correct.” It means the top token is always chosen, even when it had 30% probability.
    • “Higher temperature makes the model more intelligent or creative.” The model’s knowledge is unchanged. Only the dice are loaded differently.
    • “The KV cache changes the result.” It is purely a speed optimization; outputs are identical.
    • Pitfall: text outside the context window is forgotten completely. Nothing about it remains inside the model.
    Why models make things up

    The model does not look facts up; it samples a plausible next token. When its training text held no clear answer, a fluent wrong answer can be just as probable as a right one, and it is written with the same confidence. This is called hallucination. Giving the model the facts in its context (retrieval, see ), asking it to say when it does not know, and checking its claims all reduce it; lowering the temperature does not, because the wrong answer may be the most probable one.

    Key takeaways

    • Temperature \tau divides the logits: below 1 sharpens the distribution, above 1 flattens it.
    • Greedy = always the top token: deterministic and often repetitive.
    • Top-k keeps the k most probable tokens; top-p keeps the smallest set whose probabilities total at least p.
    • These are settings applied at generation time. They do not change the model.

    covered what a model generates. This section covers what it costs to run one: how long a response takes, how much memory it needs, and why serving many users at once changes both. Training happens once; inference happens on every request, so these numbers decide whether a model is practical to use.

    A request has two phases with very different behaviour:

    • Prefill: the whole prompt is processed in a single parallel pass, exactly as in training. Its keys and values are stored in the KV cache. The time this takes is, roughly, the time to first token (TTFT).
    • Decode: output tokens are produced one at a time. Each step processes only the newest token and reads the cache for everything earlier. This phase is sequential and cannot be parallelized across the tokens of one response.

    The vocabulary of serving

    Four terms come up in every conversation about serving a model:

    • Latency: how long one request takes. Usually split into time to first token and the generation speed after it, in tokens per second.
    • Streaming: sending each token to the user as soon as it is produced. It does not make generation faster, but the wait people feel becomes the time to first token and not the full response time.
    • Throughput: tokens per second summed over all requests being served. This is what determines cost.
    • Batching: running several requests through the model in the same step. One pass over the weights serves all of them, so throughput rises; past a point each request slows down. Throughput and latency pull in opposite directions.

    The equations, and the reasoning behind them

    How much work does the cache save? Write P for the number of prompt tokens and n for the number of tokens to generate. To predict the first new token the model must process all P prompt positions; for the second, P+1 positions; and so on. Without a cache every pass starts from scratch, so the totals add up. With a cache, each pass after the first processes only the one position that is new:

    \text{without cache: }\sum_{j=0}^{n-1}(P+j)=nP+\frac{n(n-1)}{2}\qquad\qquad\text{with cache: }P+(n-1)

    j counts the passes from 0. The first total grows with n^2, the second with n.

    What does the cache cost? For every layer and every token it stores one key vector and one value vector. Summed over the heads, each has d_{\text{model}} numbers:

    M_{\text{KV}}=2\times L\times T\times d_{\text{model}}\times \text{bytes per number}\times B,\qquad M_{\text{weights}}=N\times\text{bytes per parameter}

    The 2 is for keys and values. L is the number of layers. T=P+n is the context length in use. B is the number of requests in the batch. N is the number of parameters.

    How long does a response take? The two phases simply add:

    t_{\text{response}}\approx t_{\text{first token}}+\frac{n}{\text{tokens per second}}

    Worked example

    Generating 5 tokens after a 3-token prompt takes 25 units of work if the model starts over each time, and 7 if it remembers its earlier work. The memory for that remembering is modest for a small model and several gigabytes per conversation for a large model with a long context.

    Runs on its own · Python 3 + NumPy
    import numpy as np


def softmax(s):
    e = np.exp(s - s.max())
    return e / e.sum()


rng = np.random.default_rng(0)
d_model, P, n = 8, 3, 5               # prompt of 3 tokens, generate 5
W_Q, W_K, W_V = (rng.normal(size=(d_model, d_model)) for _ in range(3))
X = rng.normal(size=(P + n - 1, d_model))  # token vectors that will be processed


def attend(q, K, V):
    return softmax(K @ q / np.sqrt(d_model)) @ V


# Without a cache: every pass recomputes keys and values for all positions
no_cache, work_no_cache = [], 0
for t in range(P - 1, P + n - 1):     # one pass per generated token
    seen = X[:t + 1]
    K, V = seen @ W_K, seen @ W_V     # recomputed every time
    work_no_cache += len(seen)
    no_cache.append(attend(X[t] @ W_Q, K, V))

# With a cache: prefill the prompt once, then add one row per step
K_cache, V_cache = X[:P] @ W_K, X[:P] @ W_V
work_cache = P
with_cache = [attend(X[P - 1] @ W_Q, K_cache, V_cache)]
for t in range(P, P + n - 1):
    K_cache = np.vstack([K_cache, X[t] @ W_K])        # append the new key
    V_cache = np.vstack([V_cache, X[t] @ W_V])        # append the new value
    work_cache += 1
    with_cache.append(attend(X[t] @ W_Q, K_cache, V_cache))

print("identical outputs:", np.allclose(no_cache, with_cache))
print("positions computed without cache:", work_no_cache,
      "=", P * n + n * (n - 1) // 2)
print("positions computed with cache:   ", work_cache, "=", P + n - 1)

    def kv_cache_bytes(L, T, d_model, bytes_per_number=2, B=1):
    return 2 * L * T * d_model * bytes_per_number * B  # 2 = keys and values


def weight_bytes(N, bytes_per_param=2):
    return N * bytes_per_param


def response_seconds(t_first_token, n_tokens, tokens_per_second):
    return t_first_token + n_tokens / tokens_per_second


def rough_speed(N, P, B, F, R, bytes_per_param=2):
    """Order-of-magnitude bounds; real systems are slower."""
    m_weights = weight_bytes(N, bytes_per_param)
    throughput = min(F / (2 * N), B * R / m_weights)    # tokens/s, all requests
    t_first = max(2 * N * P * B / F, m_weights / R)     # seconds
    return throughput, throughput / B, t_first

    Other techniques you will hear about

    • Prompt caching: keeping the KV cache of a prefix that many requests share, such as a long system prompt, so its prefill is paid once.
    • Beam search: keeping several candidate continuations alive and choosing the most probable overall. Common in translation; rare in chat models, where sampling gives more natural text.
    • FlashAttention: computes attention in tiles that fit in the GPU’s fast on-chip memory, so the full T\times T score matrix is never written out. The result is exact; it saves memory traffic, which is what makes long contexts affordable (). Some long-context models also use sliding-window attention in some layers, where each token attends only to the most recent few thousand tokens.
    • A smaller cache: most current models share each key and value head between several query heads (grouped-query attention, see ), which divides the cache by the same factor.
    • Speculative decoding: a small, fast model drafts a few tokens and the large model checks them in one parallel pass, keeping those it agrees with. Done correctly, the output distribution is unchanged and only the speed improves.

    Common misconceptions

    • “The KV cache saves memory.” It spends memory to save computation.
    • “Generation can be parallelized like training.” A prompt is processed in parallel, but each output token depends on the one before it, so decoding is sequential.
    • “Tokens per second is a property of the model.” It depends on hardware, precision, batch size and context length together.
    • “Streaming makes the model faster.” The total time is unchanged. Only the wait before the first visible word shrinks.
    • “Quantization only matters for fitting in memory.” Fewer bytes per weight also means fewer bytes to read on every step, which is often the real speed limit.
    • Pitfall: sizing hardware for the weights alone. Leave room for one KV cache per concurrent request at the longest context you intend to allow.

    Key takeaways

    • Because of the causal mask, earlier positions’ keys and values never change, so they can be cached.
    • Without a cache the work grows with n^2; with it, with n.
    • Cache memory = 2 × layers × tokens × d_{\text{model}} × bytes, per request.
    • Response time ≈ time to first token + output tokens ÷ tokens per second.
    • Batching raises total throughput but not the speed of a single request.

    Almost all the work in a Transformer is matrix multiplication: billions of multiply-adds that do not depend on each other. A CPU has a few dozen powerful cores built for varied, step-by-step code. A GPU has thousands of simpler cores that apply one instruction to many numbers at once, plus tensor cores that multiply a small block of a matrix in one step at reduced precision.

    A GPU has its own memory, often called VRAM. The weights, the KV cache () and the intermediate values must all fit in it. Two figures matter: capacity decides whether a model fits at all; bandwidth, the bytes per second the GPU can read from that memory, decides how fast it generates.

    The equations, and the reasoning behind them

    Will the model fit? The weights take one number per parameter. The KV cache adds memory for every token of every request being served. The CUDA context, intermediate values and gaps between allocations come on top; a common rule of thumb allows another 20%:

    M_{\text{needed}}\approx1.2\times\left(N\times\text{bytes per parameter}+M_{\text{KV}}\right)\le n_{\text{GPU}}\times M_{\text{GPU}}

    N is the number of parameters, at 4, 2, 1 or 0.5 bytes each. M_{\text{KV}} is the KV cache from : 2\times L\times T\times d_{\text{model}}\times2\times B bytes at 16 bits. n_{\text{GPU}} GPUs have M_{\text{GPU}} bytes each. The 1.2 is an allowance, not a measured constant.

    How fast can it generate? Each decode step reads every weight, and every cached key and value, from memory once. With few requests that reading takes longer than the arithmetic, so bandwidth sets the speed:

    \text{tokens per second per request}\lesssim\frac{n_{\text{GPU}}\times R}{N\times\text{bytes per parameter}+M_{\text{KV}}}

    R is one GPU’s memory bandwidth in bytes per second. This is an upper bound; real systems reach a fraction of it.

    Why bandwidth and not compute?
    For one request, each 16-bit weight read from memory (2 bytes) takes part in one multiply and one add (2 operations): one operation per byte. An H100 can do about 989\times10^{12} operations per second but read only 3.35\times10^{12} bytes, so it needs about 295 operations per byte to keep its tensor cores busy. Serving B requests together uses each byte B times, which is why batching raises throughput almost for free until B nears that ratio.

    And training? With the Adam optimizer in mixed precision, a common recipe keeps bf16 weights (2 bytes), bf16 gradients (2), fp32 master weights (4) and Adam’s two fp32 running averages (8), plus the activations saved for the backward pass:

    M_{\text{train}}\approx16\times N\ \text{bytes, before activations}

How fast it writes depends on how quickly the card reads its memory: about 62 tokens a second on a fast gaming card, about 19 on a low-power data-centre card with the same memory. Training the same model needs more than 100 GB.

GPUS = {
    "RTX 4090": (24e9, 1008e9, 165.2e12),
    "L4": (24e9, 300e9, 121e12),
    "A100 80GB": (80e9, 2039e9, 312e12),
    "H100 SXM": (80e9, 3350e9, 989.5e12),
    "DGX Spark": (128e9, 273e9, None),     # unified memory; no BF16 figure published

BYTES = {"fp32": 4, "bf16": 2, "int8": 1, "int4": 0.5}


def memory_needed(N, fmt, L, d_model, T, B=1, allowance=1.2):
    weights = N * BYTES[fmt]
    kv = 2 * L * T * d_model * 2 * B       # keys and values, 16-bit, full width
    return weights, kv, allowance * (weights + kv)


def report(name, N, fmt, L, d_model, T):
    w, kv, total = memory_needed(N, fmt, L, d_model, T)
    print(f"{name} in {fmt}, T={T}: weights {w / 1e9:.1f} GB + KV cache "
          f"{kv / 1e9:.2f} GB, x1.2 -> {total / 1e9:.1f} GB")
    for gpu, (mem, bw, _) in GPUS.items():
        n = math.ceil(total / mem)           # GPUs needed, split evenly
        speed = n * bw / (w + kv)            # every step reads weights and cache
        print(f"   {gpu:9} x{n}: at most {speed:4.0f} tokens/s for one request")

    Serving many requests at once

    Batching () lets one read of the weights serve several requests. That raises total throughput until compute, not bandwidth, becomes the limit, as the chart in the interactive above shows.

    Math detail: throughput, speed per request and time to first token

    Processing one token costs about 2N floating-point operations (one multiply and one add per parameter), so hardware delivering F operations per second can do at most F/2N tokens per second in total. There is a second limit: every decode step has to read all the weights from memory once, however many requests share that step. With a memory bandwidth of R bytes per second, that allows R/M_{\text{weights}} steps per second, or B\cdot R/M_{\text{weights}} tokens per second for a batch of B. Whichever limit is lower wins:

    \text{throughput}\approx\min\!\left(\frac{F}{2N},\ \frac{B\,R}{M_{\text{weights}}}\right),\qquad \text{speed per request}=\frac{\text{throughput}}{B},\qquad t_{\text{first token}}\approx\max\!\left(\frac{2N\,P\,B}{F},\ \frac{M_{\text{weights}}}{R}\right)

    These are order-of-magnitude bounds. They ignore attention’s extra cost at long contexts, software overhead and hardware details, all of which make real systems slower.

    Continuous batching

    Static batching starts a group of requests together and keeps the group until the longest one finishes. A request that stopped after ten tokens holds its place while another writes two hundred, and new requests wait for the whole group. Continuous batching (iteration-level scheduling, from the Orca paper of 2022) lets the scheduler act after every decode step: finished requests leave at once and waiting ones take their places. New prompts are prefilled alongside the running requests, often in chunks so that one long prompt does not stall everyone (“chunked prefill”).

    Worked example: four places, four requests

    Four requests that want 10, 200, 30 and 50 tokens run together. Static batching runs 200 steps with four places: 800 place-steps, of which 290 produce a token, so 36% of the batch does useful work. Continuous batching refills the three short requests’ places from the queue as soon as they finish, so while requests are waiting, every place produces a token at every step.

    Paged KV memory

    Each request’s keys and values grow by one token per step, and nobody knows in advance how long a reply will be. Earlier servers reserved one contiguous piece of memory per request, big enough for the longest possible reply. Most of it stayed empty, and the gaps between pieces could not be used. Measured in the vLLM paper, only 20.4% to 38.2% of the KV memory in those systems held real keys and values.

    PagedAttention (vLLM, 2023) borrows the paging of an operating system’s virtual memory. The cache is cut into blocks of 16 tokens, a request gets a new block only when its last one is full, and a per-request block table records where its blocks are. The attention kernel reads the blocks wherever they are. At most one block per request is partly empty, and in the paper 96.3% of the memory held real keys and values. More requests fit, so the batch is larger: 2 to 4 times the throughput of the earlier systems at the same latency. Blocks can also be shared, for example by several samples of one prompt.

    How much does one token take? With grouped-query attention, only the KV heads are stored:

    \text{bytes per token}=2\times L\times n_{\text{kv}}\times d_k\times\text{bytes per number}

    L is the number of layers, n_{\text{kv}} the number of key–value heads and d_k the width of each. The 2 counts keys and values. Llama 3.1 8B in 16 bits: 2 \times 32 \times 8 \times 128 \times 2 = 131{,}072 bytes per token.

    Worked example: reserve or page?

    A Llama 3.1 8B request has 500 tokens so far, and may grow to 8,192. Reserving the maximum takes 1.07 GB, of which 6% is used. Paging takes 32 blocks of 16 tokens, 67 MB, with 12 token places unused.

    Work through the exact numbers

    Reserved: 8{,}192 \times 131{,}072 = 1{,}073{,}741{,}824 bytes, 1.07 GB. Used: 500 \times 131{,}072 = 65{,}536{,}000 bytes, 65.5 MB, which is 6.1%. Paged: \lceil 500/16 \rceil = 32 blocks, 32 \times 16 = 512 token places, 512 \times 131{,}072 = 67{,}108{,}864 bytes, 67.1 MB. On an 80 GB H100, about 60 GB is left after the 16 GB of weights and a margin: room for 55 reservations, or about 890 paged requests of this length.

    Speculative decoding

    With few requests running, a decode step is limited by reading the weights, not by arithmetic (). Scoring five tokens in one pass therefore costs about the same as scoring one, just as prefill scores a whole prompt at once. Speculative decoding (2022) exploits this. A small, fast draft model guesses the next few tokens. The big model then scores all of them in one pass, keeps the guesses it agrees with, and writes one token of its own: the correction at the first guess it rejects, or one more token if it accepts all of them. Each pass of the big model now yields one token or more.

    How many tokens per pass? Say each guess is accepted with probability a, independently, and the draft proposes n_{\text{draft}} tokens. The j-th guess counts only if all the guesses before it were accepted, and the big model always adds one token:

    \text{tokens per pass}=1+a+a^2+\dots+a^{\,n_{\text{draft}}}=\frac{1-a^{\,n_{\text{draft}}+1}}{1-a}

    And the speed-up? A pass costs one big-model step plus the draft’s steps:

    \text{speed-up}=\frac{1-a^{\,n_{\text{draft}}+1}}{(1-a)\,(1+n_{\text{draft}}\,c_{\text{draft}})}

    a is the acceptance rate, n_{\text{draft}} the number of tokens drafted per pass, and c_{\text{draft}} the cost of one draft step as a fraction of one big-model step. The formula assumes every guess has the same chance of acceptance; real text has easy and hard stretches.

    Why is the output exactly the big model’s?

    Let p be the big model’s probabilities for the next token and q the draft’s. The draft samples a token x from q; it is accepted with probability \min(1, p(x)/q(x)). On a rejection, the big model samples from the leftover \max(0, p - q), rescaled to sum to 1. A token then comes out with probability \min(p, q) through acceptance plus \max(0, p - q) through the leftover, which is exactly p. With greedy decoding the rule becomes “accept if it is the big model’s top token”, and the text is identical. The 2022 paper reported 2 to 3 times faster T5-XXL with identical outputs.

    Worked example: four tokens drafted

    The draft model guesses right 80% of the time and proposes 4 tokens per pass, each draft step costing 5% of a big-model step. Each pass yields 3.36 tokens on average instead of 1 and costs 1.2 big-model steps, so text appears 2.8 times as fast.

    Work through the exact numbers

    Tokens per pass: 1 + 0.8 + 0.64 + 0.512 + 0.4096 = 3.3616, which matches (1 - 0.8^5)/(1 - 0.8) = 0.67232/0.2. Cost per pass: 1 + 4 \times 0.05 = 1.2 big-model steps. Speed-up: 3.3616 / 1.2 = 2.80. With 8 tokens drafted instead: (1 - 0.8^9)/0.2 = 4.33 tokens for 1.4 steps, 3.09 times; with 2 tokens drafted: 2.44 / 1.1 = 2.22 times.

    In Python: the acceptance rule keeps the big model’s distribution
    Runs on its own · Python 3 + NumPy
    import numpy as np

rng = np.random.default_rng(0)
vocab = ["mat", "rug", "chair", "bed", "floor"]
p = np.array([0.60, 0.20, 0.10, 0.06, 0.04])   # the big model's next-token probabilities
q = np.array([0.40, 0.35, 0.05, 0.15, 0.05])   # the draft model's
leftover = np.maximum(p - q, 0) / np.maximum(p - q, 0).sum()


def speculate(n_samples):
    """The draft samples from q; keep its token with probability min(1, p/q), else sample from the leftover of p."""
    x = rng.choice(len(q), size=n_samples, p=q)
    accepted = rng.random(n_samples) < np.minimum(1, p[x] / q[x])
    return np.where(accepted, x, rng.choice(len(p), size=n_samples, p=leftover)), accepted


# 1. The tokens that come out follow p, the big model, not q
out, accepted = speculate(1_000_000)
for i, word in enumerate(vocab):
    print(f"{word:6} big model {p[i]:.2f}  draft {q[i]:.2f}  speculative output {np.mean(out == i):.3f}")

    Where do drafts come from? A small model of the same family that shares the tokenizer; extra prediction heads trained on the big model itself (Medusa, EAGLE); or text copied from the prompt, which works well when a reply repeats much of its input, such as an edited document. Speculative decoding helps most with few requests at once. In a large batch the GPU is already busy with arithmetic, and checking guesses that get rejected costs real time.

    Prefix caching

    A token’s keys and values depend only on the tokens before it. Two requests that begin with the same tokens, such as the same system prompt, the same examples, the same document or the earlier turns of a chat, therefore have identical keys and values for that beginning. Prefix caching keeps those blocks and reuses them, so prefill runs only on the new part. vLLM does it automatically by matching blocks of tokens; API providers offer it as prompt caching, with cached input tokens billed at a discount. A 2,000-token system prompt followed by a 100-token question needs prefill for 100 tokens instead of 2,100.

    Beyond one GPU

    • Tensor parallelism splits each weight matrix across the GPUs of one server; they exchange partial results in every layer, so they need fast links such as NVLink.
    • Pipeline parallelism gives each GPU a run of layers, passing activations from one to the next.
    • Separate prefill and decode: prefill is compute-bound and decode bandwidth-bound, so some large deployments run them on different GPUs and move the KV cache between them.

    Common misconceptions

    • “Speculative decoding changes the answers.” With the acceptance rule above, the output follows the big model’s distribution exactly.
    • “Bigger batches are always better.” Throughput rises but each user’s text streams more slowly. Services set latency targets and cap the batch to meet them.
    • “Any shared text is cached.” Only an identical beginning is reused. One changed token early in the prompt changes the keys and values of every token after it.
    • Pitfall: putting the date, a request ID or the user’s name at the start of the system prompt, which defeats prefix caching. Put the fixed part first and the changing part last.

    Key takeaways

    • Servers are judged by time to first token, time per output token and throughput; larger batches raise throughput and slow each request.
    • Continuous batching swaps requests in and out after every step, so no place in the batch waits for the longest request.
    • Paged KV memory hands out blocks of 16 tokens as needed, so almost no memory is wasted and more requests fit.
    • Speculative decoding yields (1-a^{\,n_{\text{draft}}+1})/(1-a) tokens per big-model pass, with the big model’s output unchanged.
    • Prefix caching reuses the keys and values of an identical beginning; put the fixed part of the prompt first.

    The equations, and the reasoning behind them

    What can 4 bits hold? Sixteen values. Symmetric quantization uses the integers −7 to 7 (8 bits: −127 to 127), so zero stays exactly zero and positive and negative weights are treated alike. Call the largest integer q_{\max}: 7 for 4 bits, 127 for 8.

    Which real numbers do they stand for? Choose a step size, the scale, so that the largest weight in the group lands exactly on q_{\max}. Then every weight in the group fits:

    \Delta=\frac{\max|w|}{q_{\max}},\qquad q=\operatorname{round}\!\left(\frac{w}{\Delta}\right),\qquad \hat w=q\,\Delta

    w is one weight and \max|w| the largest weight in its group, ignoring sign. \Delta is the scale, stored once per group. q is the integer that is stored. \hat w is the weight the model computes with.

    How wrong can a weight be? Rounding moves a number by at most half a step:

    |w-\hat w|\le\frac{\Delta}{2}

    So the error depends on the step, and the step depends on the largest weight in the group. That is the weak point: one unusually large weight makes the step large for every weight that shares its scale.

    What do the scales cost? Each group stores one 16-bit scale, so the real size per weight is a little over the nominal bits:

    \text{bits per weight}=\text{bits}+\frac{16}{\text{group size}}

    With groups of 32, 4-bit weights cost 4+16/32=4.5 bits each.

    Worked example: four weights to 4 bits

    Four weights, the largest 0.50, share a step of 0.50 ÷ 7 ≈ 0.071. Each is rounded to the nearest step: 0.12 becomes 0.143 and 0.33 becomes 0.357, errors of about 0.02. If one weight were 3.0 instead, the step would be 0.43, and 0.12 would round to 0. One large weight spoils its whole group.

    Work through the exact numbers

    Weights [0.12,\;-0.50,\;0.33,\;0.02]. The largest is 0.50, so \Delta=0.50/7=0.0714.

    Divide: [1.68,\;-7.00,\;4.62,\;0.28]. Round: q=[2,\;-7,\;5,\;0]. Multiply back: \hat w=[0.143,\;-0.500,\;0.357,\;0]. Errors: [0.023,\;0,\;0.027,\;0.020], all within \Delta/2=0.036.

    Now replace the last weight with an outlier, 3.0. The scale becomes 3.0/7=0.429, and the others round to q=[0,\;-1,\;1]: 0.12 becomes 0, and 0.33 becomes 0.429. One weight has wrecked three.

def quantize(w, bits, group):
    """Symmetric round-to-nearest: one scale per `group` consecutive weights in each column."""
    q_max = 2 ** (bits - 1) - 1                       # 127 for 8 bits, 7 for 4 bits
    g = w.T.reshape(w.shape[1], -1, group)            # [columns, groups, group]
    scale = np.abs(g).max(axis=-1, keepdims=True) / q_max
    q = np.clip(np.round(g / scale), -q_max, q_max)   # the small integers that are stored
    return (q * scale).reshape(w.shape[1], -1).T      # dequantized weights


def rel(a, b):
    return np.sqrt(((a - b) ** 2).mean() / (b ** 2).mean())

    What it saves

    • Memory. Llama 3.1 8B has 8.03 billion parameters: 16.1 GB in bf16, about 8.5 GB at 8 bits and about 4.5 GB at 4 bits, counting a 16-bit scale per 32 weights. Its Ollama download is 4.9 GB, because a few tensors keep more bits.
    • Speed. Generating one token reads every weight (), so reading a quarter of the bytes raises the bandwidth limit up to four times. Real gains are smaller, because the integers must be unpacked and multiplied by their scales on the fly.
    • What it costs. At 8 bits the loss is usually too small to measure. At 4 bits it is small but real, and larger for small models. Below 4 bits, quality falls quickly. Always check on your own task.

    What gets quantized

    • Weights: the common case, called weight-only quantization. Activations stay in 16 bits; each weight is turned back into a 16-bit number just before it is used.
    • The KV cache: often stored at 8 bits, which halves the memory that grows with every token ().
    • Activations: the hardest, because they contain large outliers. With weights and activations both at 8 bits, the multiplication itself runs on 8-bit tensor cores, which is what fp8 on H100-class GPUs provides.

    Methods and formats you will meet

    • Round-to-nearest: what the interactive does. Good enough at 8 bits.
    • GPTQ: quantizes a layer a column at a time, and adjusts the weights not yet quantized to cancel the error so far, using a small set of example inputs, the calibration data (128 text samples of 2,048 tokens in the paper).
    • AWQ (activation-aware): finds the weights that meet the largest activations and scales them up before rounding, so the weights that matter most lose least.
    • GGUF files for llama.cpp and Ollama, with names like Q4_K_M: about 4 bits, “K” for a scheme with scales inside scales, and “M” for a medium mix in which some tensors keep more bits.
    • NF4: the 4-bit format of QLoRA. Its 16 levels are not evenly spaced; they follow the bell shape of typical weights, so more levels sit near zero.
    • Quantization-aware training: simulating the rounding during training or fine-tuning, so the model learns weights that survive it. Better quality at low bits, at the cost of training.

    Common misconceptions

    • “A 4-bit model is a quarter as good.” Bits measure storage, not quality. A large model at 4 bits usually loses little.
    • “Quantizing a model means retraining it.” Post-training quantization needs no training, at most a small set of example inputs.
    • “All 4-bit versions of a model are the same.” The group size, the method and which tensors keep more bits all differ, and so does quality.
    • Pitfall: comparing two models, or two providers, without checking that both run at the same precision.

    Key takeaways

    • A quantized weight is a small integer times a shared scale; the scale is the group’s largest weight divided by the largest integer.
    • Rounding error is at most half a step, so large weights, which enlarge the step, hurt everything in their group.
    • Scales per group of 32 to 128 weights limit that damage, for a fraction of a bit per weight.
    • 4-bit weights take about a quarter of bf16’s memory and speed up memory-bound decoding; 8 bits is nearly lossless, below 4 bits quality falls fast.

    Builds on and the memory and bandwidth ideas in .

    For “the cat sat on the”, the attention scores of one head form a 5 × 5 grid: 25 numbers. For a 32,768-token document they form a grid of over a billion numbers, per head, per layer. Writing that grid to memory and reading it back takes longer than computing it.

    Attention, as written in , computes every score, turns each row into probabilities, then mixes the values. Done in that order, the full T\times T grid of scores has to be stored in between. FlashAttention (Dao and others, 2022) computes exactly the same result without ever storing the grid. It is now the standard way attention is computed on GPUs.

    Two kinds of GPU memory

    • Main memory (HBM, the “GPU memory” on the box): tens of gigabytes, read at a few terabytes per second. The weights, the KV cache and anything stored between steps live here.
    • On-chip memory (SRAM): a few hundred kilobytes next to each group of cores, tens of megabytes in all, and roughly ten times faster. Arithmetic can only work on data brought in here.

    The FlashAttention paper gives the A100 as an example: about 40 GB of main memory at 1.5 TB/s, against 20 MB of on-chip memory at about 19 TB/s.

    The equations, and the reasoning behind them

    Why not just cut the grid into tiles? Scores are easy to compute a tile at a time: each one needs only a query and a key. The softmax is the problem. Every probability is divided by the sum over the whole row, and that sum is not known until the last tile of the row has been seen.

    The fix: keep running totals. For each query, keep three numbers while the tiles of keys go past: the largest score so far, the sum of the exponentials of the scores measured from that largest score, and the matching weighted sum of the values. When a tile brings a larger score, the totals so far are rescaled to the new largest score. After the last tile, one division gives the exact result:

    \begin{aligned}m_i' &= \max\!\big(m_i,\ \max_{j\in\text{tile}} s_{ij}\big)\\ r_i' &= r_i\,e^{m_i-m_i'}+\textstyle\sum_{j\in\text{tile}}e^{s_{ij}-m_i'}\\ o_i' &= o_i\,e^{m_i-m_i'}+\textstyle\sum_{j\in\text{tile}}e^{s_{ij}-m_i'}\,v_j\end{aligned}\qquad\text{and at the end}\qquad c_i=\frac{o_i}{r_i}

    s_{ij} is the score of query i against key j, v_j the value of key j, and c_i the output, all as in . m_i is the largest score seen so far, r_i the running sum of exponentials and o_i the running weighted sum of values; a prime marks the value after the tile. They start at -\infty, 0 and 0.

    Why subtract the largest score at all?
    Softmax gives the same result whatever constant is subtracted from every score, and subtracting the largest keeps every exponential at most 1, so nothing overflows (the same trick as in ’s Python box). The factor e^{m_i-m_i'} converts totals measured from the old largest score into totals measured from the new one.

    Worked example: a softmax in two tiles

    Scores 1, 2, 3 and 0 for values 10, 20, 30 and 40, taken two at a time. After the first pair the running total is measured from the largest score so far, 2. The second pair brings a 3, so the old total is scaled down by e^{-1} before the new terms are added. The final answer, 26.21, is exactly what the ordinary softmax gives.

    Work through the exact numbers

    One query, four keys with scores [1,\;2,\;3,\;0] and one-number values [10,\;20,\;30,\;40], in tiles of two.

    Tile 1, scores 1 and 2: m=2, r=e^{-1}+e^{0}=1.3679, o=10e^{-1}+20=23.679.

    Tile 2, scores 3 and 0: the largest score rises to 3, so the old totals are multiplied by e^{2-3}=0.3679. Then r=1.3679\times0.3679+e^{0}+e^{-3}=1.5530 and o=23.679\times0.3679+30+40e^{-3}=40.702.

    Result: c=40.702/1.5530=26.21. The ordinary softmax gives weights [0.087,\;0.237,\;0.644,\;0.032] and the same 26.21.

    What just happened? In plain attention the whole grid of scores was written to main memory, then the grid of probabilities, and both were read back. In the tiled version each tile of scores was computed in fast memory, folded into the running totals and thrown away, so nothing of size T\times T was ever stored, and tiles entirely above the diagonal were skipped. Each time a tile raised the largest score, the earlier totals were rescaled.     Runs on its own · Python 3 + NumPy
    import numpy as np

rng = np.random.default_rng(0)
T, d_k, tile = 1024, 64, 128
Q, K, V = (rng.normal(size=(T, d_k)) for _ in range(3))


def plain_attention(Q, K, V):
    S = Q @ K.T / np.sqrt(d_k)                        # the full T x T grid of scores
    S[np.triu_indices(T, 1)] = -np.inf                # causal mask
    P = np.exp(S - S.max(axis=1, keepdims=True))
    return (P / P.sum(axis=1, keepdims=True)) @ V, S.size


def tiled_attention(Q, K, V):
    out, largest = np.zeros_like(Q), 0
    for q0 in range(0, T, tile):                      # one tile of queries at a time
        q = Q[q0:q0 + tile]
        m = np.full(len(q), -np.inf)                  # running largest score
        r = np.zeros(len(q))                          # running sum of exponentials
        o = np.zeros((len(q), V.shape[1]))            # running weighted sum of values
        for k0 in range(0, q0 + tile, tile):          # tiles wholly above the diagonal are skipped
            s = q @ K[k0:k0 + tile].T / np.sqrt(d_k)  # one tile of scores, never stored
            rows, cols = np.arange(q0, q0 + len(q))[:, None], np.arange(k0, k0 + tile)[None, :]
            s[cols > rows] = -np.inf
            largest = max(largest, s.size)
            m_new = np.maximum(m, s.max(axis=1))
            scale = np.exp(m - m_new)                 # rescale the old totals to the new maximum
            e = np.exp(s - m_new[:, None])
            r = r * scale + e.sum(axis=1)
            o = o * scale[:, None] + e @ V[k0:k0 + tile]
            m = m_new
        out[q0:q0 + tile] = o / r[:, None]
    return out, largest

    What it changes, and what it does not

    • The result is exact. Up to the rounding of floating-point arithmetic, the output is the same as plain attention’s.
    • Memory falls from T^2 to T. Only tiles, the running totals and the output are held, so long contexts no longer need room for the score grid.
    • Speed rises because far less data moves through main memory. The paper reported attention several times faster than the standard implementation of the time.
    • Training does not store the probabilities for the backward pass either; it recomputes each tile when needed. That is more arithmetic but less memory traffic, a good trade on a GPU.
    • The arithmetic still grows with T^2. FlashAttention removes the memory cost of the grid, not the work of computing it. Approximations such as sliding-window attention () are a different idea.

    Later versions, FlashAttention-2 (2023) and FlashAttention-3 (2024), divide the work better between the GPU’s cores and use newer hardware features such as fp8 on H100 GPUs. You rarely call it yourself: PyTorch’s built-in scaled_dot_product_attention and inference servers such as vLLM use FlashAttention-style kernels when the hardware supports them.

    Common misconceptions

    • “FlashAttention approximates attention to make it faster.” It computes the same numbers in a different order.
    • “FlashAttention makes long contexts cheap.” It removes the memory for the score grid and much of the memory traffic. The arithmetic still grows with the square of the length.
    • “FlashAttention shrinks the KV cache.” The cache stores keys and values, not scores. Grouped-query attention () and quantization () shrink the cache.

    Key takeaways

    • Plain attention stores the T\times T scores and probabilities in main memory, and the traffic, not the arithmetic, sets its speed.
    • FlashAttention computes attention one tile at a time in fast on-chip memory and writes only the output.
    • A running maximum, sum and weighted sum per query let the softmax be computed in pieces, exactly.
    • It saves memory and time, but the arithmetic still grows with T^2.

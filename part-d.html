    Builds on Self-attention and the causal mask from ; the block from .

    A different task for this section: translating “le chat noir dort”. To write “black”, the decoder queries the encoder’s output and puts 61% of its attention on “noir”.

    Everything so far described a single stack that reads and writes one sequence. The original 2017 Transformer was built differently, for translation: one stack, the encoder, reads the whole input sentence; a second stack, the decoder, writes the output sentence one token at a time. The two are joined by a third kind of attention, cross-attention, through which the decoder consults the encoder’s result at every step.

    • Encoder: self-attention with no causal mask. The input is fully known, so every source token may look at every other, left and right. It runs once.
    • Decoder: causal self-attention over the output written so far, exactly as in Part B, because the rest of the output does not exist yet.
    • Cross-attention: the same query–key–value computation, with one change. The queries come from the decoder, while the keys and values come from the encoder’s output. In the library analogy, the readers are in one building and the books in another.

    The equations, and the reasoning behind them

    The question: how does the decoder read the source sentence? It already has a tool for “one set of vectors gathers information from another set”: attention. The only change is where the three inputs come from. The decoder is the one asking, so it supplies the queries. The encoder holds the answers, so it supplies the keys and values.

    Let X_{\text{dec}} be the decoder’s vectors, shape [T_tgt, d_model], and X_{\text{enc}} the encoder’s output, shape [T_src, d_model].

    Q=X_{\text{dec}}W_Q,\qquad K=X_{\text{enc}}W_K,\qquad V=X_{\text{enc}}W_V
    \mathrm{CrossAttention}(X_{\text{dec}},X_{\text{enc}})=\mathrm{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}\right)V

    Compare with : the formula is identical. Q has T_{\text{tgt}} rows and K has T_{\text{src}} rows, so the weight table QK^{\top} has shape [T_tgt, T_src]: a rectangle, not a square.

    Why no causal mask here?
    The mask exists to hide tokens that have not been produced yet. The whole source sentence is known before decoding starts, so nothing in it is “in the future”, and every decoder position may read all of it.

    A decoder block therefore has three sublayers, each an update added to the stream:

    \begin{aligned}x' &= x + \mathrm{MaskedSelfAttention}(\mathrm{LayerNorm}(x))\\ x'' &= x' + \mathrm{CrossAttention}(\mathrm{LayerNorm}(x'),\,X_{\text{enc}})\\ y &= x'' + \mathrm{FFN}(\mathrm{LayerNorm}(x''))\end{aligned}

    First look at what has been written so far, then consult the source, then process the result. This is written in the pre-norm style of for consistency; the 2017 paper normalised after each addition instead ().

    Worked example: the decoder is about to write “black”

    Translating “le chat noir dort”. The decoder has written “the” and its query is q=[0,0,2,0], with d_k=4 and the encoder keys and values shown in the visualizer below.

    \begin{aligned}\text{dot products } q\cdot k_j &= [0,\ 2,\ 4,\ 0]\quad(\text{le, chat, noir, dort})\\ \text{divide by }\sqrt{4}=2 &\Rightarrow [0,\ 1,\ 2,\ 0]\\ \exp &\Rightarrow [1,\ 2.7183,\ 7.3891,\ 1],\ \text{sum}=12.1073\\ \alpha &= [0.0826,\ 0.2245,\ 0.6103,\ 0.0826]\\ c=\textstyle\sum_j\alpha_jv_j &= [0.1239,\ 0.5316,\ 1.2206,\ -0.1793]\end{aligned}

    61% of the attention lands on “noir”, the third source word, even though “black” is the second target word. Cross-attention is free to reorder.

    Parameter cost, with d_{\text{model}}=8,\ d_{\text{ff}}=32 and the formulas of : an encoder block, like a decoder-only block, has 288+552+32=872 parameters. A decoder block adds a second attention layer and a third LayerNorm: 872+288+16=1176.

    To write “black”, the decoder asks the encoder “which source word should I translate now?”. The answer is mostly “noir” (61%), with some weight on “chat” (22%), the noun that “noir” describes. French puts the adjective after the noun and English before it, and cross-attention handles the swap without any special rule.

    In Python: cross-attention
    Runs on its own · Python 3 + NumPy
    import numpy as np


def softmax(S, axis=-1):
    e = np.exp(S - S.max(axis=axis, keepdims=True))
    return e / e.sum(axis=axis, keepdims=True)


def attention(Q, K, V):              # the same function as self-attention
    A = softmax(Q @ K.T / np.sqrt(Q.shape[-1]))
    return A @ V, A


source = ["le", "chat", "noir", "dort"]           # encoder side
written = ["<s>", "the", "black"]                 # decoder input so far
Q_dec = np.array([[2, 1, 0, 0], [0, 0, 2, 0], [0, 2, 0, 0]], dtype=float)
K_enc = np.array([[2, 0, 0, 0], [0, 2, 1, 0], [0, 1, 2, 0], [0, 0, 0, 2]],
                 dtype=float)
V_enc = np.array([[1, 0, 0, 0.5], [0, 2, 0, 1], [0, 0, 2, -1], [0.5, 1, 0, 2]])

# Queries from the decoder; keys and values from the encoder. No causal mask.
context, weights = attention(Q_dec, K_enc, V_enc)
print("weights shape:", weights.shape, "= [T_tgt, T_src], a rectangle")

i = 1                                             # decoder has written "the"
print("after 'the', alpha =", weights[i].round(4))
print("context c         =", context[i].round(4))
print("most attended     =", source[weights[i].argmax()])
for word, row in zip(written, weights):
    print(f"query from {word!r:8} attends most to {source[row.argmax()]!r}")

# Output:

    Contrast with the decoder-only design

    A decoder-only model has no encoder and no cross-attention. To translate, it puts the source and the target in one sequence, “le chat noir dort <s> the black cat …”, and relies on ordinary causal self-attention. The target tokens can still look back at the source tokens, so the job cross-attention did is absorbed into self-attention. The widget below shows who may attend to whom in each design.

    What just happened? In the encoder–decoder view there are three separate tables, each with its own weights. In the decoder-only view the same three kinds of connection appear as regions of a single lower-triangular table, computed by one set of attention weights. One region shrinks: source tokens can no longer see later source tokens, because the single causal mask applies to them too.

    Neither design is strictly better. Encoder–decoder models fit tasks with a clear input and a clear output, such as translation or speech recognition, and give the input a bidirectional reading. Decoder-only models are simpler, treat every task as “continue this text”, and can be pretrained on raw text with no input–output pairs, which is a large part of why they became the default for general-purpose LLMs.

    Common misconceptions

    • “Cross-attention needs a causal mask.” It does not. The whole source is available from the start. Only the decoder’s self-attention is masked.
    • “The encoder runs again for every generated token.” It runs once. Its output is fixed and reused by every decoder step.
    • “Decoder-only models cannot translate or summarise.” They can: the source goes in the prompt and self-attention reaches back to it.
    • “Cross-attention is a different mechanism.” It is the same scaled dot-product attention, with queries from one sequence and keys and values from another.
    • Pitfall: each kind of attention has its own W_Q, W_K, W_V. The decoder’s self-attention and cross-attention do not share weights.

    Key takeaways

    • The encoder reads the whole source with unmasked self-attention; the decoder writes the target with masked self-attention.
    • Cross-attention: Q from the decoder, K and V from the encoder. Same formula as before.
    • Its weight table is a rectangle, [T_tgt, T_src], and needs no causal mask.
    • Decoder-only models do the same job by putting source and target in one sequence.

    What the paper’s model looked like

    It is the encoder–decoder design of : 6 encoder layers and 6 decoder layers. The paper trained two sizes on the WMT 2014 translation benchmarks.

    BLEU is a translation score from 0 to 100 that measures word-sequence overlap with human reference translations. At the time, 28.4 on English–German was the best published result, including against ensembles of several models, and it was reached at a fraction of the usual training cost.

    The equations that are specific to the paper

    The attention and multi-head formulas of and are the paper’s own, unchanged. Four other details differ from the GPT-style recipe used in the rest of this guide.

    1. Normalisation after the residual add (“post-norm”).

    x\leftarrow\mathrm{LayerNorm}\big(x+\mathrm{Sublayer}(x)\big)
    How this differs from .
    There, the stream is left alone and only a copy is normalised before each sublayer. Here the stream itself is normalised after every addition, so there is no untouched path from the first layer to the last. That makes deep stacks harder to train, which is why later models moved the normalisation.

    2. ReLU in the feed-forward network, not GELU, and fixed sinusoidal positional encodings ():

    \mathrm{FFN}(x)=\max(0,\;xW_1+b_1)\,W_2+b_2

    3. Scaled, shared embeddings. One weight matrix serves as the source embedding, the target embedding and the output projection, and embeddings are multiplied by \sqrt{d_{\text{model}}} before the positional encoding is added. The reason for the scaling: embedding values start out small, while positional encodings range up to 1, so without it the position signal would drown out the token.

    4. A learning-rate schedule with warm-up, which became a standard ingredient of Transformer training:

    \eta(\text{step})=d_{\text{model}}^{-0.5}\cdot\min\!\left(\text{step}^{-0.5},\ \ \text{step}\cdot\text{warmup}^{-1.5}\right)

    \eta is the learning rate (the paper calls it lrate). \text{step} counts training steps from 1. \text{warmup} is a fixed number of steps, 4000 in the paper.

    Reading the formula.
    The \min chooses between two candidates. \text{step}\cdot\text{warmup}^{-1.5} is a straight line rising from zero; it is the smaller one early on. \text{step}^{-0.5} is a slowly falling curve; it is the smaller one later. They are equal exactly when \text{step}=\text{warmup}, which is where the rate peaks. The factor d_{\text{model}}^{-0.5} gives wider models smaller steps. The gentle start stops a randomly initialised model from being thrown off course by its first, very noisy gradients.

    The paper also used the Adam optimizer with \beta_1=0.9,\ \beta_2=0.98,\ \epsilon=10^{-9}, and label smoothing of 0.1, which trains towards targets that are slightly less than 100% certain.

    Worked example: the learning-rate schedule

    Base model, d_{\text{model}}=512, \text{warmup}=4000. First, 512^{-0.5}=0.044194.

    At step 1 the second term of the minimum is smaller: 1\times4000^{-1.5}=3.9528\times10^{-6}, so \eta=0.044194\times3.9528\times10^{-6}=1.747\times10^{-7}.

    At step 4000 the two terms are equal, 4000^{-0.5}=0.015811, and the rate peaks: \eta=0.044194\times0.015811=6.988\times10^{-4}.

    At step 100,000: 100000^{-0.5}=0.0031623, so \eta=0.044194\times0.0031623=1.398\times10^{-4}, one fifth of the peak.

    The learning rate starts almost at zero, climbs in a straight line for 4,000 steps to about 0.0007, then slides down slowly. By the end of training it is a fifth of its peak.

    In Python: the learning-rate schedule, post-norm and pre-norm
    Runs on its own · Python 3 + NumPy
    import numpy as np


def paper_lr(step, d_model=512, warmup=4000):
    return d_model ** -0.5 * min(step ** -0.5, step * warmup ** -1.5)


for step in (1, 4000, 100_000):
    print(f"step {step:>7,}: lr = {paper_lr(step):.4g}")
print("peak = (d_model * warmup) ** -0.5 =", round((512 * 4000) ** -0.5, 7))


def layer_norm(x, eps=1e-5):
    mu = x.mean(axis=-1, keepdims=True)
    return (x - mu) / np.sqrt(x.var(axis=-1, keepdims=True) + eps)


def post_norm(x, sublayer):          # 2017 paper: normalise after the add
    return layer_norm(x + sublayer(x))


def pre_norm(x, sublayer):           # GPT-style: normalise a copy first
    return x + sublayer(layer_norm(x))


rng = np.random.default_rng(0)
W = rng.normal(0, 0.1, size=(8, 8))
sublayer = lambda x: np.tanh(x @ W)
x = rng.normal(3, 2, size=(4, 8))

print("post-norm stream: mean", post_norm(x, sublayer).mean().round(3),
      "std", post_norm(x, sublayer).std().round(3), "(rescaled every layer)")
print("pre-norm stream:  mean", pre_norm(x, sublayer).mean().round(3),
      "std", pre_norm(x, sublayer).std().round(3), "(the input passes through)")

    Common misconceptions

    • “Modern LLMs use the paper’s architecture as written.” The core is intact, but normalisation placement, activation, positional scheme and overall structure have all changed.

    Rotary position embeddings (RoPE)

    The problem. “The cat” means the same at the start of a document and deep inside it. So what attention needs is how far apart two tokens are, more than where each one sits. Adding a position vector to the input () mixes position into everything, and leaves the model to work out distances for itself.

    The change. RoPE adds nothing to the input. Instead, inside every attention layer, it rotates each query and each key by an angle that grows with the token’s position.

    Why that works. Split a vector into pairs of numbers, and treat each pair as an arrow in a plane. Turning an arrow does not change its length. Turn the query at position i by i\omega and the key at position j by j\omega. The angle between them then changes by (i-j)\omega, so their dot product depends only on the distance i-j. For one pair (x_1,x_2):

    \operatorname{RoPE}(x_1,x_2;\,i)=\left(x_1\cos i\omega-x_2\sin i\omega,\ \ x_1\sin i\omega+x_2\cos i\omega\right),\qquad \omega_f=10000^{-2f/d_k}

    i is the token’s position. \omega is the pair’s rotation speed, and each pair f=0,1,\dots,d_k/2-1 has its own. The first pairs turn quickly and tell neighbours apart. The last pairs turn slowly and carry long-range position. Queries and keys are rotated; values are not.

    Llama 3 uses a base of 500,000 instead of 10,000. That slows every pair down, which helps with long contexts.

    Interactive · RoPE turns queries and keys by their position

    The point: After rotation, the attention score depends only on the distance between the two tokens. Do this: Move the query and key positions, then press “Shift both by 5” several times. Switch to a slower pair. Watch for: The score stays the same when both move together, and the slow pair barely turns.

    Dimension pair
     
    What is simplified: one pair of dimensions out of d_k/2 is drawn, with a hand-picked query and key; the real score adds up the contributions of all pairs.
    What just happened? Each arrow is turned by its position times the pair’s speed. Moving both positions by the same amount turns both arrows equally. The angle between them stays the same, and so does the score: only the distance matters. A fast pair turns a lot between neighbouring positions. A slow pair hardly moves over dozens of tokens, so it can still compare tokens that are far apart.

    RMSNorm

    The problem. LayerNorm () does four things to each vector: it subtracts the mean, divides by the standard deviation, then scales and shifts. Experiments found that not all of that is needed.

    The change. RMSNorm only divides by the root mean square, then scales. There is no mean and no shift. Current models place it before each sublayer (pre-norm).

    The gain. Less work per token, and models train as well. So most current models use it.

    \operatorname{RMSNorm}(x)=\gamma\odot\frac{x}{\sqrt{\frac{1}{d_{\text{model}}}\sum_i x_i^2+\epsilon}}

    \gamma is the learned gain and \epsilon a small constant, as in LayerNorm.

    SwiGLU

    The problem. The 2017 MLP is simple: one projection, a ReLU, another projection. Later experiments found a design that learns more for the same compute.

    The change. A gated MLP computes two projections of the input. One of them, passed through a smooth switch function called SiLU, decides how much of the other gets through, element by element. This is SwiGLU.

    The gain. A lower loss for the same compute. This is an empirical finding, not something derived.

    \operatorname{FFN}(x)=\left(\operatorname{SiLU}(xW_1)\odot xW_3\right)W_2,\qquad \operatorname{SiLU}(z)=z\cdot\operatorname{sigmoid}(z)

    W_1 and W_3 are [d_model, d_ff], and W_2 is [d_ff, d_model]. Three matrices instead of two would add parameters, so models choose a smaller d_{\text{ff}} than 4d_{\text{model}}. Llama 3.1 8B uses 14,336, which is 3.5 times 4,096.

    Grouped-query attention (GQA)

    The problem. The KV cache () stores a key and a value for every head, in every layer, for every token. At long contexts it grows bigger than the model’s weights.

    The change. Do all the heads need their own keys and values? Experiments say no. In grouped-query attention the query heads are split into groups, and each group shares one key head and one value head. Multi-query attention is the extreme case: one key and value head for all.

    The gain. Queries keep all their heads, so the model still looks for many different things. Only what is stored shrinks:

    M_{\text{KV}}=2\times L\times T\times n_{\text{kv}}\times d_k\times\text{bytes per number}\times B

    n_{\text{kv}} is the number of key and value heads per layer. GQA divides the cache by h/n_{\text{kv}}. With n_{\text{kv}}=h this is ordinary multi-head attention, and the cache formula used earlier in the guide, since h\,d_k=d_{\text{model}}.

    Interactive · how many key and value heads?

    The point: Sharing keys and values between query heads shrinks the cache without changing the weights much. Do this: Start with 32 KV heads (multi-head), then choose 8 and 1, and raise the context length. Watch for: The coloured groups of query heads, and the cache against the weights.

    What is simplified: the shape is Llama 3.1 8B’s (32 layers, 32 query heads of width 128, 8.03 billion parameters in bf16); the other choices of KV heads are hypothetical versions of it, and their small change in parameter count is ignored. The cache is stored at 16 bits; servers can also quantize it.
    What just happened? Each colour is one key and value head and the query heads that read it. With 32 KV heads, every query head has its own and the cache is largest. With 8, four query heads share each pair and the cache is a quarter of the size. With 1, everything shares one pair. At long contexts the multi-head cache is several times the weights, which is why nearly every current model uses GQA.

    Mixture of experts (MoE)

    The problem. A model with more parameters can hold more knowledge, but in an ordinary model every token passes through every parameter. Twice the parameters means twice the work per token.

    The change. A mixture-of-experts layer replaces the single MLP with many smaller MLPs, the experts, and a small router. For each token, in each layer, the router scores the experts, keeps the few best and blends their outputs:

    \operatorname{MoE}(x)=\sum_{e\in\mathcal{S}(x)}g_e(x)\,\operatorname{FFN}^{(e)}(x),\qquad g(x)=\operatorname{softmax}\!\big(\text{router scores of the chosen experts}\big)

    \mathcal{S}(x) is the set of experts chosen for this token: usually 1 to 8 out of n_{\text{experts}}, which is often 8 to 128. g_e is expert e’s gate, and the gates add up to 1. \operatorname{FFN}^{(e)} is expert e’s MLP.

    Training adds a small extra loss that keeps tokens spread across the experts. Without it, the router tends to send everything to a favourite few.

    The gain, and the cost. Each token passes through only the chosen experts, so compute and the bytes read per token follow the active parameter count. But any token may be sent to any expert, so every expert must be in memory: memory follows the total count. That is why the mixture-of-experts models in are fast for their size but still need a lot of memory.

    Worked example

    The cache. Llama 3.1 8B stores 2\times32\times8\times128\times2=131{,}072 bytes per token, which is 128 KiB. Its full context is 131,072 tokens, so the cache for one request is 131{,}072\times131{,}072\approx17.2 GB. That is more than its 16.1 GB of bf16 weights.

    With 32 key and value heads instead of 8, the cache would be 68.7 GB. The full context would then not fit on even an 80 GB GPU alongside the weights.

    Experts. Mixtral 8x7B has 8 experts per layer and sends each token to 2. It has 46.7 billion parameters in total, and all of them must be in memory. Each token uses only 12.9 billion of them, about 28%, so it computes like a 13B model.

    The cache. Llama 3.1 8B shares each key and value head between four query heads. At its longest context of about 131,000 tokens, its cache is about 17 GB. Without sharing it would be about 69 GB, more than four times the model’s own weights.

    Experts. Mixtral 8x7B picks 2 of its 8 experts for every token. All 46.7 billion parameters must be in memory, but only 12.9 billion are used for each token.

    In Python: RoPE, RMSNorm, SwiGLU, grouped-query attention and a router
    Runs on its own · Python 3 + NumPy
    import numpy as np

rng = np.random.default_rng(0)
d_model, h, n_kv, T = 64, 8, 2, 6
d_k = d_model // h


def rms_norm(x, gain, eps=1e-6):
    # LayerNorm without the mean subtraction and without the shift
    return gain * x / np.sqrt((x ** 2).mean(-1, keepdims=True) + eps)


def silu(z):
    return z / (1 + np.exp(-z))


def swiglu(x, W1, W3, W2):
    # one projection is passed through SiLU and gates the other, element by element
    return (silu(x @ W1) * (x @ W3)) @ W2


def rope(x, positions, base=10000.0):
    # rotate each pair of dimensions (2f, 2f+1) by the angle position * omega_f
    omega = base ** (-np.arange(0, x.shape[-1], 2) / x.shape[-1])
    angle = positions[:, None] * omega
    x1, x2 = x[..., 0::2], x[..., 1::2]
    out = np.empty_like(x)
    out[..., 0::2] = x1 * np.cos(angle) - x2 * np.sin(angle)
    out[..., 1::2] = x1 * np.sin(angle) + x2 * np.cos(angle)
    return out


# RoPE: the score depends only on how far apart the query and the key are
q, k = rng.normal(size=d_k), rng.normal(size=d_k)
score = lambda i, j: rope(q[None], np.array([i]))[0] @ rope(k[None], np.array([j]))[0]
print(f"score(10, 7) = {score(10, 7):.4f}, score(103, 100) = {score(103, 100):.4f}")

# Grouped-query attention: 8 query heads share 2 key/value heads
X = rms_norm(rng.normal(size=(T, d_model)), np.ones(d_model))
Wq = rng.normal(size=(d_model, h * d_k)) / 8
Wk, Wv = (rng.normal(size=(d_model, n_kv * d_k)) / 8 for _ in range(2))
pos = np.arange(T)
Q = rope((X @ Wq).reshape(T, h, d_k).transpose(1, 0, 2), pos)       # [h, T, d_k]
K = rope((X @ Wk).reshape(T, n_kv, d_k).transpose(1, 0, 2), pos)    # [n_kv, T, d_k]
V = (X @ Wv).reshape(T, n_kv, d_k).transpose(1, 0, 2)
K, V = np.repeat(K, h // n_kv, axis=0), np.repeat(V, h // n_kv, axis=0)
s = Q @ K.transpose(0, 2, 1) / np.sqrt(d_k) + np.triu(np.full((T, T), -np.inf), 1)
a = np.exp(s - s.max(-1, keepdims=True))
out = (a / a.sum(-1, keepdims=True)) @ V
print("queries", Q.shape, "cached keys per layer", (n_kv, T, d_k), "output", out.shape)

d_ff = 3 * d_model
W1, W3 = (rng.normal(size=(d_model, d_ff)) / 8 for _ in range(2))
W2 = rng.normal(size=(d_ff, d_model)) / 8
print("SwiGLU output", swiglu(X, W1, W3, W2).shape)

# KV cache for the Llama 3.1 8B shape: 32 layers, 32 query heads, 8 KV heads of width 128
for name, heads in (("multi-head", 32), ("grouped-query", 8), ("multi-query", 1)):
    per_token = 2 * 32 * heads * 128 * 2                                # keys and values, 2 bytes
    print(f"{name:13}: {per_token / 1024:4.0f} KiB per token, "
          f"{per_token * 131072 / 1e9:5.1f} GB for 131,072 tokens")

# Mixture of experts: a router picks 2 of 8 experts for each token
router = rng.normal(size=(d_model, 8)) / 8
logits = X @ router
top = np.argsort(-logits, axis=1)[:, :2]
gates = np.exp(np.take_along_axis(logits, top, 1))
gates /= gates.sum(1, keepdims=True)
print("experts chosen for each token:", top.tolist())
print("gates for the first token:", gates[0].round(3))

# score(10, 7) = -1.5865, score(103, 100) = -1.5865

    Common misconceptions

    • “RoPE adds a position vector to the embeddings.” Nothing is added to the input. Queries and keys are rotated inside every attention layer; values are not.
    • “GQA means fewer attention heads.” Queries keep all their heads. Only keys and values are shared.
    • “A mixture-of-experts model sends each question to one expert model.” Routing happens for every token in every layer, and the experts are MLPs inside one model, not separate models.
    • “These changes make a different kind of model.” It is still a decoder-only Transformer trained on next-token prediction; the changes are refinements for cost and stability.

    Key takeaways

    • RoPE rotates queries and keys by their positions, so attention scores depend on the distance between tokens.
    • RMSNorm drops LayerNorm’s mean and shift; SwiGLU gates the MLP; both are cheaper or better for the same compute.
    • GQA shares key and value heads between query heads and divides the KV cache by h/n_{\text{kv}}.
    • A mixture-of-experts model needs memory for all its parameters but computes only with the active ones.

    Check yourself

    Only the distance i-j=3 matters. Swapping the positions reverses the distance.

    2. A model has 32 query heads and 8 key and value heads. Compared with ordinary multi-head attention, its KV cache is:

    32 ÷ 8 = 4 query heads share each key and value head.

    3. A mixture-of-experts model has 46.7B parameters, 12.9B active per token. What does it need memory for?

    Any token may be routed to any expert, so all must be loaded. The active count sets the work per token.

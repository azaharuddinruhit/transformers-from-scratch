    The running example

    The guide follows one prompt, “the cat sat on the ▢”, through the whole model. Here you only see the two ends: the text goes in, and “mat” comes out as the most probable next token.

    A large language model is a function with one job: given some text, say how likely each possible next piece of text is. Everything else, from answering questions to writing code, comes from running that one function again and again.

    • Token: the unit of text the model reads and writes. Usually a word or a piece of a word.
    • Vocabulary: the fixed list of all tokens the model knows, typically 30,000 to 200,000 entries.
    • Next-token prediction: the model outputs one probability per vocabulary entry.
    • Autoregressive generation: pick a token, append it to the input, predict again.
    • Parameters: the numbers inside the function (millions to trillions) that training adjusts.
    • Training changes the parameters so good predictions become likelier. Inference uses the finished parameters without changing them.

    The equations, and the reasoning behind them

    Step 1: scores. For the next position the network outputs one real number per vocabulary entry, called a logit and written z_v for entry v. A higher logit means “more plausible here”. But logits can be negative and do not add up to anything in particular, so they are not probabilities yet.

    Step 2: turn scores into probabilities. We need numbers that are positive and sum to 1. Softmax gets there in two moves: exponentiate every logit, which makes it positive and keeps the ranking, then divide by the total, which makes the sum 1.

    p(w_{t+1}=v \mid w_1,\dots,w_t)=\mathrm{softmax}(z)_v=\frac{e^{z_v}}{\sum_{v'=1}^{n_{\text{vocab}}} e^{z_{v'}}}

    w_t is the token at position t; v and v' run over the n_{\text{vocab}} vocabulary entries; the bar “|” reads “given”.

    Why the exponential? Dividing each logit by the plain sum would fail: logits can be negative, and the sum can be zero. The exponential is always positive. It also gives logits a precise meaning: a gap of 1 between two logits always means a probability ratio of e\approx2.72, wherever the two logits sit. That is why adding the same number to every logit changes nothing; only the gaps matter.

    Step 3: from one token to a whole text. The probability of a sequence is the probability of its first token, times the probability of the second given the first, and so on. This is the chain rule of probability. It is exact, and it is the reason a next-token predictor is a model of entire texts.

    p(w_1,\dots,w_T)=\prod_{t=1}^{T}p(w_t\mid w_{\lt t})

    T is the number of tokens and w_{\lt t} means “all tokens before position t”.

    Worked example

    Three tokens with logits z=[2.0,\;1.0,\;0.1].

    Exponentiate: e^{2.0}=7.3891,\; e^{1.0}=2.7183,\; e^{0.1}=1.1052, which sum to 11.2125.

    Divide each by the sum: p=[0.6590,\;0.2424,\;0.0986]. They add up to 1.

    Check the “gap” rule: the first two logits differ by 1, and 0.6590/0.2424=2.72.

    Three candidate tokens get scores 2.0, 1.0 and 0.1. Softmax turns those into roughly 66%, 24% and 10%. The gaps between scores matter, not the scores themselves: adding 5 to every score changes nothing.

    Beginner note

    The model never outputs a word directly. It outputs a list of numbers as long as the vocabulary, and a separate, simple piece of code chooses a token from that list.

    Common misconceptions

    • “It looks answers up in a database.” There is no stored text. There are only parameters, and the text is recomputed from them one token at a time.
    • “It predicts the next word.” It predicts a probability distribution over tokens, and tokens are often pieces of words.
    • “It learns while I chat with it.” During inference the parameters are frozen. It only appears to remember because the whole conversation is fed back in as input each time.
    • “Next-token prediction is too simple to be useful.” Predicting the next token of a proof, a program or a dialogue well requires modelling a great deal about what the text is describing.

    Key takeaways

    • An LLM is a function from “text so far” to one probability per vocabulary entry.
    • Softmax = exponentiate, then divide by the sum. Only the gaps between logits matter.
    • The chain rule turns next-token probabilities into the probability of a whole text.
    • Generation is a loop: predict, pick, append, repeat.

    3. Two logits differ by 1. How do their probabilities compare?

    A gap of 1 in logits is always a ratio of e in probability, whatever the other logits are.

    The running example

    In an RNN, information from “cat” must survive three updates to influence the prediction after “the cat sat on the”. In a Transformer the last position can look at “cat” directly.

    Everything in this guide descends from one eleven-page paper by Vaswani, Shazeer, Parmar, Uszkoreit, Jones, Gomez, Kaiser and Polosukhin, presented at the NIPS conference in 2017. It was not about chatbots. It was about machine translation, and its claim was narrow and bold: you can drop recurrence and convolution entirely and build a translation model from attention alone, and it will be both better and much faster to train.

    You do not need to understand the paper yet. This section explains the problem it solved, so that the components in the following sections have a purpose. The paper itself is read in detail in , once you know all the parts.

    The problem it solved

    Before 2017 the standard tool for sequences was the recurrent neural network (RNN, usually an LSTM). An RNN reads one token at a time and carries a single “memory” vector forward. That has two costs. Training cannot be parallelised along the sequence, because step 50 needs the result of step 49. And information from an early word has to survive dozens of updates to reach a late one. Attention had already been added to RNNs as a helper (Bahdanau et al., 2014). The 2017 paper kept the helper and removed the RNN.

    RNNword 1 → 2 → 3 → … → n
    :
    n − 1 stepsbetween the first and last word; computed one after another
    Transformerevery word ↔ every word
    :
    1 stepbetween any two words; all positions computed in parallel

    What it costs

    The paper compared the two kinds of layer directly. For a sequence of T tokens and width d_{\text{model}} (the paper writes n and d):

    Layer typeWork per layerSequential stepsLongest path between two positions
    Self-attentionO(T^{2}\cdot d_{\text{model}})O(1)O(1)
    RecurrentO(T\cdot d_{\text{model}}^{2})O(T)O(T)

    d_{\text{model}} is the length of the vector the model keeps for each token; you will meet it properly in . Self-attention compares all T^2 pairs of tokens, each comparison costing about d_{\text{model}}. A recurrent layer takes T steps, each a d_{\text{model}}\times d_{\text{model}} matrix product.

    What the model is made of: the road ahead

    Removing recurrence leaves gaps that other parts have to fill. Each gets its own section:

    • Tokens and embeddings turn text into vectors ().
    • Positional information restores word order, which an RNN had for free ().
    • Self-attention lets every token read every other token (), several times in parallel ().
    • A feed-forward network, residual connections and normalisation turn attention into a trainable block ().
    • A stack of blocks plus an output layer is the complete model ().

    Common misconceptions

    • “The paper invented attention.” Attention was already used alongside RNNs. The contribution was a model built on it with no recurrence at all, plus multi-head attention and the surrounding recipe.
    • “Attention is literally all you need.” The model also needs feed-forward layers, residual connections, normalisation, embeddings and positional information. Remove any of them and it stops working.
    • “The paper introduced large language models.” It introduced a translation model of at most 213 million parameters. Pretraining on raw text and scaling up came later.

    Key takeaways

    • RNNs process tokens one after another: no parallelism along the sequence, and long paths between distant words.
    • Self-attention connects every pair of tokens in one step and computes all positions in parallel.
    • The price is work that grows with the square of the sequence length.
    • The 2017 paper introduced the recipe; modern LLMs keep its core and change a few details.

    Check yourself

    1. Why can an RNN not be trained in parallel along the sequence?

    Step 50 takes the memory vector produced by step 49 as input, so the steps must run in order.

    2. When does a self-attention layer do less arithmetic than a recurrent layer?

    The costs are T²·d_model against T·d_model². They are equal at T = d_model.

    3. What was the 2017 paper’s model built for?

    It was an encoder–decoder translation model. Decoder-only language models came afterwards.

    The running example

    “the cat sat on the” becomes 5 tokens, then 5 integer IDs, then 5 rows of the table E: a matrix of shape [5, d_model]. Both copies of “the” get exactly the same row, which is the problem the next section solves.

    Neural networks do arithmetic, so text has to become numbers. This happens in two steps: the tokenizer cuts text into tokens and replaces each with an integer ID, then the embedding table swaps each ID for a vector of real numbers that the network can learn to adjust.

    Characters, words or subwords?

    • Characters: tiny vocabulary, never meets an unknown symbol, but sequences get very long and each unit carries little meaning.
    • Words: meaningful units, but the vocabulary is enormous and any word not seen in training cannot be represented.
    • Subwords (what real LLMs use): common words stay whole, rare words are assembled from pieces. “played” becomes play + ##ed. Nothing is ever out of vocabulary, and sequences stay short.

    The equation, and the reasoning behind it

    The question: how should a token be presented to a network that only does arithmetic? Three candidates:

    • The ID itself (say 4071). This would tell the network that token 4071 is nearly the same as 4072 and very different from 12, which is meaningless.
    • A one-hot vector: n_{\text{vocab}} numbers, all 0 except a single 1. No false ordering, but it is enormous and makes every pair of tokens exactly equally different.
    • A short learned vector of d_{\text{model}} numbers per token. Compact, and training can move similar tokens close together. This is the embedding.

    The vectors are stored as the rows of one matrix, and using a token means reading its row:

    x_t = E[w_t], \qquad E\in\mathbb{R}^{n_{\text{vocab}}\times d_{\text{model}}}

    w_t is the token ID at position t; E is the embedding table; E[w_t] is its row number w_t; x_t is the resulting vector of length d_{\text{model}}.

    Math detail: lookup is a matrix product in disguise

    Multiplying a one-hot row vector by E picks out exactly one row: x_t=\mathrm{onehot}(w_t)\,E. Nobody computes it that way because indexing is far cheaper, but it shows that the embedding table is an ordinary weight matrix, trained by gradient descent like every other one.

    Worked example

    Take n_{\text{vocab}}=5 and d_{\text{model}}=2:

    E=\begin{bmatrix}0.1&0.3\\-0.2&0.5\\0.7&-0.4\\0.0&0.9\\0.6&0.6\end{bmatrix},\quad w_t=2 \;\Rightarrow\; \mathrm{onehot}(w_t)=[0,0,1,0,0] \;\Rightarrow\; x_t=E[2]=[0.7,\,-0.4]

    Rows are counted from 0, so ID 2 is the third row.

    Think of the embedding table as a spreadsheet with one row per token. Token ID 2 means “use row 2”. That row of numbers is the token’s vector.

    What training does to embeddings

    At the start the vectors are random. Training nudges them so that tokens used in similar contexts end up with similar vectors. Real embeddings have hundreds or thousands of dimensions; squashed to two for plotting, related tokens tend to sit near each other.

    Common misconceptions

    • “One token is one word.” A rough rule for English is 3 to 4 characters per token. Rare words, names and code split into many pieces.
    • “Token IDs carry meaning.” ID 6 is not “close to” ID 7. IDs are arbitrary labels; only the embedding vectors carry meaning.
    • “Embeddings are designed by people.” They start random and are learned. Nobody assigns a dimension to mean “is an animal”.
    • Pitfall: a model must be used with the exact tokenizer it was trained with. A different tokenizer produces IDs that point at the wrong rows.

    Key takeaways

    • A tokenizer is a fixed algorithm, not a neural network: text in, integer IDs out.
    • An embedding is a lookup: ID w_t selects row E[w_t].
    • E has shape [n_vocab, d_model] and is learned like any other weight matrix.
    • Training moves tokens that are used alike close together; nobody assigns the dimensions a meaning.

    One row of 768 numbers for each of 50,000 tokens: 50,000 × 768.

    3. What happens to a word that is not in the vocabulary?

    Subword tokenizers fall back to smaller pieces, down to single characters or bytes.

    The running example

    Each of the 5 vectors gets a position vector added. The two “the” tokens, at positions 0 and 4, started identical and are now different. The shape is still [5, d_model].

    The attention mechanism you will meet next treats its input as an unordered collection of vectors. Shuffle the input tokens and each token’s output is the same as before, just shuffled along with it. So “dog bites man” and “man bites dog” would look identical to it. To fix this, we add a second vector to every token embedding that depends only on where the token sits.

    E[“dog”]what the token is

    position vector for slot 2where it is

    Two common ways to build position vectors

    • Learned positional embeddings (GPT-2): a second table E_{\text{pos}} with one trainable row per position. Simple, but there is no row for positions beyond the trained maximum.
    • Sinusoidal positional encoding (the original Transformer): a fixed formula using sine and cosine waves of different wavelengths. Nothing to train, and any position has a defined value.

    Many recent models use relative schemes such as rotary embeddings (RoPE) that inject position inside attention itself. The goal is unchanged: make order visible.

    The equations, and the reasoning behind them

    The question: what vector should stand for “position t”? It has to have length d_{\text{model}} so it can be added to a token vector, its values should stay small, every position needs a different vector, and neighbouring positions should get similar ones.

    The idea: think of how a binary counter writes numbers. The last digit flips at every step, the next one every two steps, the next every four. Read together, the digits identify the number. Sinusoidal encoding is the smooth version of this: each pair of dimensions is a wave with its own wavelength, short for the first pairs and very long for the last.

    PE(t,2i)=\sin\!\left(\frac{t}{10000^{2i/d_{\text{model}}}}\right),\qquad PE(t,2i+1)=\cos\!\left(\frac{t}{10000^{2i/d_{\text{model}}}}\right)

    t is the position (0, 1, 2, …); i=0,1,\dots,d_{\text{model}}/2-1 numbers the pairs of dimensions, so dimensions 2i and 2i+1 share a wavelength. The 2017 paper writes pos where this guide writes t.

    Why this form? The divisor 10000^{2i/d_{\text{model}}} grows from 1 for the first pair to almost 10000 for the last, so wavelengths run from about 6 positions to about 63,000: fast waves separate neighbours, slow waves separate distant positions. Sine and cosine come as a pair because together they fix a point on a circle, like a clock hand; with sine alone, two positions on either side of a peak would look identical. The constant 10000 is simply large enough that the slowest wave never repeats within a realistic sequence.

    The input to the first layer is the sum of the two vectors. From here on, x_t means this sum:

    x_t = E[w_t] + PE(t)
    Why add and not concatenate? Adding keeps the width at d_{\text{model}}, so nothing downstream changes size. In hundreds of dimensions there is room for both signals, and the model learns to read content from some directions and position from others.

    Worked example

    With d_{\text{model}}=4 there are two pairs: i=0 divides by 10000^{0}=1 and i=1 divides by 10000^{2/4}=100.

    \begin{aligned}PE(0)&=[\sin 0,\ \cos 0,\ \sin 0,\ \cos 0]=[0,\ 1,\ 0,\ 1]\\ PE(1)&=[\sin 1,\ \cos 1,\ \sin 0.01,\ \cos 0.01]=[0.8415,\ 0.5403,\ 0.0100,\ 1.0000]\\ PE(2)&=[\sin 2,\ \cos 2,\ \sin 0.02,\ \cos 0.02]=[0.9093,\ -0.4161,\ 0.0200,\ 0.9998]\end{aligned}

    The first two numbers change a lot from one position to the next. The last two barely move; they only become informative across hundreds of positions.

    Picture a row of clock hands turning at different speeds. The fast hands distinguish position 3 from position 4. The slow hands distinguish position 30 from position 300. Read together, they give every position a unique fingerprint.

    Math detail: equivariant, strictly speaking

    People say attention is “permutation-invariant”. The precise statement is that self-attention without positions is permutation-equivariant: permuting the inputs permutes the outputs in the same way and changes nothing else. Anything computed from the collection as a whole is then invariant to order. Either way, word order is invisible.

    This holds for attention with no mask. A causal mask does break the symmetry, because each token sees a different number of predecessors, but that is a weak and indirect signal. GPT-style models still add explicit positional information.

    Common misconceptions

    • “Adding position vectors corrupts the token’s meaning.” In high dimensions there is room for both. The model learns to read content and position from the same vector.
    • “Position is concatenated.” In the classic design it is added, so the vector size stays d_{\text{model}}.
    • Pitfall: a model with learned absolute positions cannot process sequences longer than its position table.

    Key takeaways

    • Attention by itself treats its input as a set, so order must be supplied.
    • Each position gets its own vector of length d_{\text{model}}, added to the token vector.
    • Sinusoidal encoding: fast waves separate neighbours, slow waves separate distant positions.
    • Learned position tables and newer relative schemes do the same job in other ways.

    Queries, keys and values: a library analogy

    Imagine each token is both a reader and a book in a library.

    • As a reader it writes a query: a note describing what it is looking for.
    • As a book it carries a key: a label on the spine describing what it contains.
    • It also holds a value: the content it hands over if someone picks it.

    Each reader compares its query with every book’s key. A good match means “read more of this one”. But instead of choosing a single book, the reader takes a blend of all the values, weighted by how well each key matched.

    Deriving the formula, one decision at a time

    The goal: give token i a new vector that summarises the other tokens, weighted by how relevant each is to token i. Each step below settles one design question. The input is the matrix X of shape [T, d_model], whose row t is the vector x_t from the previous section.

    1. Three roles, three projections. What a token is looking for, what it advertises about itself, and what it hands over are three different things. So each gets its own learned matrix:

    Q = XW_Q,\qquad K = XW_K,\qquad V = XW_V

    Row i of Q is the query q_i; row j of K and V are the key k_j and value v_j. Each matrix has shape [T, d_k], where d_k is the length of a query or key.

    2. Relevance is a dot product. We need one number for “how relevant is token j to token i?”. The dot product q_i\cdot k_j is large when the two vectors point the same way, near zero when they are unrelated and negative when they are opposed. It is cheap, and because W_Q and W_K are learned, the model itself decides what “pointing the same way” should mean.

    3. Divide by \sqrt{d_k}. A dot product adds up d_k terms. If each term varies by about 1, the sum varies by about \sqrt{d_k}, so longer vectors give larger scores for no meaningful reason. Dividing by \sqrt{d_k} returns the scores to a typical size of 1 whatever the dimension. Without it, large scores push softmax into a near one-hot output where gradients vanish.

    4. Softmax turns scores into a budget. Token i should distribute a fixed amount of attention: weights that are positive and sum to 1. That is exactly what softmax produces ().

    5. Blend the values. The new vector is the average of the value vectors, weighted by the budget.

    s_{ij}=\frac{q_i\cdot k_j}{\sqrt{d_k}},\qquad \alpha_{ij}=\frac{e^{s_{ij}}}{\sum_{j'}e^{s_{ij'}}},\qquad c_i=\sum_j \alpha_{ij}\,v_j

    s_{ij} is the scaled score of key j for query i; \alpha_{ij} is the attention weight; c_i is the context vector for token i.

    6. All tokens at once. Stack the three steps into matrices. Entry (i,j) of QK^{\top} is q_i\cdot k_j, softmax is applied to each row, and multiplying by V forms every weighted sum in one go:

    \mathrm{Attention}(Q,K,V)=\mathrm{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}\right)V
    • Q, K, V: one row per token, shape [T, d_k].
    • QK^{\top}: every query dotted with every key, shape [T, T].
    • softmax, applied to each row: one query’s scores become weights that sum to 1.
    • Multiplying by V: row i of the result is c_i. Output shape [T, d_k].

      The whole attention matrix, and the causal mask

      Running every token as a query gives a square table: row i shows where token i looks. A GPT-style model has one more rule. It is trained to predict the next token, so a token must not be allowed to look at tokens that come after it, or it could simply read the answer. The causal mask enforces this by setting the score to -\infty wherever j \gt i, before softmax. Since e^{-\infty}=0, those positions receive exactly zero weight.

      s_{ij}\leftarrow\begin{cases}s_{ij}& j\le i\\-\infty& j\gt i\end{cases}\qquad\text{then}\qquad \alpha_{i}=\mathrm{softmax}(s_{i})

      Common misconceptions

      • “Attention weights explain the model’s reasoning.” They show where information flowed in one layer and head. They are a useful clue, not a complete explanation.
      • “The mask is applied after softmax.” It must be applied before, so the remaining weights still sum to 1.
      • “Q, K and V are three different inputs.” In self-attention all three are projections of the same token vectors.
      • Pitfall: forgetting the \sqrt{d_k} scaling. With large d_k, unscaled scores make softmax nearly one-hot and learning stalls.

      Key takeaways

      • Attention = for each token, a weighted average of all tokens’ value vectors.
      • Weights come from query·key dot products, scaled by \sqrt{d_k}, then softmax.
      • In matrix form: \mathrm{softmax}(QK^{\top}/\sqrt{d_k})\,V.
      • The causal mask sets scores for later tokens to −∞ so that a position cannot see the future.
      • Attention weights show where information was read from; they are not an explanation of the model’s reasoning.

      The equations, and the reasoning behind them

      The limitation: in , each token gets one row of weights, one softmax, one “question”. The fix: run h separate attention computations, called heads. To keep the cost unchanged, each head works in a smaller space of d_k=d_{\text{model}}/h dimensions, with its own projection matrices of shape [d_model, d_k]:

      \mathrm{head}_m=\mathrm{Attention}\!\left(XW_Q^{(m)},\;XW_K^{(m)},\;XW_V^{(m)}\right),\qquad m=1,\dots,h

      This is the single-head formula with matrices that belong to head m; the superscript (m) only says “which head”. Each head’s output has shape [T, d_k]. The 2017 paper writes these matrices as W_i^{Q}, W_i^{K}, W_i^{V}.

      The h outputs are placed side by side, which restores the width h\cdot d_k=d_{\text{model}}, and one more matrix mixes them:

      \mathrm{MultiHead}(X)=\mathrm{Concat}(\mathrm{head}_1,\dots,\mathrm{head}_h)\,W_O
      Why W_O? Concatenation alone would confine each head to its own fixed slice of the output vector. The matrix W_O, of shape [d_model, d_model], lets the model combine what different heads found and write the result anywhere in the vector that later layers read. In code the per-head projections are usually one big matrix whose output is reshaped into h slices, which is the same thing.

      • Outputs are concatenated back to d_{\text{model}} and mixed by W_O.
      • Input and output shapes are identical: [B, T, d_model].

      The feed-forward network (MLP)

      After attention has gathered context, each token’s vector is passed through the same small network, independently of every other token. Attention decides what to collect; the MLP decides what to make of it. Most of a Transformer’s parameters live here. It works in three moves:

      • Expand. W_1 maps the vector from d_{\text{model}} up to d_{\text{ff}} numbers, typically 4 times as many. Think of each of these as a detector for one pattern.
      • Bend. A non-linear function lets each detector respond strongly to some inputs and stay quiet for others.
      • Contract. W_2 maps back to d_{\text{model}}, writing what the detectors found into the token’s vector.
      \mathrm{FFN}(x)=\mathrm{GELU}(xW_1+b_1)\,W_2+b_2

      x is one token’s vector (length d_{\text{model}}); W_1 has shape [d_model, d_ff] and W_2 has shape [d_ff, d_model]; b_1 and b_2 are bias vectors.

      Why the non-linearity? Without it the formula would be (xW_1)W_2=x(W_1W_2): two matrices in a row are just one matrix, so the second layer would add nothing. The bend in the middle is what lets the network compute things a single matrix cannot. A note on notation: many texts write this as W_2\,\mathrm{GELU}(W_1x+b_1)+b_2 with column vectors. It is the same computation transposed. This guide writes vectors as rows, so xW lines up with the shapes [T, d_model] you see in code.

      This guide uses GELU, the activation in GPT-2 and most LLMs since. It is applied to each number a separately:

      \mathrm{GELU}(a)=a\,\Phi(a),\qquad \mathrm{ReLU}(a)=\max(0,a)

      \Phi(a) is the probability that a standard normal random number is below a, a value between 0 and 1.

      Why this form? Read \Phi(a) as a smooth gate: close to 1 for large positive a (the input passes through), close to 0 for large negative a (it is blocked), and in between near zero. ReLU is the same gate with a hard on/off switch at 0. The smooth version gives a usable gradient everywhere, which tends to make training better behaved.

      Worked example: a tiny FFN

      Input x=[1,2], d_{\text{ff}}=3, biases zero.

      W_1=\begin{bmatrix}1&0.5&-1\\-1&2&1\end{bmatrix},\quad xW_1=[-1,\ 4.5,\ 1],\quad \mathrm{GELU}=[-0.1587,\ 4.5000,\ 0.8413]
      W_2=\begin{bmatrix}1&0\\0&1\\1&-1\end{bmatrix},\quad \mathrm{FFN}(x)=[0.6827,\ 3.6586]

      The first entry of xW_1 is 1\cdot1+2\cdot(-1)=-1. The first output is -0.1587+0.8413 and the second is 4.5000-0.8413. Results are computed at full precision and rounded for display, which is why a last digit can differ by one from adding the rounded terms.

      The two input numbers are stretched into three, bent by GELU (big positives pass through, negatives are mostly squashed), then recombined into two. The bending is what lets the network compute things a single matrix cannot.

      Residual connections

      Instead of replacing a token’s vector, each sublayer adds its result to it:

      x \leftarrow x + \mathrm{Sublayer}(x)

      \mathrm{Sublayer} stands for either attention or the MLP; the arrow means “the new value of x is”.

      Each token’s vector becomes a running total that every layer reads from and writes to. This running total is called the residual stream.

      Why add? Two reasons. Going forward, a layer only has to learn a correction to the vector; if it has nothing useful to say it can output something near zero and the information passes through untouched. Going backward, the slope of x+\mathrm{Sublayer}(x) with respect to x is “1 plus the sublayer’s slope”. That constant 1 gives the gradient a path to every earlier layer that is never multiplied by any weights, so it cannot shrink to nothing however deep the stack is.

      Layer normalization

      As vectors pass through many layers their scale can drift, growing huge or shrinking towards zero. LayerNorm resets it, one token’s vector at a time, in four steps:

      1. Compute the mean of the vector’s numbers: \mu=\frac{1}{d_{\text{model}}}\sum_i x_i.
      2. Compute their variance: \sigma^2=\frac{1}{d_{\text{model}}}\sum_i (x_i-\mu)^2.
      3. Subtract the mean and divide by the standard deviation. The vector now has mean 0 and standard deviation 1.
      4. Multiply by a learned scale \gamma and add a learned shift \beta.
      \mathrm{LayerNorm}(x)=\gamma\odot\frac{x-\mu}{\sqrt{\sigma^{2}+\epsilon}}+\beta

      x_i is the i-th number of the vector; \gamma and \beta are learned vectors of length d_{\text{model}}; \odot multiplies element by element; \epsilon is a tiny constant that prevents division by zero.

      Why step 4? Forcing every vector to mean 0 and spread 1 might be too rigid for what a layer needs. \gamma and \beta start at 1 and 0 (no effect) and let training choose a different scale and offset per dimension. The scale is then under the model’s control instead of drifting.

      Worked example: LayerNorm

      x=[2,4,6,8], with \gamma=1,\ \beta=0 and ignoring \epsilon.

      Mean \mu=\tfrac{2+4+6+8}{4}=5. Variance \sigma^2=\tfrac{9+1+1+9}{4}=5, so \sigma=2.2361.

      \mathrm{LayerNorm}(x)=\left[\tfrac{-3}{2.2361},\tfrac{-1}{2.2361},\tfrac{1}{2.2361},\tfrac{3}{2.2361}\right]=[-1.3416,\ -0.4472,\ 0.4472,\ 1.3416]

      Subtract the average so the numbers centre on zero, then divide by their spread. [2, 4, 6, 8] and [200, 400, 600, 800] come out identical: only the pattern survives, not the scale.

      Putting it together: the Transformer block

      GPT-style models use the “pre-norm” arrangement. Read each line below as: normalise a copy of the stream, compute an update from it, add the update to the stream.

      \begin{aligned}x' &= x + \mathrm{MultiHead}(\mathrm{LayerNorm}(x))\\ y &= x' + \mathrm{FFN}(\mathrm{LayerNorm}(x'))\end{aligned}

      x is the block’s input, x' the stream after the attention update and y the block’s output. \mathrm{MultiHead} is the self-attention of , with the causal mask.

      The shape never changes, which is what makes blocks stackable. Tensor shapes are written [batch, sequence_length, d_model], shortened to [B, T, d_model]: B independent sequences processed together, T tokens in each, d_model numbers per token.

Turn both off and the signal either dies away or blows up exponentially, depending on the weight scale; a network in that state cannot be trained. Residuals without normalisation keep the signal alive but let it grow layer after layer. Normalisation without residuals keeps the sizes tame in this toy, but each layer then overwrites its input, so nothing guarantees the original token information survives.

      Common misconceptions

      • “The MLP mixes information between tokens.” It does not. It is applied to each position separately; only attention moves information across positions.
      • “LayerNorm is the same as BatchNorm.” LayerNorm uses statistics of a single token’s vector, so it behaves identically in training and inference and does not depend on batch size.
      • “Residual connections are an optimisation trick you could drop.” Deep Transformers do not train without them.
      • Pitfall: the original 2017 paper put the normalisation after the residual add (post-norm). Pre-norm, shown here, is what GPT-style models use because it is easier to train at depth. compares the two.

      Key takeaways

      • FFN: expand to d_{\text{ff}}, apply GELU, contract back. Applied to each token separately.
      • Residual: every sublayer adds to the stream and never replaces it.
      • LayerNorm: rescale each token’s vector to mean 0, spread 1, then apply a learned scale and shift.
      • Block = x+\mathrm{MultiHead}(\mathrm{LayerNorm}(x)), then the same pattern with the FFN.
      • Input and output shapes match, so blocks stack.

      The running example

      You now have every part. A GPT-style model is those parts in a straight line: turn text into vectors, refine the vectors through a stack of identical blocks, then turn the final vectors back into a probability for every token in the vocabulary. It is called “decoder-only” because it keeps just the generating half of the original encoder–decoder Transformer, which covers.

      The whole model is four lines. Each one is something you have already met:

      \begin{aligned}x^{(0)}_t &= E[w_t]+E_{\text{pos}}[t] &&\text{token and position vectors, added}\\ x^{(\ell)} &= \mathrm{Block}_{\ell}\!\left(x^{(\ell-1)}\right),\ \ \ell=1,\dots,L &&L\text{ blocks, each refining the stream}\\ z &= \mathrm{LayerNorm}\!\left(x^{(L)}\right)W_U &&\text{final normalisation, then vocabulary scores}\\ p &= \mathrm{softmax}(z) &&\text{scores to probabilities}\end{aligned}

      The superscript (\ell) counts blocks: x^{(0)} is the input to the first block and x^{(L)} the output of the last. E_{\text{pos}} is the learned position table (or the sinusoidal PE of ). W_U has shape [d_model, n_vocab], so z holds one logit per vocabulary entry.

      Why does W_U look like that? Each logit is the dot product of the final vector with one column of W_U, so there is one column per vocabulary entry, and the entry whose column best matches the vector scores highest. It is the embedding lookup run in reverse, from vector back to token, which is why many models reuse the embedding table E for it (“weight tying”).

      One detail makes training efficient: the model produces a next-token prediction at every position at once. Position 3’s output predicts token 4, and thanks to the causal mask it was computed without seeing token 4.

        Counting parameters

        The rule: a linear layer from a numbers to b numbers has a\times b weights and b biases. Apply that to every part of the model:

        • Token embeddings: one row of d_{\text{model}} numbers for each of n_{\text{vocab}} entries.
        • Position embeddings: one row for each of T positions.
        • Attention, per block: four [d_model, d_model] matrices (W_Q, W_K, W_V, W_O), each with a bias of length d_{\text{model}}.
        • MLP, per block: W_1 with its bias (d_{\text{model}}d_{\text{ff}}+d_{\text{ff}}) and W_2 with its bias (d_{\text{ff}}d_{\text{model}}+d_{\text{model}}).

        L is the number of blocks, T the context length, d_{\text{ff}} the MLP’s hidden width. The number of heads h does not appear: heads slice the same matrices.

        Worked example

        The loss: cross-entropy, derived

        What we want: a model that gives real text a high probability. From , the probability of a text is a product of next-token probabilities, \prod_t p_\theta(w_t\mid w_{\lt t}).

        Make it workable. A product of thousands of numbers below 1 is astronomically small and awkward to differentiate. Taking the logarithm turns the product into a sum without changing which parameters are best.

        Turn it into something to minimise. Optimizers minimise, so flip the sign. Then divide by the number of tokens so the value does not depend on how long the text is:

        \mathcal{L}(\theta)=-\frac{1}{T}\sum_{t=1}^{T}\log p_{\theta}\!\left(w_t \mid w_{\lt t}\right)

        \theta stands for all the parameters; p_\theta(w_t\mid w_{\lt t}) is the probability the model gave to the token that really came next; \log is the natural logarithm. In words: \mathcal{L}=-\sum_t\log p(\text{target}_t\mid\text{tokens}_{\lt t}), averaged over positions.

        Why -\log? It is 0 when the model gave the correct token probability 1, and it grows without limit as that probability approaches 0. So a confident mistake is punished far more than a hesitant one. It also has a plain reading: the loss is the model’s average surprise at the real text. A useful reference point: guessing uniformly gives every token probability 1/n_{\text{vocab}}, hence a loss of \ln n_{\text{vocab}}. An untrained model starts near that value.

        Teacher forcing

        The targets are just the inputs shifted one place left, so a single sequence of T tokens provides T training examples. At every position the model is given the true previous tokens rather than its own guesses; this is called teacher forcing. Combined with the causal mask (), it lets all positions be trained in one parallel pass.

        inputthe␣ca
        targethe␣cat

        From loss to learning

        • Batching: B sequences are processed together so the update reflects an average over examples and the hardware is used efficiently.
        • Backpropagation: the chain rule, applied mechanically from the loss back through every layer, yields the gradient \nabla_\theta\mathcal{L}: for each parameter, how much the loss would rise if that parameter increased slightly.
        • Gradient descent: move every parameter a small step in the direction that lowers the loss.
        \theta\leftarrow\theta-\eta\,\nabla_{\theta}\mathcal{L}

        \eta is the learning rate, the step size.

        Why the minus sign? The gradient points in the direction in which the loss increases fastest, so we step the opposite way. \eta controls how far: too small and training crawls, too large and each step overshoots. It usually warms up from zero, then decays. In practice the optimizer (Adam or AdamW) replaces the raw gradient with a running average that gives each parameter a step size suited to it. One elegant fact: for softmax with this loss, the gradient with respect to each logit is simply “predicted probability minus 1 for the correct token, predicted probability for every other”. The model is pushed in proportion to how wrong it was.

        Reading loss curves

        • Validation loss is measured on text held out from training. It estimates how well the model handles text it has not seen, which is what you actually care about.
        • Underfitting: both losses stay high. The model is too small, has trained too briefly, or the learning rate is wrong.
        • Overfitting: training loss keeps dropping while validation loss stalls or rises. The model is memorising its training text instead of learning patterns that carry over.
        • Why curves matter: they are the main instrument panel of training. A flat line, a sudden spike or a widening gap between the two curves each points to a different problem, long before you read any generated text.

        Common misconceptions

        • “Loss should reach zero.” Language is uncertain; many continuations are valid. A loss of zero would mean memorisation.
        • “The model is trained on its own outputs.” During pretraining it always sees real text (teacher forcing). It first consumes its own outputs at inference time.
        • “A larger learning rate just trains faster.” Beyond a point it destabilises training or settles on a worse result.
        • Pitfall: evaluating on data that overlaps the training set makes a model look better than it is.

        • Context window: the maximum number of tokens the model can take in. Older tokens beyond it are simply not seen.
        • Greedy decoding: always take the most probable token. Deterministic, but prone to dull, repetitive text.
        • Temperature T: divide the logits by T before softmax. Below 1 sharpens the distribution, above 1 flattens it.

        • Repetition penalty: lower the logits of tokens already present in the context, to discourage loops.
        • KV cache: when one token is appended, the keys and values of all earlier tokens are unchanged, because the causal mask stops them seeing the new token.         The equations, and the reasoning behind them

        Temperature. We want one dial that makes the model’s distribution sharper or flatter without retraining. Recall from that softmax depends only on the gaps between logits. So divide every logit by a number \tau before softmax:

        p_v=\frac{e^{z_v/\tau}}{\sum_{v'} e^{z_{v'}/\tau}}

        z_v is the logit of vocabulary entry v; \tau is the temperature; \tau=1 leaves the model’s distribution unchanged.

        Why does dividing work? Dividing by \tau multiplies every gap by 1/\tau. A small \tau stretches the gaps, so the largest logit dominates; as \tau\to0 this becomes greedy decoding. A large \tau shrinks the gaps, pushing the distribution towards uniform. The ranking of tokens never changes, only how much the ranking matters. That is the whole “determinism versus creativity” dial: low temperature repeats the model’s single best guess; high temperature gives lower-ranked guesses a real chance, which reads as more varied and, pushed too far, as incoherent.

        Top-k and top-p. Even a sensible distribution has a long tail of very unlikely tokens, and over hundreds of steps an unlucky draw from that tail becomes likely. Both filters choose a set S of tokens to keep, discard the rest, and rescale what is left so it sums to 1 again:

        p'_v=\begin{cases}\dfrac{p_v}{\sum_{u\in S}p_u}& v\in S\\[2ex]0& v\notin S\end{cases}

        For top-k, S is the k most probable tokens. For top-p, S is the smallest set of most-probable tokens whose probabilities total at least p.

        Logits z=[2.0,\ 1.0,\ 0.1] again.

        The vocabulary of serving

        • Latency: how long one request takes. Usually split into time to first token and the generation speed after it, in tokens per second.
        • Streaming: sending each token to the user as soon as it is produced. It does not make generation faster, but the wait people feel becomes the time to first token and not the full response time.
        • Throughput: tokens per second summed over all requests being served. This is what determines cost.
        • Batching: running several requests through the model in the same step. One pass over the weights serves all of them, so throughput rises; past a point each request slows down. Throughput and latency pull in opposite directions.
        • Memory: the weights, plus one KV cache per active request, plus working space. The cache grows with every token of context.
        • Prompt caching: keeping the KV cache of a prefix that many requests share, such as a long system prompt, so its prefill is paid once.
        • Beam search: keeping several candidate continuations alive and choosing the most probable overall. Common in translation; rare in chat models, where sampling gives more natural text.
        • Speculative decoding: a small, fast model drafts a few tokens and the large model checks them in one parallel pass, keeping those it agrees with. Done correctly, the output distribution is unchanged and only the speed improves.

        The equations, and the reasoning behind them

        How much work does the cache save? Write P for the number of prompt tokens and n for the number of tokens to generate. To predict the first new token the model must process all P prompt positions; for the second, P+1 positions; and so on. Without a cache every pass starts from scratch, so the totals add up. With a cache, each pass after the first processes only the one position that is new:

        \text{without cache: }\sum_{j=0}^{n-1}(P+j)=nP+\frac{n(n-1)}{2}\qquad\qquad\text{with cache: }P+(n-1)

        j counts the passes from 0. The first total grows with n^2, the second with n.

        What does the cache cost? For every layer and every token it stores one key vector and one value vector. Summed over the heads, each has d_{\text{model}} numbers:

        M_{\text{KV}}=2\times L\times T\times d_{\text{model}}\times \text{bytes per number}\times B,\qquad M_{\text{weights}}=N\times\text{bytes per parameter}

        The 2 is for keys and values; L is the number of layers; T=P+n is the context length in use; B is the number of requests in the batch; N is the number of parameters.

        How long does a response take? The two phases simply add:

        t_{\text{response}}\approx t_{\text{first token}}+\frac{n}{\text{tokens per second}}
        Math detail: the rough speed model used by the estimator below

        Processing one token costs about 2N floating-point operations (one multiply and one add per parameter), so hardware delivering F operations per second can do at most F/2N tokens per second in total. There is a second limit: every decode step has to read all the weights from memory once, however many requests share that step. With a memory bandwidth of R bytes per second, that allows R/M_{\text{weights}} steps per second, or B\cdot R/M_{\text{weights}} tokens per second for a batch of B. Whichever limit is lower wins:

        \text{throughput}\approx\min\!\left(\frac{F}{2N},\ \frac{B\,R}{M_{\text{weights}}}\right),\qquad \text{speed per request}=\frac{\text{throughput}}{B},\qquad t_{\text{first token}}\approx\max\!\left(\frac{2N\,P\,B}{F},\ \frac{M_{\text{weights}}}{R}\right)

        These are order-of-magnitude bounds. They ignore attention’s extra cost at long contexts, software overhead and hardware details, all of which make real systems slower.

        Worked example

        Work saved. Prompt of P=3 tokens, generate n=5. Without a cache the passes process 3+4+5+6+7=25 token positions. With a cache: 3 in prefill, then 1 for each of the 4 later steps, 7 in all.

        Cache memory. A GPT-2-small-sized model, L=12,\ d_{\text{model}}=768, with T=1024 tokens of context at 2 bytes per number: 2\times12\times1024\times768\times2=37{,}748{,}736 bytes, about 37.7 MB, next to 248.9 MB of weights. A larger model with L=32,\ d_{\text{model}}=4096 and T=8192: 2\times32\times8192\times4096\times2=4{,}294{,}967{,}296 bytes, about 4.29 GB, for one request.

        Response time. Time to first token 0.4 s, then 50 tokens per second, for a 200-token answer: 0.4+200/50=4.4 seconds.

        Generating 5 tokens after a 3-token prompt takes 25 units of work if the model starts over each time, and 7 if it remembers its earlier work. The memory for that remembering is modest for a small model and several gigabytes per conversation for a large model with a long context.

        Beginner note

        This is why a model that “fits” on a device can still feel slow, and why a long conversation can run out of memory even though the model itself has not changed: the weights are fixed, but the cache grows with every token.

        Common misconceptions

        • “The KV cache saves memory.” It spends memory to save computation.
        • “Generation can be parallelised like training.” A prompt is processed in parallel, but each output token depends on the one before it, so decoding is sequential.
        • “Tokens per second is a property of the model.” It depends on hardware, precision, batch size and context length together.
        • “Streaming makes the model faster.” The total time is unchanged. Only the wait before the first visible word shrinks.
        • “Quantization only matters for fitting in memory.” Fewer bytes per weight also means fewer bytes to read on every step, which is often the real speed limit.
        • Pitfall: sizing hardware for the weights alone. Leave room for one KV cache per concurrent request at the longest context you intend to allow.

        Key takeaways

        • Because of the causal mask, earlier positions’ keys and values never change, so they can be cached.
        • Without a cache the work grows with n^2; with it, with n.
        • Cache memory = 2 × layers × tokens × d_{\text{model}} × bytes, per request.
        • Response time ≈ time to first token + output tokens ÷ tokens per second.
        • Batching raises total throughput but not the speed of a single request.

        • Model size (parameters, N): capacity to store patterns. More parameters help only if there is enough data to fill them.

        The equations, and the reasoning behind them

        Training compute. One forward pass costs about 2 floating-point operations per parameter per token: each weight is used in one multiplication and one addition. The backward pass costs about twice the forward pass. Together that is roughly 6 operations per parameter per token, so for N parameters and D training tokens:

        C_{\text{train}}\approx 6\,N\,D\ \ \text{FLOPs}

        Loss as a function of scale. Think of the loss as having three sources: a part no model can remove because language is uncertain, a part caused by having too few parameters, and a part caused by having seen too little data. Measured curves are close to straight lines on logarithmic axes, which is the signature of a power law, so each removable part is modelled as one:

        \mathcal{L}(N,D)\approx \mathcal{L}_{\infty}+\frac{a}{N^{r}}+\frac{b}{D^{s}}

        \mathcal{L}_\infty is the irreducible loss; a, b are constants; r, s are exponents between 0 and 1. This is the form fitted by Hoffmann et al. (2022).

        What the form tells you. The two fractions shrink independently. Make N enormous and the second term vanishes, but the third is untouched: you are left with \mathcal{L}_\infty+b/D^{s} however large the model. Whichever of parameters or data is scarce sets the floor, which is why the two must grow together.

        Worked example

        A model with N=10^{9} parameters trained on D=2\times10^{10} tokens needs about 6\times10^{9}\times2\times10^{10}=1.2\times10^{20} FLOPs. Stored at 16 bits (2 bytes) per weight, it occupies 2\times10^{9} bytes, or 2 GB; quantized to 4 bits, 0.5 GB.

        A 1-billion-parameter model reading 20 billion tokens costs on the order of a hundred billion billion arithmetic operations to train. Its weights take about 2 GB, or a quarter of that after 4-bit quantization.

        Common misconceptions

        • “Bigger is always better.” Only when data and compute grow too. An oversized model on too little data wastes compute and overfits.
        • “Scaling laws are laws of nature.” They are empirical fits over the ranges tested, for particular setups.

        • “Quantization is free.” It trades a little accuracy for a lot of memory, and the trade gets worse at very low bit widths.

        The equations, and the reasoning behind them

        The question: how does the decoder read the source sentence? It already has a tool for “one set of vectors gathers information from another set”: attention. The only change is where the three inputs come from. The decoder is the one asking, so it supplies the queries. The encoder holds the answers, so it supplies the keys and values.

        Let X_{\text{dec}} be the decoder’s vectors, shape [T_tgt, d_model], and X_{\text{enc}} the encoder’s output, shape [T_src, d_model].

        Q=X_{\text{dec}}W_Q,\qquad K=X_{\text{enc}}W_K,\qquad V=X_{\text{enc}}W_V
        \mathrm{CrossAttention}(X_{\text{dec}},X_{\text{enc}})=\mathrm{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}\right)V

        Compare with : the formula is identical. Q has T_{\text{tgt}} rows and K has T_{\text{src}} rows, so the weight table QK^{\top} has shape [T_tgt, T_src]: a rectangle, not a square.

        Why no causal mask here? The mask exists to hide tokens that have not been produced yet. The whole source sentence is known before decoding starts, so nothing in it is “in the future”, and every decoder position may read all of it.

        A decoder block therefore has three sublayers, each an update added to the stream:

        The equations that are specific to the paper

        The attention and multi-head formulas of and are the paper’s own, unchanged. Four other details differ from the GPT-style recipe used in the rest of this guide.

        1. Normalisation after the residual add (“post-norm”).

        x\leftarrow\mathrm{LayerNorm}\big(x+\mathrm{Sublayer}(x)\big)
        How this differs from . There, the stream is left alone and only a copy is normalised before each sublayer. Here the stream itself is normalised after every addition, so there is no untouched path from the first layer to the last. That makes deep stacks harder to train, which is why later models moved the normalisation.

        2. ReLU in the feed-forward network, not GELU, and fixed sinusoidal positional encodings ():

        \mathrm{FFN}(x)=\max(0,\;xW_1+b_1)\,W_2+b_2

        3. Scaled, shared embeddings. One weight matrix serves as the source embedding, the target embedding and the output projection, and embeddings are multiplied by \sqrt{d_{\text{model}}} before the positional encoding is added. The reason for the scaling: embedding values start out small, while positional encodings range up to 1, so without it the position signal would drown out the token.

        4. A learning-rate schedule with warm-up, which became a standard ingredient of Transformer training:

        \eta(\text{step})=d_{\text{model}}^{-0.5}\cdot\min\!\left(\text{step}^{-0.5},\ \ \text{step}\cdot\text{warmup}^{-1.5}\right)

        \eta is the learning rate (the paper calls it lrate); \text{step} counts training steps from 1; \text{warmup} is a fixed number of steps, 4000 in the paper.

        Reading the formula. The \min chooses between two candidates. \text{step}\cdot\text{warmup}^{-1.5} is a straight line rising from zero; it is the smaller one early on. \text{step}^{-0.5} is a slowly falling curve; it is the smaller one later. They are equal exactly when \text{step}=\text{warmup}, which is where the rate peaks. The factor d_{\text{model}}^{-0.5} gives wider models smaller steps. The gentle start stops a randomly initialised model from being thrown off course by its first, very noisy gradients.

        The paper also used the Adam optimizer with \beta_1=0.9,\ \beta_2=0.98,\ \epsilon=10^{-9}, and label smoothing of 0.1, which trains towards targets that are slightly less than 100% certain.

        Worked example: the learning-rate schedule

        Base model, d_{\text{model}}=512, \text{warmup}=4000. First, 512^{-0.5}=0.044194.

        At step 1 the second term of the minimum is smaller: 1\times4000^{-1.5}=3.9528\times10^{-6}, so \eta=0.044194\times3.9528\times10^{-6}=1.747\times10^{-7}.

        At step 4000 the two terms are equal, 4000^{-0.5}=0.015811, and the rate peaks: \eta=0.044194\times0.015811=6.988\times10^{-4}.

        At step 100,000: 100000^{-0.5}=0.0031623, so \eta=0.044194\times0.0031623=1.398\times10^{-4}, one fifth of the peak.

        The learning rate starts almost at zero, climbs in a straight line for 4,000 steps to about 0.0007, then slides down slowly. By the end of training it is a fifth of its peak.

        Common misconceptions

        • “Modern LLMs use the paper’s architecture as written.” The core is intact, but normalisation placement, activation, positional scheme and overall structure have all changed.
        • Pitfall: code or diagrams that follow the paper (post-norm, encoder–decoder) do not match GPT-style code (pre-norm, decoder-only). Check which one a tutorial is describing before comparing details.

        Key takeaways

        • The 2017 model is an encoder–decoder with post-norm, ReLU and sinusoidal positions.
        • Its attention and multi-head formulas are unchanged in every model since.
        • Warm-up then decay: a small learning rate while gradients are noisy, a peak, then a slow decline.
        • GPT kept the decoder, BERT kept the encoder; scaling the decoder-only branch led to LLMs.

        Architecture

        Q1Walk me through what happens when a prompt goes into a decoder-only LLM.

        • Tokenize: text becomes T integer IDs.
        • Embed: each ID selects a row of E; add position information. Shape [T, d_model].
        • L blocks, each: masked multi-head attention, then an MLP, each wrapped in LayerNorm and a residual add. Shape never changes.
        • Output: final LayerNorm, then W_U gives logits [T, n_vocab]; softmax at the last position gives the next-token distribution.
        • Decode: choose a token (greedy or sampling), append it, repeat. The KV cache avoids recomputing earlier positions.

        Likely follow-up: “Where are most of the parameters?” In the MLPs: with d_{\text{ff}}=4d_{\text{model}} an MLP has about 8d_{\text{model}}^2 weights, attention about 4d_{\text{model}}^2. Review:

        Q2Explain self-attention. Why divide by √d_k?

        • Each token is projected to a query, a key and a value.
        • Score of token j for token i is q_i\cdot k_j; softmax over j gives weights that sum to 1; the output is the weighted sum of values.
        • Matrix form: \mathrm{softmax}(QK^{\top}/\sqrt{d_k})\,V.
        • A dot product of d_k terms has a spread of about \sqrt{d_k}. Unscaled, large scores saturate softmax into near one-hot outputs with vanishing gradients. Dividing keeps the spread near 1.

        Trap: “attention weights explain the model’s decision.” They show where information was read from, not why the output was produced. Review:

        Q3Why multi-head attention? What are MQA and GQA?

        • One head gives each token one softmax, so one pattern of focus. Several heads capture several relationships at once (syntax, coreference, nearby tokens).
        • Each head works in d_k=d_{\text{model}}/h dimensions, so the cost and parameter count match one wide head.
        • Head outputs are concatenated and mixed by W_O.
        • MQA (multi-query): all heads share one key and value head. GQA (grouped-query): groups of query heads share a key and value head.
        • Why: the KV cache shrinks by the sharing factor, which cuts inference memory and speeds up decoding, with little quality loss.

        Review: ,

        Q4What does the causal mask do, and why does training still run in parallel?

        • It sets the scores for later positions to −∞ before softmax, so position t only sees positions ≤ t.
        • Training feeds the true text (teacher forcing) and predicts every next token in one pass; the mask makes every position’s prediction honest.
        • It matches generation, where the future does not exist yet.
        • It is also why the KV cache is exact: earlier positions never change when tokens are appended.

        Review: ,

        Q5Why do Transformers need positional encodings? What options exist?

        • Attention without a mask treats its input as a set: shuffle the tokens and the outputs shuffle with them. Order must be supplied.
        • Sinusoidal (2017 paper): fixed waves of different frequencies added to the embeddings.
        • Learned absolute (GPT-2): a trainable table, one row per position, with a hard maximum length.
        • RoPE (rotary): rotates queries and keys by a position-dependent angle so q\cdot k depends on the relative offset. Common in recent open models; context can be extended by rescaling its frequencies.
        • ALiBi: adds a distance-proportional penalty to attention scores.

        Review:

        Q6Why residual connections and LayerNorm? Pre-norm or post-norm?

        • Residual (x+f(x)): layers learn corrections; the gradient has a path to early layers that bypasses all weights, so deep stacks train.
        • LayerNorm: resets each token vector to mean 0 and spread 1, plus a learned scale and shift, so activations do not drift.
        • Post-norm (2017): normalise after the add. Pre-norm (GPT-style): normalise a copy before each sublayer; easier to train at depth.
        • RMSNorm, used in many recent models, drops the mean subtraction and the bias: cheaper and about as good.

        Review: ,

        Q7What is the cost of attention, and how do models handle long context?

        • Compute grows as T^2 d_{\text{model}}; a naive implementation stores a T\times T score matrix per head.
        • FlashAttention: exact attention computed in tiles held in fast on-chip memory, never storing the full matrix. Same result, much less memory traffic, faster.
        • Approximate or restricted attention: sliding windows, sparse patterns.
        • At inference, the KV cache grows linearly with T: GQA, paged KV memory and KV quantization address that.
        • Quality also matters: models often use information in the middle of a long context less reliably than at the start or end.

        Review: ,

        Q8Encoder-only, decoder-only, encoder–decoder: when would you use each?

        • Encoder-only (BERT family): bidirectional; classification, tagging, and embedding models for search.
        • Decoder-only (GPT family): causal; generation and general-purpose assistants. The dominant LLM design.
        • Encoder–decoder (T5, the 2017 model): a separate input and output, linked by cross-attention; translation and summarisation.
        • A decoder-only model can do seq2seq tasks by putting input and output in one sequence.

        Review:

        Q9What is a mixture of experts (MoE)?

        • The MLP in each block is replaced by many expert MLPs plus a small router.
        • The router sends each token to its top-k experts (often 1 or 2).
        • Result: many more total parameters with roughly the compute per token of a much smaller dense model.
        • Costs: all experts must sit in memory, an auxiliary loss is needed to balance load across experts, training can be less stable, and serving is more complex.

        Training

        Q10What is the pretraining objective? What is perplexity?

        • Next-token prediction with cross-entropy: the average of -\log p(correct next token) over all positions.
        • Self-supervised: the targets are the text itself shifted by one, so any raw text is training data.
        • Perplexity = e^{\mathcal{L}}: the effective number of tokens the model is choosing between. Lower is better.
        • Sanity check: an untrained model has loss near \ln n_{\text{vocab}}, perplexity near n_{\text{vocab}}.

        Trap: comparing perplexity across models with different tokenizers. The numbers are per token, and tokens differ. Review:

        Q11How does a base model become a chat assistant?

        • Pretraining on a very large text corpus: knowledge and language.
        • Supervised fine-tuning (SFT) on prompt–response examples: follows instructions, uses a chat format.
        • Preference tuning (RLHF or DPO) on pairs of better and worse answers: helpfulness, tone, safety.
        • Throughout: evaluation, red-teaming, safety data. Some models add training for reasoning or tool use.

        Review:

        Q12Why AdamW, warm-up and gradient clipping?

        • Adam keeps running averages of each parameter’s gradient and squared gradient, giving every parameter its own step size.
        • AdamW applies weight decay directly to the weights, separate from the adaptive step.
        • Warm-up: early gradients are noisy and Adam’s estimates are poor, so the learning rate starts small, then decays.
        • Gradient clipping caps the gradient norm, preventing one bad batch from causing a loss spike.

        Review: ,

        Q13The loss curve misbehaves. How do you diagnose it?

        • Loss spikes or NaN: learning rate too high, missing warm-up, bad data batch, precision overflow. Lower the LR, clip gradients, use bf16, inspect the batch.
        • Flat from the start: bug. Overfit one small batch first; check that labels are shifted and that the mask is right.
        • Train falls, validation rises: overfitting. More data, dropout or weight decay, early stopping.
        • Both plateau high: model too small or LR too low.

        Review:

        Q14What do scaling laws say? What is “Chinchilla-optimal”?

        • Loss falls as a smooth power law in parameters N, data D and compute, until one of them becomes the bottleneck.
        • Training compute is about 6ND FLOPs.
        • Hoffmann et al. (2022): for a fixed compute budget, grow N and D together, roughly 20 tokens per parameter.
        • In practice many models are trained on far more tokens than that: a smaller model is cheaper to serve, and serving cost dominates over the model’s lifetime.

        Review:

        Inference

        Q15What is the KV cache, and how much memory does it use?

        • During generation, the keys and values of earlier tokens are stored and reused; each step computes only the new token.
        • Valid because of the causal mask: earlier positions never change.
        • Memory ≈ 2 × layers × tokens × (KV heads × d_k) × bytes per number × batch. Without GQA the bracket is d_{\text{model}}.
        • It grows with context length and concurrent requests, and often limits how many users one GPU can serve.

        Review:

        Q16Prefill versus decode: why are they different?

        • Prefill: the whole prompt in one parallel pass. Compute-bound. Sets time to first token.
        • Decode: one token per step, reading all weights each step. Memory-bandwidth-bound. Sets tokens per second.
        • Batching many requests raises decode throughput because they share each read of the weights.

        Review:

        Q17How would you make inference cheaper or faster?

        • Quantization: 8- or 4-bit weights (e.g. GPTQ, AWQ) cut memory and bandwidth; check quality on your own eval.
        • Continuous batching and paged KV memory (as in vLLM): keep the GPU full and memory unfragmented.
        • Speculative decoding: a small draft model proposes several tokens, the large model checks them in one pass; with correct acceptance sampling the output distribution is unchanged.
        • Prefix (prompt) caching for shared system prompts and documents.
        • Smaller or distilled model, routing easy requests to it; shorter prompts; capped output length.

        Review:

        Q18Explain temperature, top-k and top-p. Is temperature 0 deterministic?

        • Temperature divides logits: below 1 sharpens, above 1 flattens; the ranking never changes.
        • Top-k keeps the k most likely tokens; top-p keeps the smallest set whose probabilities reach p. Both cut the unreliable tail.
        • Low temperature for extraction, classification and code; higher for brainstorming.
        • Temperature 0 means greedy, but outputs can still vary run to run in practice, because batching and floating-point arithmetic order are not fully deterministic.

        Concepts

        Q1What is RAG, and when would you choose it over fine-tuning?

        • Retrieve relevant passages for each query and include them in the prompt.
        • Use RAG for knowledge: private, changing or very large document sets. Updating means re-indexing, not retraining.
        • Gives citations and lets you enforce access control per user.
        • Use fine-tuning for behaviour: format, style, tone, domain phrasing. The two combine well.

        Trap: “fine-tune the model on our docs so it knows them.” Fine-tuning is unreliable for adding facts and cannot cite or be updated cheaply.

        Q2What is an embedding model, and how is similarity measured?

        • A model, often encoder-only, that maps a text to one vector; trained contrastively so related texts land close together.
        • Similarity is usually cosine similarity (a dot product of normalised vectors).
        • Bi-encoder: query and documents are embedded separately, so document vectors are computed once and search is fast.
        • Different from the token embeddings inside an LLM: one vector per text, not per token.

        Review:

        Q3How do you chunk documents?

        • Chunk size trades precision against context: small chunks match precisely but lose surrounding meaning; large chunks dilute the embedding and waste prompt space.
        • A common start: a few hundred tokens with some overlap, then tune on your eval.
        • Split on structure (headings, paragraphs, code blocks, table rows), not at a fixed character count.
        • Attach metadata: title, section path, date, source URL, permissions.
        • Parent–child: retrieve small chunks, pass their larger parent section to the model.

        Q4How does vector search scale to millions of chunks?

        • Exact search compares the query to every vector: too slow at scale.
        • Approximate nearest neighbour (ANN) indexes trade a little recall for large speed-ups: HNSW (navigable graph), IVF (search only nearby clusters), PQ (compressed vectors).
        • Filter on metadata (permissions, date, product) during search.
        • Tooling ranges from pgvector or FAISS to dedicated vector databases; choose by scale, filtering needs and operations effort.

        Q5Why hybrid search and reranking?

        • Embeddings capture meaning but miss exact strings: error codes, product IDs, names. Keyword search (BM25) catches those.
        • Run both and merge the lists, for example with reciprocal rank fusion.
        • A cross-encoder reranker reads query and passage together: much more accurate than a bi-encoder, but too slow for the whole corpus, so apply it to the top 20 to 100.
        • Then send only the best few passages to the LLM.

        Quality and evaluation

        Q6How do you evaluate a RAG system?

        • Evaluate retrieval and generation separately, so you know which stage to fix.
        • Retrieval: label which chunks answer each query; measure recall@k, MRR, nDCG.
        • Generation: faithfulness (every claim supported by the retrieved context), answer relevance, correctness against a reference answer.
        • Build the test set from real user questions plus hard cases; score with an LLM judge using a rubric, calibrated against human labels.
        • Re-run on every change: chunking, embedder, prompt, model.

        Review:

        Q7Name common RAG failure modes and fixes.

        • Right passage not retrieved: improve chunking, add hybrid search, rewrite the query, try a better or domain-tuned embedder.
        • Retrieved but ignored: too many passages, or the key one buried in the middle. Rerank, send fewer, put the best first.
        • Answers beyond the context: instruct the model to use only the context, allow “I don’t know”, require citations, check faithfulness.
        • Stale or conflicting sources: date metadata, de-duplication, prefer the newest.
        • Multi-part questions: decompose into sub-queries, or retrieve iteratively.

        Q8How do you handle follow-up questions in a conversation?

        • “What about the second one?” retrieves nothing useful on its own.
        • Rewrite the latest message into a standalone query using the chat history, then retrieve.
        • Other query techniques: generate several query variants; HyDE (write a hypothetical answer and embed that); decompose complex questions.

        Q9Context windows are huge now. Is RAG still needed?

        • Long context removes the need to retrieve for small, static document sets.
        • But cost and latency grow with prompt length, quality drops as irrelevant text is added, and corpora often exceed any window.
        • RAG also gives per-user access control and fresh data.
        • Common middle ground: retrieve generously, rerank, and let the long context hold more; use prompt caching for content that repeats.

        Review:

        Q10What security issues does RAG introduce?

        • Permission leakage: enforce access control at retrieval time, before any text reaches the model.
        • Indirect prompt injection: a document can contain instructions. Treat retrieved text as data, delimit it clearly, and limit what the model is allowed to do with it.
        • Sensitive data in the index: classify and redact before embedding; logs need the same care.

        When and how

        Q1Prompting, RAG or fine-tuning: how do you decide?

        • Start with prompting: cheapest, fastest to iterate, establishes a baseline on your eval.
        • Add RAG when the gap is missing knowledge.
        • Fine-tune when the gap is behaviour: consistent format or style, domain jargon, a narrow task done cheaply by a smaller model, or prompts that have grown too long.
        • Fine-tuning brings data collection, training, evaluation and maintenance costs; justify it with eval numbers.

        Review:

        Q2What is supervised fine-tuning (SFT)?

        • Train on (prompt, ideal response) pairs with the usual next-token loss.
        • The loss is usually computed only on the response tokens; prompt tokens are masked out.
        • Use the model’s own chat template exactly, or behaviour degrades.
        • Quality beats quantity: a few hundred to a few thousand clean, consistent examples often suffice for format and style.

        Review:

        Q3Full fine-tuning versus LoRA. How does LoRA work?

        • Full fine-tuning updates every weight. Memory holds weights, gradients and optimizer state: roughly 16 bytes per parameter with Adam in mixed precision.
        • LoRA freezes each chosen weight matrix W and learns a low-rank update: W'=W+\tfrac{\alpha}{r}BA, with rank r much smaller than the matrix sides.
        • Trainable parameters per matrix: r\,(d_{\text{in}}+d_{\text{out}}), often well under 1% of the model.
        • B starts at zero, so training starts from the original model.
        • After training, BA can be merged into W (no extra latency), or kept as a swappable per-task adapter.

        Likely follow-up: “Which matrices get adapters?” Originally the attention projections; applying it to all linear layers often works better. Review:

        Q4What is QLoRA?

        • The frozen base model is stored in 4-bit precision (the NF4 format); LoRA adapters are trained in higher precision.
        • Gradients flow through the dequantised base weights into the adapters.
        • Makes fine-tuning large models possible on a single GPU, at a small quality cost.

        Review:

        Q5What can go wrong in fine-tuning?

        • Overfitting: small datasets overfit within a few epochs. Hold out data, watch validation loss, usually 1 to 3 epochs.
        • Catastrophic forgetting: general abilities degrade. Use a lower learning rate, LoRA, or mix in general data; test general skills, not only the target task.
        • Learning rate: LoRA typically uses a higher LR than full fine-tuning.
        • Data problems: inconsistent formats, duplicates, leakage of test items into training.
        • No baseline: always compare against the best prompt-only result on the same eval.

        Review:

        Q6How would you build a fine-tuning dataset?

        • Start from real inputs: logs or user requests (with consent and PII handling).
        • Write or collect ideal outputs; stronger models can draft synthetic data, then humans review it (check the provider’s terms).
        • Clean, de-duplicate, use one format, and cover edge cases and refusals.
        • Split off an evaluation set before training and never train on it.

        Alignment

        Q7Explain RLHF.

        • Collect human comparisons: for one prompt, which of two responses is better.
        • Train a reward model to predict those preferences.
        • Optimise the policy (the LLM) with reinforcement learning, classically PPO, to maximise reward.
        • Add a KL penalty that keeps the policy close to the SFT model.
        • Effective but complex: several models in memory, sensitive hyperparameters, unstable training.

        Q8What is DPO, and why is it popular?

        • Direct Preference Optimization trains directly on preference pairs (chosen, rejected).
        • Its loss raises the probability of the chosen response relative to the rejected one, measured against a frozen reference model.
        • No separate reward model and no RL loop: simpler and more stable, similar results in many settings.
        • Many variants exist; the core idea is preference learning as a classification-style loss.

        Q9What is reward hacking, and why the KL penalty?

        • The policy finds outputs the reward model scores highly but people do not actually prefer: excess length, flattery, confident tone.
        • The KL penalty limits how far the policy moves from the reference model, restraining that exploitation.
        • Related symptom: sycophancy, agreeing with the user rather than being correct.

        Q10What is distillation?

        • Train a small student model on the outputs (or the full probability distributions) of a larger teacher.
        • Gives most of the teacher’s quality on the target task at a fraction of the serving cost.
        • The student rarely exceeds the teacher on that task; check licence terms before distilling from a commercial model.

        Building agents

        Q1What is an agent, and when should you not build one?

        • An LLM that chooses its own sequence of actions (tool calls) based on what it observes, until a goal is met.
        • A workflow is different: code fixes the steps and calls the LLM at chosen points.
        • Prefer the simplest thing that works: one call, then a fixed chain or workflow, then an agent only when the steps cannot be known in advance.
        • Agents cost more, are slower and harder to test, and errors compound over steps.

        Q2How does tool (function) calling work?

        • You describe each tool to the model: a name, a description and a JSON schema for its parameters.
        • The model replies with a structured call: tool name plus arguments.
        • Your code validates the arguments, executes the tool and sends back the result; the model never executes anything itself.
        • The model then continues: another call, or a final answer.

        Q3What makes a good tool?

        • A clear name and description: the model reads them like documentation.
        • A few well-scoped tools instead of many overlapping ones.
        • Typed parameters, enums where possible, sensible defaults.
        • Concise results and actionable error messages the model can recover from.
        • Safe by design: read-only where possible, idempotent, permission-checked. Standards such as the Model Context Protocol (MCP) let one tool server work with many clients.

        Q4What agent patterns do you know?

        • ReAct: alternate reasoning, an action, and the observation it returns.
        • Plan then execute: draft a plan, then work through its steps, re-planning when needed.
        • Reflection: the model critiques and revises its own output.
        • Orchestrator and workers: one agent splits the task and delegates to sub-agents. Useful for independent, parallel subtasks; costs more tokens and coordination.

        Q5How does an agent remember things?

        • Short-term: the context window. Trim, or summarise older turns, as it fills.
        • Long-term: write facts or past episodes to a store (database, vector index) and retrieve them when relevant.
        • Keep authoritative state (orders, tickets, files) in your systems, not in the model’s context.

        Review:

        Q6How do you get reliable structured output?

        • Use the provider’s structured-output or JSON mode with a schema.
        • Constrained decoding masks out tokens that would break the schema.
        • Always validate (for example with a schema library) and retry with the validation error included.
        • Keep schemas small and flat; describe each field.

        Reliability and safety

        Q7How do agents fail, and how do you mitigate it?

        • Loops and repeated actions: step, time and cost limits; detect repeats.
        • Wrong tool or invented arguments: clearer tool descriptions, validation, fewer tools.
        • Errors compound over long tasks: shorter tasks, checkpoints, verification steps.
        • Context overflow: summarise history, keep tool outputs short.
        • Stopping too early or claiming success: check the end state with code where possible.

        Q8What are the security risks of agents?

        • Prompt injection: web pages, emails or files contain instructions the model may follow. Treat all tool output as untrusted data.
        • Least privilege: only the tools and permissions the task needs.
        • Human confirmation for irreversible or outward-facing actions: payments, deletions, sending messages.
        • Sandbox code execution; keep audit logs of every action.
        • Assume an injected instruction will eventually get through, and limit what damage it could do.

        Review:

        Q9How do you evaluate an agent?

        • A suite of realistic tasks with a checkable outcome; measure the task success rate.
        • Check the end state with code where possible (a record created, a test passing).
        • Inspect trajectories: right tools, wasted steps, cost and latency per task.
        • Run each task several times; report pass rates, because runs vary.
        • Add every production failure to the suite.

        Mid-level interviews usually include a “how would you ship and run this?” discussion. The questions below cover evaluation, cost, latency, reliability and safety, and end with a worked system-design answer you can adapt.

        Evaluation

        Q1How do you evaluate an LLM feature?

        • Agree on what success means with stakeholders, and turn it into measurable criteria.
        • Build an eval set: real user inputs, edge cases, adversarial cases; a reference answer or rubric for each.
        • Choose the scorer by output type: exact match or parsing checks for structured output; task metrics; an LLM judge with a rubric for open-ended text; human review for a sample.
        • Run it offline on every prompt or model change, like a regression test; measure online after launch (A/B tests, feedback, task completion).

        Q2What are the pitfalls of LLM-as-judge?

        • Biases: position (prefers the first answer), verbosity (prefers longer), self-preference (prefers its own model family’s style), leniency.
        • Mitigate: a specific rubric with examples, pairwise comparison run in both orders, scores on narrow criteria rather than “overall quality”.
        • Calibrate: measure agreement with human labels on a sample before trusting it.

        Q3What causes hallucinations, and how do you reduce them?

        • The model is trained to produce probable text, not verified facts; gaps and outdated knowledge get filled with plausible guesses.
        • Ground answers in retrieved sources and require citations.
        • Let the model say “I don’t know”, and reward that in your eval.
        • Low temperature for factual tasks; a verification step for high-stakes claims; human review where errors are costly.
        • Measure the hallucination rate on your eval; it does not reach zero.

        Review:

        Q4How do you write and manage prompts?

        • Clear task and role, relevant context, explicit output format, a few examples.
        • For complex tasks, ask for step-by-step reasoning, or break the work into several calls.
        • Put long documents first and the question and instructions after them.
        • Version prompts, review changes like code, and run the eval before each release.

        Production

        Q5How do you choose a model?

        • Quality on your eval, not public leaderboards alone.
        • Latency (time to first token, tokens per second), price per million input and output tokens, context length, tool-use and multimodal support.
        • Data privacy and hosting: a hosted API or self-hosted open weights; licence terms.
        • Start with the strongest model to find the quality ceiling, then test cheaper ones; route easy requests to a smaller model.

        Review:

        Q6How do you estimate and reduce cost?

        • Cost ≈ requests × (input tokens × input price + output tokens × output price). Output tokens usually cost more.
        • Shorter prompts, capped output length, prompt caching for repeated prefixes, smaller models via routing, batch APIs for offline jobs, caching repeated answers.
        • Track cost per request and per user from day one.

        Review:

        Q7How do you reduce latency?

        • Time to first token grows with prompt length; total time grows with output length.
        • Stream the output so users see progress.
        • Shorten prompts and outputs; put static content first so it can be cached.
        • Run independent calls in parallel; use a smaller model where quality allows; speculative decoding when you host the model.

        Review:

        Q8What do you monitor in production?

        • Traces of prompts, responses and tool calls, with PII handling and retention rules.
        • Latency, error and timeout rates, token usage and cost, refusal rate.
        • User feedback signals and task completion.
        • Regular sampled human review; every failure becomes a new eval case.

        Q9How do you make an LLM service reliable?

        • Timeouts; retries with exponential backoff for rate limits and transient errors.
        • Fallback to another model or provider; graceful degradation when all fail.
        • Validate and parse every structured output; retry on failure.
        • Pin model versions; re-run the eval before upgrading.

        Q10What guardrails would you add?

        • Input checks: abuse, prompt injection patterns, off-topic requests.
        • Output checks: PII, policy violations, schema validity, groundedness for factual answers.
        • Least-privilege tools and confirmation steps for risky actions.
        • Red-team before launch and again after major changes.

        Worked system-design answer

        Q11System design: “Design a Q&A assistant over our internal documents for 5,000 employees.”

        Clarify (2–3 minutes)

        • Who are the users and what do they ask? What document types, how many, how often do they change?
        • Do permissions differ per user? Latency and cost targets? Languages?
        • How will we know it works: deflected tickets, time saved, answer accuracy?

        Ingestion (offline)

        • Connectors per source; parse to text while keeping structure.
        • Chunk by headings with metadata: title, path, date, owner, access list.
        • Embed and index for both vector and keyword search; re-index incrementally on change.

        Query path (online)

        • Rewrite the question using chat history.
        • Hybrid retrieval of the top 50, filtered by the user’s permissions; rerank to the top 5–8.
        • Prompt: instructions, passages with IDs, question; require citations and allow “I don’t know”. Stream the answer.

        Evaluation

        • A golden set of about 200 real questions with answers and source passages from subject experts.
        • Retrieval recall@k; answer faithfulness and correctness with a calibrated LLM judge.
        • Run on every change; add failures from production.

        Operations

        • Cost per query estimate; prompt caching; answer caching for frequent questions.
        • Tracing, feedback buttons, dashboards for latency, cost and “no answer” rate.
        • Fallback model; rate limiting.

        Risks and mitigations

        • Permission leakage → filter at retrieval. Prompt injection in documents → treat as data, no write tools.
        • Stale documents → dates in metadata, prefer newest. Hallucination → citations, abstention, faithfulness checks.

        Close

        • Ship a simple baseline first, measure each stage, improve the weakest one. Name what you would do with more time.

        Glossary and further learning

        1 LLM2 Why3 Tokens4 Position5 Attention6 Heads7 Block8 Model9 Train10 Generate11 Serve12 Scale13 Enc–dec14 Paper15 Q: Core16 Q: RAG17 Q: Tuning18 Q: Agents19 Q: Prod20 Glossary
        Token
        The unit of text a model reads and writes: a word, part of a word, a character or a symbol.
        Embedding
        A learned vector that represents a token (or a position) as numbers the network can compute with.
        Attention
        The operation that lets each token build a weighted blend of information from other tokens.
        Query
        The vector a token uses to express what it is looking for in other tokens.
        Key
        The vector a token exposes so queries can be matched against it.
        Value
        The vector a token contributes to whoever attends to it.
        Softmax
        A function that turns any list of numbers into positive values that sum to 1.
        Logits
        The raw, unnormalised scores a model outputs, one per vocabulary entry.
        Logits vs. probabilities
        Logits can be any real number and only their differences matter; probabilities are what softmax makes of them, lying between 0 and 1 and summing to 1.
        Residual stream
        The running vector for each token that every layer reads from and adds to.
        LayerNorm
        Rescales one token’s vector to mean 0 and standard deviation 1, then applies a learned scale and shift.
        MLP
        Multi-layer perceptron: the feed-forward network applied to each token separately inside every block.
        Context window
        The maximum number of tokens the model can take as input at once.
        KV cache
        Stored keys and values of earlier tokens, reused during generation to avoid recomputing them.
        Temperature
        A divisor applied to logits before softmax; low values sharpen the distribution, high values flatten it.
        Top-k
        Sampling restricted to the k most probable tokens.
        Top-p
        Sampling restricted to the smallest set of top tokens whose probabilities total at least p. Also called nucleus sampling.
        Loss
        A single number measuring how wrong the model’s predictions were; training tries to lower it.
        Gradient
        For every parameter, the rate at which the loss changes when that parameter changes.
        Optimizer
        The algorithm that converts gradients into parameter updates, for example SGD or AdamW.
        Parameter
        One learned number in the model: an entry of a weight matrix, bias or embedding.
        Checkpoint
        A saved snapshot of all parameters (and often optimizer state) at some point in training.
        Fine-tuning
        Further training of a pretrained model on a smaller, more specific dataset.
        RLHF
        Reinforcement learning from human feedback: optimising a model towards outputs people prefer.
        Encoder
        A Transformer stack with unmasked self-attention that reads a whole input sequence and outputs one vector per token.
        Decoder
        A Transformer stack with causal self-attention that generates a sequence one token at a time.
        Cross-attention
        Attention whose queries come from the decoder and whose keys and values come from the encoder output.
        Prefill
        The first phase of inference: the whole prompt is processed in one parallel pass and its keys and values are cached.
        Time to first token
        The delay between sending a request and receiving the first output token; roughly the prefill time.
        Throughput
        Tokens generated per second summed over all requests being served at once.
        BLEU
        A 0 to 100 score for machine translation that measures overlap of word sequences with human reference translations.
        Warm-up
        Raising the learning rate gradually from near zero over the first training steps, before letting it decay.
        Hallucination
        Fluent output that is false or unsupported. It arises because the model generates probable text, not verified facts.
        RAG
        Retrieval-augmented generation: fetching relevant passages at query time and placing them in the prompt so the model answers from them.
        Embedding model
        A model that maps a whole text to one vector so that similar texts have similar vectors; used for semantic search.
        Cosine similarity
        The dot product of two vectors after scaling each to length 1; the usual similarity measure for embeddings.
        BM25
        A classic keyword-ranking formula; strong for exact terms such as names and codes.
        Reranker
        A model that reads a query and a passage together and scores their relevance; more accurate and slower than embedding search.
        HNSW
        Hierarchical navigable small world: a graph index for fast approximate nearest-neighbour search.
        Chunking
        Splitting documents into passages of manageable size before embedding them.
        SFT
        Supervised fine-tuning on prompt and ideal-response pairs.
        LoRA
        Low-rank adaptation: fine-tuning by learning a small low-rank update to frozen weight matrices.
        QLoRA
        LoRA trained on top of a base model stored in 4-bit precision.
        DPO
        Direct preference optimization: training on chosen and rejected answer pairs without a separate reward model.
        Reward model
        A model trained to predict which of two responses people prefer; used in RLHF.
        Distillation
        Training a smaller model to imitate a larger one.
        Agent
        An LLM running in a loop that chooses actions, such as tool calls, until a goal is reached.
        Tool calling
        The model emits a structured request (name and arguments) for your code to run a function and return the result.
        Prompt injection
        Instructions hidden in user input, documents or tool output that try to override the intended behaviour.
        LLM-as-judge
        Using a language model with a rubric to score or compare outputs.
        Perplexity
        The exponential of the cross-entropy loss: the effective number of choices the model is unsure between.
        RoPE
        Rotary position embedding: encodes position by rotating query and key vectors.
        GQA
        Grouped-query attention: several query heads share one key/value head, shrinking the KV cache.
        FlashAttention
        An exact attention algorithm that works tile by tile in fast memory, avoiding the full T × T matrix.
        Mixture of experts
        A layer with many expert MLPs and a router that sends each token to only a few of them.
        Quantization
        Storing weights (and sometimes activations or the KV cache) in fewer bits to save memory and bandwidth.
        Speculative decoding
        A small draft model proposes tokens that the large model verifies in one pass, speeding up generation.
